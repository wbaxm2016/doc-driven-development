# 文档组织管理规范

> 通用规则只留指针，不在本文件复写（一个事实一处）：
> - 固定动作与收尾五连跑顺序 → `SKILL.md`「日常三动作」；
> - 硬规则 → `SKILL.md`「硬规则」；
> - 校验码（E / W / P / S / D / V）→ `references/check-rules.md`；
> - 提交前缀与 PR → `CONTRIBUTING.md`「提交与 PR」。

## 1. 改代码时的顺序（本仓库特有）

1. 先改模板与 `references/`，再改脚本，最后改 `SKILL.md`（常驻上下文是最后一环）。
2. **新增规则必须先在 `scripts/self_test.py` 立断言**，再谈文档里怎么写——2.1.0 之前的教训是：码表写了 W4/W5，代码从未实现。
3. 改完跑 `python scripts/self_test.py`，再跑 `python build.py`（体检会拦下 front-matter 缺字段、引用不存在、包内多文件少文件）。
4. **`.skill` 是构建产物**：只要改了**包内文件**（`scripts/`、`references/`、`assets/`、`SKILL.md`、`VERSION`、`.skill-metadata.yaml`）就必须发版，否则技能里的版本会悄悄落后；只改 `docs/`、`CHANGELOG`、`README`、`CONTRIBUTING`、`build.py`、`install.py` 不用发版。发版节奏与顺序见 CONTRIBUTING「发版与回滚」——**先提交、后打包**，`build.py --check-dist` 会拦"产物与 HEAD 不一致"。
5. `docs/` 与 `dist/` 的分界不得混淆：`docs/` 记录本项目怎么演化，`dist/` 是把能力交付给别人。
