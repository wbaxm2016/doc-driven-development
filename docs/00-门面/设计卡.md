# 设计卡

> **设计是工作与任务之间的一步，不是实施的一部分。** 工作与功能回答「做什么」，任务回答「这一场改什么」；设计回答「怎么做、哪里以后要换」。卡没定，不拆任务（`P19`）。
>
> **按改动大小伸缩**：小改动写三行（接口 / 可替换点 / 失败边界）；没有可替换点的写「无」并说明为什么（只写「无」按空算）；大改动才写满六格。判满六格会把设计门变成填表仪式。
>
> **一个工作一张卡。** 标题 `## K<n> · W<n.m> · 标题` 里的工作号是机器认的锚——`P19` 按它核对「还没做完的工作有没有卡」「卡里的工作是否存在」；卡号只增不复用。
>
> **和技术设计的分工**：`10-架构/technical-design.md` 写系统为什么这样搭；设计卡写「这一块以后要换，换哪里、换一处要改几处」，随工作产生、随工作归档。

## K1 · W5.8 · 设计步与可替换性

- **接口**：三样对外的东西——① `00-门面/设计卡.md` 的卡片形状（`## K<n> · W<n.m> · 标题` + `- **字段**：值` 六项）；② `plan.py check` 的 `P19`（三格必填 / 待开工与进行中的工作有卡 / 一工作一卡 / 孤儿卡）；③ `SKILL.md` 的设计门五问。
- **可替换点**：卡放独立文档还是并进技术设计（换承载只改 `names.design_card` 与 `designs_path` 两处）；卡用小节还是表格（解析只在 `load_designs` 一处，换写法不动判据）；「需要设计」按工作状态还是按任务状态判（`plan.design_before_states`，改词表不改代码）。
- **扩展点**：要加「设计评审记录」（谁评的、结论）就加一格，`P19` 三格不变；要记设计变更史就在卡下加 `### 变更`，解析忽略未知小节与未知字段。
- **失败边界**：卡缺失只报一条，不逐行刷屏；格子写 `—` / `待补` 按空算（与 `blank()` 同口径）；工作号写错会变成孤儿卡；小节改坏时 `load_designs` 返回 `None` 而不是空字典——否则「读不出」会被当成「没有卡」而静默通过。
- **任务拆分**：T5.8.1 一次做完（模板 + 本卡 + `P19` + SKILL / plan-model / check-rules 同步 + 第 38 组断言）；2.4.0 发版不在这张卡里，属 W8.1。
- **取舍**：卡做成小节而不是表格——接口与失败边界都是长句，表格会把它们压成一格，读者看不下去；代价是 `load_designs` 得自己解析小节（约二十行），换来「小改动写三行」这条伸缩规则能真的执行。

## K2 · W8.1 · 2.4.0 发版与可用端重装

- **接口**：三样对外的锚——① `VERSION`（唯一版本号来源，`build.py` / `install.py` / 包内 `.install.json` 都读它）；② `dist/doc-driven-development-<版本>.skill` 与 `dist/doc-driven-development.skill`（发版产物与「最新」别名）；③ `install-targets.json` 的 `targets[]`（产品级清单，装哪些宿主由它决定，不由本机决定）。
- **可替换点**：宿主清单与路径（加产品只改 `install-targets.json`，不改 `install.py`）；包来源 `--from worktree|dist`（发版必须以 `dist` 为准，两种来源同名不同物）；本机可用端（缺宿主时只影响「装了几端」，不影响产物本身）。
- **扩展点**：以后要有 release notes / 自动发布，从 `build.py` 的验包步骤之后接；要按平台分架构打包，从 `materialize()` 接。
- **失败边界**：宿主目录不存在时 `probe()` 报探查原因并计失败，**不猜目录名、不建目录**（假装比没装更难查）；`VERSION` 与 `dist` 不一致由 `build.py --check-dist` 拦；装完逐文件哈希不等即失败；本机缺宿主（dsh / 豆包 / Qoder CN 的 `skills` 目录）如实记「未覆盖」，不写成已装。
- **任务拆分**：T8.1.1 一次做完（bump `VERSION` → CHANGELOG → `build.py` → `--check-dist` → 按可用端 `--from dist` 安装 → 逐端哈希核对 → 回写）。
- **取舍**：不在本机伪造 dsh / 豆包 / Qoder CN 的技能目录来凑「5 端」——那会让「装了几端」这条证据失去意义；宁可写「声明端 5 / 可用端 2」，把缺口留在台账里（`probe()` 的探查原因就是证据）。

## K3 · W7.2 · 2.4.0 对外发布

- **接口**：三样对外可见的东西——① tag `v2.4.0`（指向包含 2.4.0 产物与回写的提交）；② release 正文（直接截 `CHANGELOG.md` 的 2.4.0 段，不另写一份摘要）；③ 资产 `doc-driven-development-2.4.0.skill` 与它的 sha256（下载核对用）。
- **可替换点**：发布通道（`gh` CLI / REST API——本机没有 `gh`，走 API，换通道只影响一条命令）；正文来源（截 CHANGELOG vs 手写摘要，选前者：同一件事不写两遍）；是否标 latest（默认标，仓库只有一个活跃版本）。
- **扩展点**：以后要「打 tag 即自动发布」，从 `.github/workflows` 接；要签名或校验和文件，从资产上传之前接。
- **失败边界**：tag / release 已存在时报错不覆盖（重发应先删旧 release 或换版本号）；上传中断按 API 返回的 `size` 与 `digest` 核对，不认「命令返回 0」；token 只从 `git credential fill` 取，不落文件、不进日志、不回显；网络失败重试一次即停，不循环重试。
- **任务拆分**：T7.2.1 一次做完（建 tag → 建 release → 传资产 → 下载核对 sha256）。
- **取舍**：不为一次发布去装 `gh`——一次 API 调用的事，装工具与维护登录态的成本更高；代价是脚本里要自己处理 token 与重名报错。
