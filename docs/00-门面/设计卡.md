# 设计卡

> **设计是工作与任务之间的一步，不是实施的一部分。** 工作与功能回答「做什么」，任务回答「这一场改什么」；设计回答「怎么做、哪里以后要换」。卡没定，不拆任务（`P19`）。
>
> **按改动大小伸缩**：小改动写三行（接口 / 可替换点 / 失败边界）；没有可替换点的写「无」并说明为什么（只写「无」按空算）；大改动才写满六格。判满六格会把设计门变成填表仪式。
>
> **一个工作一张卡。** 标题 `## K<n> · W<n.m> · 标题` 里的工作号是机器认的锚——`P19` 按它核对「还没做完的工作有没有卡」「卡里的工作是否存在」；卡号只增不复用。
>
> **和技术设计的分工**：`10-架构/technical-design.md` 写系统为什么这样搭；设计卡写「这一块以后要换，换哪里、换一处要改几处」，随工作产生、随工作归档。

## K1 · W5.8 · 设计步与可替换性

- **接口**：三样对外的东西——① `00-门面/设计卡.md` 的卡片形状（`## K<n> · W<n.m> · 标题` + `- **字段**：值` 六项）；② `plan.py check` 的 `P19`（三格必填 / 待开工与进行中的工作有卡 / 一工作一卡 / 孤儿卡）；③ `SKILL.md` 的设计门五问。
- **可替换点**：卡放独立文档还是并进技术设计（换承载只改 `names.design_card` 与 `designs_path` 两处）；卡用小节还是表格（解析只在 `load_designs` 一处，换写法不动判据）；「需要设计」按工作状态还是按任务状态判（`plan.design_before_states`，改词表不改代码）。
- **扩展点**：要加「设计评审记录」（谁评的、结论）就加一格，`P19` 三格不变；要记设计变更史就在卡下加 `### 变更`，解析忽略未知小节与未知字段。
- **失败边界**：卡缺失只报一条，不逐行刷屏；格子写 `—` / `待补` 按空算（与 `blank()` 同口径）；工作号写错会变成孤儿卡；小节改坏时 `load_designs` 返回 `None` 而不是空字典——否则「读不出」会被当成「没有卡」而静默通过。
- **任务拆分**：T5.8.1 一次做完（模板 + 本卡 + `P19` + SKILL / plan-model / check-rules 同步 + 第 38 组断言）；2.4.0 发版不在这张卡里，属 W8.1。
- **取舍**：卡做成小节而不是表格——接口与失败边界都是长句，表格会把它们压成一格，读者看不下去；代价是 `load_designs` 得自己解析小节（约二十行），换来「小改动写三行」这条伸缩规则能真的执行。

## K2 · W8.1 · 2.4.0 发版与可用端重装

- **接口**：三样对外的锚——① `VERSION`（唯一版本号来源，`build.py` / `install.py` / 包内 `.install.json` 都读它）；② `dist/doc-driven-development-<版本>.skill` 与 `dist/doc-driven-development.skill`（发版产物与「最新」别名）；③ `install-targets.json` 的 `targets[]`（产品级清单，装哪些宿主由它决定，不由本机决定）。
- **可替换点**：宿主清单与路径（加产品只改 `install-targets.json`，不改 `install.py`）；包来源 `--from worktree|dist`（发版必须以 `dist` 为准，两种来源同名不同物）；本机可用端（缺宿主时只影响「装了几端」，不影响产物本身）。
- **扩展点**：以后要有 release notes / 自动发布，从 `build.py` 的验包步骤之后接；要按平台分架构打包，从 `materialize()` 接。
- **失败边界**：宿主目录不存在时 `probe()` 报探查原因并计失败，**不猜目录名、不建目录**（假装比没装更难查）；`VERSION` 与 `dist` 不一致由 `build.py --check-dist` 拦；装完逐文件哈希不等即失败；宿主目录不存在的端如实记「未覆盖」，不写成已装（哪台机器有几个目录，只在该机器的装机记录里说）。
- **任务拆分**：T8.1.1 一次做完（bump `VERSION` → CHANGELOG → `build.py` → `--check-dist` → 按可用端 `--from dist` 安装 → 逐端哈希核对 → 回写）。
- **取舍**：不为凑「5 端」伪造目录——那会让「装了几端」这条证据失去意义；宁可如实写「清单 5 端 / 本机可用 N 端」，把缺口留在这台机器的装机记录里（`probe()` 的探查原因就是证据）。

## K3 · W7.2 · 2.4.0 对外发布

- **接口**：三样对外可见的东西——① tag `v2.4.0`（指向包含 2.4.0 产物与回写的提交）；② release 正文（直接截 `CHANGELOG.md` 的 2.4.0 段，不另写一份摘要）；③ 资产 `doc-driven-development-2.4.0.skill` 与它的 sha256（下载核对用）。
- **可替换点**：发布通道（`gh` CLI / REST API——本机没有 `gh`，走 API，换通道只影响一条命令）；正文来源（截 CHANGELOG vs 手写摘要，选前者：同一件事不写两遍）；是否标 latest（默认标，仓库只有一个活跃版本）。
- **扩展点**：以后要「打 tag 即自动发布」，从 `.github/workflows` 接；要签名或校验和文件，从资产上传之前接。
- **失败边界**：tag / release 已存在时报错不覆盖（重发应先删旧 release 或换版本号）；上传中断按 API 返回的 `size` 与 `digest` 核对，不认「命令返回 0」；token 只从 `git credential fill` 取，不落文件、不进日志、不回显；网络失败重试一次即停，不循环重试。
- **任务拆分**：T7.2.1 一次做完（建 tag → 建 release → 传资产 → 下载核对 sha256）。
- **取舍**：不为一次发布去装 `gh`——一次 API 调用的事，装工具与维护登录态的成本更高；代价是脚本里要自己处理 token 与重名报错。

## K4 · W9.1 · 主干道落点在项目里可达

- **接口**：三样对外的锚——① 项目里的 `40-运行/功能对照.md`（唯一实体，用户填它，`doc_init` 铺出来）；② 包内模板 `assets/templates/feature-check.md`（四列表头，原样复制）；③ `SKILL.md` 主干道第 7 格（冒烟命令 `python scripts/self_test.py`）与第 8 格（对照清单路径）。
- **可替换点**：落点从「包内模板」换成「项目内实例」只改 `doc_init.py` 的一行 `copy_tpl`；表头口径（三栏 / 四列）只改模板与 `SKILL.md` 两处，判据不动；冒烟命令换成本项目最便宜的端到端命令，只改第 7 格一处。
- **扩展点**：以后要机器判「对照清单填没填」，从 `doc_check` 加 E 码接（现在不判）；要把对照按功能拆成多份，从模板的节结构接。
- **失败边界**：模板缺 front-matter 时新项目首跑报 `E1`；`doc_init` 幂等，已存在的 `功能对照.md` 不覆盖；表头被改坏时 `self_test` 第 1 组「四列表头」直接失败，不静默放行。
- **任务拆分**：T9.1.1（落点 + 四列）→ T9.1.2（冒烟命令）→ T9.1.3（README 指针）→ T9.1.4（发版 2.4.1 并装 5 端）。
- **取舍**：不做「脚本判对照填没填」——填没填只有人知道，硬判会逼出假行；代价是对照这一步仍然靠纪律，这条已写在 SKILL 的边界里。

## K5 · W9.2 · README 与实现同口径

- **接口**：两样对外的东西——① `SKILL.md` 的「五道门 + 主干外两处决策」与「边界三段」（判不了 / 交给别的技能 / 并发假设）；② `README.md` 里对两套编号的说明（动作 1–11 vs 十一格）。
- **可替换点**：编号说明放 README 还是放 SKILL——放 README，因为两套编号的冲突只在读 README 时发生；边界三段的顺序可换，`self_test` 只认小标题在不在。
- **扩展点**：以后 README 再加一节讲流程，只需保证它指向 SKILL 已有的门 / 决策，不新增第三套编号；边界若要加第四类（如「交给 CI 的」），加小标题即可。
- **失败边界**：`self_test` 第 29 组三条断言盯的是「两处决策」「两段边界」「并发假设」的字样——改文案时若把这些词删掉，断言会红；但它**断不了「说的和做的是不是一回事」**，那一步仍靠人读。
- **任务拆分**：T9.2.1 一次做完（SKILL 两处补写 → README 编号说明 → 断言 → 2.4.2 发版装 5 端）。
- **取舍**：不去掉 README 的数字编号——数字是读者定位用的；代价是必须写一句「两套编号不同源」，这句话本身也要维护。

## K6 · W9.3 · 判据会自己醒来、锚点不许悬空

- **接口**：两样对外的锚——① `@YYYY-MM-DD` 这个约定（写在收件箱「回到条件」、ADR「撤销条件」、方向卡「走通验收」里）；② `brief` 首屏的「复核：」行，与 `P15` / `E27` 对 `完成于` 的判法。
- **可替换点**：日期从哪读（收件箱列 / ADR 小节 / 方向卡列）各自一段，加一类载体只加一个扫描函数；到期判定阈值只改 `cmd_brief` 里的一行比较。
- **扩展点**：以后要「提前 N 天提醒」，在比较处改成 `date - N`；要按来源分组计数，`due_items` 已经带 `where` 字段。
- **失败边界**：没写 `@日期` 的判据不会被唤醒——这是有意为之，猜日期会产生噪音；日期写错（如 `@2026-13-01`）解析不到就当没有；`待提交` 一律按缺锚点报，宁可收尾红一次，也不让锚点永久悬空。
- **任务拆分**：T9.3.1 一次做完（`due_items` + `brief` 一行 + `P15`/`E27` 收紧 + 第 39 组断言 + 2.4.3 发版）。
- **取舍**：不解析「下次动 X 时」这类自然语言条件——判不了的东西不假装判得了；代价是反向判据里只有写了日期的那部分会响，其余仍靠人。

## K7 · W10.1 · 问题终态的归档归属

- **接口**：三处文本必须同口径——① `SKILL.md` 硬规则 5 的终态归表句；② `assets/templates/inbox.md` 的顶部规则与两张归档表注释；③ `references/process-recording.md` 的「三张表」一节（唯一权威，另两处引用它）。
- **可替换点**：无——改的是规则文本，撤回即改回原句；若以后要机器判「拒绝行有没有落错表」，只能给归档表加状态列，那会与「表名即状态」冲突，须先改 ADR-003 与 `D7`/`D8` 的判法。
- **失败边界**：拒绝行留在「已闭环」表里脚本判不了（`D7`/`D8` 只判行所在表的字段齐不齐）；这条缺口靠硬规则 + 人读兜着，不假装机器能判。模板与硬规则不一致时以 `process-recording.md` 为准（一处一个权威）。

## K9 · W12.1 · 计划树视图

- **接口**：三种输出（文本树 / 单文件 HTML / JSON）与一个退出码约定——计划有错时**先渲染**再把错误打到 stderr、exit 1。数据只来自既有的 `load()` 与 `load_features()`，不新增读取路径。
- **可替换点**：渲染层与数据层分开——`tree_build()` 出结构，`tree_text()` / `tree_html()` 各管一种输出；要 SVG、Markdown 或别的样式，加一个 renderer 即可，不碰取数。`--out` 与 stdout 的落点也可换。
- **失败边界**：没有方向 / 工作 / 任务时打印 0 计数的空树，不报错；孤儿（工作没挂方向、任务没挂工作）单列「未挂」，不静默丢；HTML 里所有动态文本都走 `html.escape`；不引任何外部资源，断网可看。

## K10 · W13.1 · 想法抽取与落位建议

- **接口**：三样对外的东西——① 建议清单的字段（类别 `目标/愿景/功能/需求` · 原话 · 出处（文件 + 段）· 落点 · 查重结果）；② `E29`（引文在源文件里查不到 → 拒收，exit 1）；③ `SKILL.md` 收尾段的一句「跑一次整理」。
- **可替换点**：抽取由谁来写建议（会话里的 agent / 以后接外部模型）——本卡只定义「谁产出建议」，脚本不调模型；建议清单落盘还是只打 stdout（只打 stdout，落盘会变成第二份权威）；类别表可加第五类，只改 `_schema.json` 的一处枚举。
- **扩展点**：以后要「采纳即自动写入」，从第 ③ 步裁决之后接；要按会话批次统计整理到了多少，从清单的批次字段接。
- **失败边界**：引文被改写一个字 → E29 拒收（这是唯一必须机器判的一条，否则最后会变成「机器把自己编的话写进需求」）；落点不存在 → 拒收；档案缺 §3.2 → 只报「无原话」，不编造；同一想法跨会话重复 → 标「已存在」并给已有编号，不自动合并。
- **任务拆分**：T13.1.1 一次做完（抽取规则写进 SKILL + 校验脚本 + 第 46 组断言）。
- **取舍**：不让 LLM 直接写台账——写入必须过裁决；代价是每一步多一次人工确认，换来「每一行都点得回用户原话」。

## K11 · W11.2 · 状态转写子命令

- **接口**：一条命令 `python scripts/plan.py set-status <任务编号> --to <状态> [--commit <短号>] [--review "做法=…｜一致=…｜代价=…｜结论=…"] [--dry-run] [--json]`；输出一份「文件 · 表 · 行 · 原值→新值」清单；退出码 0 = 已写或无需写、1 = 被拒（零写入）、2 = 环境或配置问题。数据只来自既有的 `load()`（计划 §5）与 `load_features()`（FEATURES「任务考核」），不新增读取路径。
- **可替换点**：行定位按「表头 + 第一列编号」，不认行号（表格插行不炸）；写入收在 `write_if_same()` 一处，换成只写差异行或写 patch 都只改这里；转写核心是纯函数 `apply(plan_text, feats_text, change) -> (新文本, 清单)`，命令挂 `plan.py` 还是别处不影响它。
- **扩展点**：其它状态（进行中 / 阻塞 / 搁置）共用同一条转写；以后 FEATURES 功能行、工作行要转写状态，接同一个 writer 与同一份清单格式；`--json` 给代理与 CI 读（现在只给人读）。
- **失败边界**：七类拒绝——任务号不在计划 §5、状态不在白名单、`已完成` 缺四格、`已完成` 缺 `完成于`、锚点写「待提交」、读入后文件被改（sha256 变）、新文本跑 `validate` 不绿；任一发生都不落盘、exit 1、原文件字节不变。两文件各写临时文件、全部成功后再 `os.replace`；替换阶段若中途失败，如实报「哪个已换、哪个没换」，不假装原子。幂等：新文本与旧文本相同 → exit 0、不写、不动 mtime。
- **任务拆分**：T11.2.1（第 48 组断言先红：六类拒绝 + 幂等 + 零写入）→ T11.2.2（实现 `set-status`）→ T11.2.3（回写 REQ-017 / F-028 + 2.8.0 发版装端）。设计卡与 F-028 进台账在本场完成。
- **取舍**：不实现「从 `git log` 推断 `完成于`」——证据必须由人给；命令一旦自己决定证据是什么，它就真的成了第二条权威。代价是每次仍要人给四格与短号。

## K12 · W14.1 · 方向卡走通验收的机器判据

- **接口**：`plan.py` 的 `P18` 扩三条判据——①「走通验收」格非空且含 `@YYYY-MM-DD` 复核日；②「接缝」格非空；③ 路径 / 接缝 / 走通验收里出现的 `F-nnn`（FEATURES 台账）、`W<n.m>`（计划 §4）、`K<n>`（设计卡）必须存在。只读既有 `load_directions()` / `load_features()` / `load_designs()`，不新增读取路径。
- **可替换点**：判据落 `P18` 还是新码——选扩 `P18`（同一张卡、同一类错误）；要加/减判据只动 `validate()` 的 P18 段；复核日格式（`@YYYY-MM-DD`）与 `brief` 的到期扫描同源，改约定只动一处。
- **扩展点**：以后要判「每步必须引用 F」「走通记录更新后有没有过期」，从 P18 段接；存量项目可用 `doc_check --update-baseline` 开口子，不改判据本身。
- **失败边界**：卡缺失仍只报一条；缺必填格时先报缺格、不再叠日期与引用报错（不刷屏）；引用扫描只认 `F-\d+` / `W\d+\.\d+` / `K\d+` 形态，正文里顺口写的「F-」字样会被当成引用——宁可让人改名，也不放过坏引用；引用不存在只报存在性，不判「引用得对不对」。
- **任务拆分**：T14.1.1（第 37 组断言先红）→ T14.1.2（扩 `P18` + 补方向卡日期 + 模板 / 文档同步）→ T14.1.3（回写 + 2.8.1 发版装端）。
- **取舍**：不做「走通记录」独立载体（新表 / 新文档）——方向卡是唯一载体，加载体就多一处定义；不强制「接缝必须引用 W/K」——存量十行接缝都没有 W/K 引用，硬逼会造形式主义（ISS-069 的教训）。

## K13 · W15.1 · 语义门预审（对照门试点）

- **接口**：两样对外的锚——① 会话档案 §3.8「预审记录」五列（指向 / 逐字引文 / 疑点 / 建议动作 / 裁决）；② `doc_check` 的 `E30`（引文逐字、指向存在、表头无状态列、不适用条目不写结论）。预审的生成者是会话里的 agent，脚本不调模型、不产生建议。
- **可替换点**：生成方式（会话内 agent / 以后接脚本或插件）——`E30` 只认记录形状，不认生成者；记录落点（会话档案 §3.8 / 以后独立文件）——只改 `doc_check` 的扫描入口；门的范围（先对照门 / 以后扩其余门）——只改 SKILL 文本，不改 `E30`。
- **扩展点**：其余门按同一五列扩，可加「门」列区分；要统计采纳率，从「裁决」列接；要接插件提醒，从收尾段接。
- **失败边界**：引文改写一个字 → `E30` 拒收；指向的文件或行不存在 → 拒收；表头出现「状态 / 确认 / 评审 / 考核」列 → 报错（预审不是台账）；对齐门、发版 / 回滚、开放问题收口写成结论 → 报错；预审没有脚本写入口，「不改台账哈希」由试点时一次实测核对，不假装有哈希断言。判不了「疑点提得对不对」「该提的提全了没有」——这仍是人读。
- **任务拆分**：T15.1.1（第 49 组断言先红）→ T15.1.2（`E30` + 模板 + SKILL + 码表）→ T15.1.3（对照门试点 + 2.9.0 发版装端）。
- **取舍**：预审记录放会话档案而不是新表——会话档案是「这一场发生了什么」的唯一载体，新表会变成第二份权威；代价是档案多一节，且只对写了预审的会话存在。
