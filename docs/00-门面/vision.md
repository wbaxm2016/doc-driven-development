# 产品定位

> 一句话：把 AI 协作开发从「聊天里的临时共识」变成「文档里的可执行事实」。

## 愿景

让 AI 协作开发的上下文不再随窗口关闭而蒸发：每个项目都有一份**记得住、分得清、排得明、收得住**的项目记忆，人和 Agent 读的是同一份，做的判断基于证据而不是回忆。

- 对开发者：换会话、换人、隔三个月回来，仍能看懂「当时为什么、做到哪、下一步是什么」。
- 对 Agent：开场先读现状，不用重新对齐技术栈与约束；说「做完了」时指得出证据。
- 对项目：文档不再是开发之外的额外负担，而是开发过程本身的可执行骨架。

## 三层 + 一个地基

层不是按重要性排的，是按「回答的问题」和「被管理的方式」分的：

```
地基     文档是唯一事实源
         一处定义 · 引用可查 · 脚本可验
         回答：凭什么信？

结构层   三张网：过程 / 工作 / 问题
         回答：项目里有哪些对象、每个装在哪？

运行层   一个闭环：正向流 + 反向流 + 五道门
         回答：一次开发怎么走完、谁在什么时候判什么？

治理层   项目管理：排序 / 状态 / 门禁 / 棘轮
         回答：多个方向之间先做哪个、怎么不跑偏？
```

**为什么这样分**：同一层回答同一类问题，用同一种方式落地（唯一载体 + 编号 + 状态 + 判据）。地基回答「凭什么信」，结构层回答「有什么」，运行层回答「怎么流动」，治理层回答「先做哪个」。缺一层，上面那层就会退化成形式：

| 层 | 缺了会怎样 |
|---|---|
| 地基 | 代码和文档打架，Agent 得先猜信谁 |
| 结构层 | 过程蒸发、工作散、问题丢 |
| 运行层 | 做完了没证据；方向错了，测试全绿 |
| 治理层 | 每天重新决定做什么，或同时推五件、每件差一点 |

## 四类成本

这套东西不生产代码，也不替人做判断。它降低的是四类协作成本：

| 成本 | 不解决的后果 | 对应机制 |
|---|---|---|
| **重复对齐** | 换会话、换人、隔三个月，都要重讲技术栈、约束、进度 | 交接锚点 + `brief` + 功能行 + 决策回顾 |
| **假完成** | AI 说「做完了」，其实只改了代码；测试全绿但方向错了 | 冒烟 → 对照 → 考核 → `verify` → 完成于；状态只被证据推进 |
| **问题丢失** | 发现的问题要么拐进去丢主线，要么静默消失 | 发现即登记；候选 → 台账 → 约束；可关闭 / 开放两种命运 |
| **排序内耗** | 每天重新决定「今天做什么」，或同时推五件、每件差一点 | 三层 + 六维 + 三视角 + 门禁；下一步只有一个出口 |

## 四条承诺

1. **一处定义**：同类事实出现第二份，就是错误（`E16` / `W2` / 生成区不手改）。
2. **可回溯**：任一「已完成」指得出需求、代码入口、验收命令、commit（`E24` / `E27`）。
3. **可排序**：任一「下一步」来自唯一出口，且能追到方向、需求与功能（`P1–P16`）。
4. **不丢问题**：任一发现都有落点；能关的有闭环，关不掉的有回到条件（`D1`–`D10`：编号、性质、状态、依据、开放不得 `实现关闭`、归档完整）。

## 地基：文档是唯一事实源

不是「代码一份、文档一份，冲突时猜哪份新」。每件事只有一个定义处：

| 想知道 | 唯一载体 |
|---|---|
| 这件事怎么一步步变成现在这样 | 会话档案（一次会话一份，双侧记录）+ 生成的时间线 |
| 为什么这么定、还摆着哪些选项 | ADR（一文件一决策，带双向取代链与回到条件） |
| 下一步做什么、为什么是它 | 开发计划（方向 / 工作 / 任务三层 + 六维 + 多视角排序） |
| 必须成立什么、做到了没有 | 需求清单（REQ，EARS + `verify:`）+ 功能台账（F，入口 + 证据） |
| 发现了什么、什么时候回来 | 问题收件箱（ISS，唯一编号） |

`docs/_schema.json` 是层、枚举、段结构、编号规则、路径的唯一来源。规则有码、引用可查、生成区不手改——这三件事让「唯一」不是靠自觉，而是靠脚本。

**唯一性不是目的，可交接才是。** 新 Agent 不需要判断「信文档还是信代码」：功能行写清了满足哪条需求、代码入口在哪、用哪条命令验证；语义冲突仍要人读，但「哪份是准的」不再靠猜。

## 结构层：三张网

项目里只有三类对象需要被记住：**过程、工作、问题**。它们各有唯一载体、编号、状态和生命周期。

### 1. 过程网：开发过程可回溯

一次会话一份档案，留下五样：

| 记什么 | 具体 |
|---|---|
| 意图 | 你当时要什么——原话按类型归档，每句有落点 |
| 约束 | 答应过什么、明确排除了什么 |
| 取舍 | 还摆着哪些选项、为什么没选、什么条件下翻案 |
| 进度 | 做到哪、什么没做完、下一步是谁 |
| 证据 | 凭什么说做完了——功能 → 需求 → 代码入口 → 验收命令 → commit |

四条链让过程回得去：时间线（`devlog index` 重建）、ADR 取代链（被否决的选项不删）、功能行的「完成于」commit、收尾的决策回顾（四问，答不出标断链）。

**记录的读者不是审计，是下一个会话的 Agent。** 它先读交接段再动手，你不用重讲；「为什么」和「还没做什么」不随窗口关闭消失。

### 2. 工作网：需求线与方向线

| 线 | 回答什么 | 载体 | 判据 |
|---|---|---|---|
| **需求线** | 必须成立什么、做到了没有 | `REQ` → `F` → `T` | EARS + `verify:`；功能指回需求、入口与证据 |
| **方向线** | 用户怎么走通、系统怎么串 | `D`（现状的结论）→ `W` → `T` | 一条能被复述的成功状态；走通验收；`W` 挂 `D`、`T` 挂 `W` |

两条线不是父子，也不是两个并行流程：它们是同一个开发整体的两个切面——需求线按「必须成立什么」切，方向线按「用户怎么走通」切。它们在**任务**上合流：

```
REQ ──► F ──► T
              ▲
现状（定 D）─► W ┘
```

- 每个任务有且只有一个 `功能` 和一个 `所属工作`。
- 一个功能的多个任务可以跨多个工作；一个工作也可以含多个功能的任务——工作常常不是新功能，而是功能之间的接缝。
- `W` 挂 `D`，不挂 `REQ`；一条 `REQ` 可以跨几个 `W`，一个 `W` 也可以服务几条 `REQ`。

把任务想成一张表的格子：行是功能（需求线的切法），列是工作（方向线的切法）。一个任务落在某一行与某一列的交叉处；需求线读行，方向线读列，读的是同一张表。

**方向线是纵切线**：从一个产品切面（接入、开一场会话、回看一个决策、换一个 Agent 接着做）出发，把走通这段路要动的系统工作串起来。它不按模块切，不按需求清单切，也不按开发时间切——它按「用户走一遍」切。

**方向线的形成过程**：方向不是一开始就有的，它是开发者与 Agent 多轮对话的产物。

1. **现状（含定方向）**：先 `brief` 读一屏，再多轮对话把「现在有什么、卡在哪、哪些是旧账、哪些是新问题」说清楚。现状不是一句总结，是一组可核对的事实；**方向是这一步的结论，不是独立的一步**——一条用户能走通的路，写清成功状态、路径、接缝、不覆盖、走通验收，落在方向卡（`00-门面/方向卡.md`）的一行里，计划 §3 只留编号与依据。
2. **工作**：沿方向切成 1–3 场会话能独立验收的一段。
3. **设计**：在工作和任务之间，写设计卡——接口、可替换点、扩展点、失败边界、任务拆分；重要取舍开 ADR。设计定了再拆任务。
4. **任务**：把工作拆成一场会话能完成、能验证、能考核的最小改动。
5. **推进**：一个任务一个任务做；每做完一个，现状更新一次，下一轮从更新后的现状开始。

这不是一条单向流水线，是一个循环：**现状（含方向）→ 工作 → 设计 → 任务 → 推进 → 新的现状**。方向不是拍脑袋的路线图，它是从现状里长出来的下一步；任务也不是孤立的待办，它挂在工作和方向上，做完要往回核对。

**方向线是主线，需求线是底线**：

| | 方向线 | 需求线 |
|---|---|---|
| 回答 | 用户怎么用、系统怎么串 | 做到什么算数 |
| 失败模式 | 路径很顺但不可验证 | 功能很多但连不成路 |
| AI 的弱点 | 缺产品判断 | 自信假完成 |
| 角色 | 主线（用户这条路） | 底线（刹车 + 仪表） |

方向线更稀缺——AI 能起草需求、写功能、跑测试，但不会替你决定用户这条路怎么走、哪些系统工作该串进来；需求线更不可省——AI 会自信地说「做完了」，验收是唯一的解药。没有方向线，需求会变成功能堆叠；没有需求线，方向会变成不可验证的路线图。

### 3. 问题网：可关闭与开放

问题按四个正交维度管理：

| 维度 | 回答什么 | 取值 |
|---|---|---|
| **层** | 承诺到哪一步 | 候选层（`Q`）/ 台账层（`ISS`）/ 约束层（`REQ` / `ADR` / `D-W-T`） |
| **状态** | 处理到哪一步 | 候选 / 确立 / 实施中 / 实现关闭 / 拒绝 |
| **性质** | 能不能关 | 可关闭 / 开放 |
| **类型** | 是什么活 | 缺陷 / 缺口 / 债 / 冲突 / 风险 / 机会 / 待决 |

**层是承诺级别，状态是处理进度。** 候选在候选层，不占 `ISS` 号；分诊通过才进台账，状态从「确立」开始。这样既保留五段生命周期，又不会让每个一闪而过的念头都占一个编号。

**两种命运**：

| 性质 | 是什么 | 怎么处理 |
|---|---|---|
| **可关闭** | 缺陷、缺口、债、冲突 | 有完成判据；修完进「已闭环」，写结论与证据 |
| **开放** | 风险、机会、待决取舍 | 没有「做完」这个判据，只有「回到条件」：这一轮先做到哪、什么信号再回来 |

开放问题「永远不关」说的是**问题类**没有终点——单条可以在某一轮以「先做到这」或「决定不做」收口，但它不靠「做完」关闭，只靠「判断 + 回到条件」。状态上走 `确立 → 实施中 → 确立`，一轮做完回到确立，带着新的「本轮边界」和「回到条件」；`实现关闭` 只对「可关闭」开放。

**每个状态都要有依据**：

| 状态 | 依据写什么 |
|---|---|
| 候选 | 来源、一句话、影响初判、作废条件 |
| 确立 | 类型 / 性质 / 影响 / 落点 / 验收判据或回到条件 |
| 实施中 | 关联任务、当前进度（做到哪 / 卡在哪）、开始日 |
| 实现关闭 | 结论、证据（commit / verify / 测试）、闭环日、完成于 |
| 拒绝 | 理由、决策人、拒绝日、重新考虑条件 |

**价值**：收件箱既能关、又能开——可关闭的问题有闭环，开放问题有触发；不逼人为问题硬造任务（这个仓库自己踩过：为了「每条开放问题都有任务」硬造，噪音大于收益）。机器判得了字段齐不齐、开放有没有被 `实现关闭`、`deferred` 有没有回到条件；判不了这条到底该不该关——那仍要人读。

## 运行层：一个闭环

### 正向：主干道与五道门

`需求/现状 → 功能/方向 → 设计 → 工作/任务 → 实施 → 冒烟 → 对照 → 考核回顾 → 测试 → 回写`。五道门嵌在其中：

| 门 | 卡在哪 | 判什么 | 机器 / 人 |
|---|---|---|---|
| 对齐门 | 需求 / 方向确立前 | 用户复述或采纳了吗 | `E23` / `E24` 判有没有；人判对不对 |
| 评审门 | 功能 / 工作进计划前 | 满足需求吗、能实现吗、代价合理吗 | `E24` 判结论非空；人答三问 |
| 设计门 | 设计卡定稿前、拆任务前 | 接口稳定吗、可替换点隔离了吗、扩展点合理吗、任务拆分覆盖设计吗 | 设计卡在不在（机器）；判断（人） |
| 对照门 | 实施后、测试前 | 做的是不是需求那一句 | `E24` 判入口存在；人读行为 |
| 考核门 | `已验收` 前 | 做得值不值、代价估错没有；要不要重新设计 / 补任务 | `P15` 判任务四格与锚点、`E27` 判功能汇总；人写判断 |

**为什么对照在测试之前**：测试证明「符合断言」，对照证明「断言写的是需求那一句」。顺序倒了，会拿「为错方向写的测试全绿」当完成证据。

### 反向：向上回溯与沉淀

一个任务完成，从实现往上走一遍：

```
T 完成
 ├─► W：验收判据成立吗？证据贴得出吗？
 ├─► F：做的是不是这件事？（对照）→ 值不值？（考核回顾）
 │     ├─► 开放问题 → 重评可调整 / 可优化 / 可扩展
 │     │     ├─► 需要重新设计 → 回到「设计」
 │     │     └─► 只需补任务 → 回到「定任务」
 │     └─► REQ：能回写「已实现」吗？依据指得出吗？
 └─► D：用户这条路走通了吗？还有什么没覆盖？
```

- **核对**：入口存在是机器判，行为覆盖是人读；差异必须落一条 `ISS`。
- **考核回顾**：四格（做法 / 一致 / 代价 / 结论）写在**任务**上；功能只留一行汇总，回答「这些任务整体值不值」。之外还要回顾开发流程——哪里顺、哪里卡、代价估偏没有——并列出开放问题。
- **重评实现**：开放问题出现时，问一句「现在的实现还调得动吗？可优化吗？可替换吗？可扩展吗？」答案是否 → 先回到「设计」重新设计，再拆任务；只是缺一块小改动才回到「定任务」。开放问题不自动变成任务，只有要求改实现的那部分才变。
- **三个出口**：不需要补任务 → 测试 / 回写；需要补任务 → 定任务；需要重新设计（比如某个实现要可替换）→ 设计。即使没发现开放问题，只要回顾认为设计还要改，也可以回去。
- **回顾过程**：决策回顾四问；答不出标「断链」进待分诊。
- **沉淀体验**：任务的「考核」是这次改动的回顾（`F` 行只留汇总，点得出是哪几个任务）；会话 §7 的「别踩的坑 / 本场经验」是给下一个 Agent 的交接；ADR 是决策的成因。

没有这一条，前三层会退化成「记录得很整齐，但没人对结果负责」。

## 治理层：项目管理

| 层 | 回答什么 | 怎么算完 |
|---|---|---|
| 方向 | 为什么现在做这块 | 一个能被复述的成功状态 |
| 工作 | 1–3 场会话交付哪块能力 | 验收判据 |
| 任务 | 这一场做完什么 | 产物 + 证据 |

排期时，工作在「方向」下排队；下一步只留一个出口（六维打分 + 三视角排序）；状态只被证据推进——不是 Agent 说「完成了」就算完成。三条硬约束优先于分数：门禁 > 优先级；`R=5` 且动已存数据置顶；前置未解标 ⛔ 不排期。

项目管理的价值不是「管得细」，是「不用每天重新决定做什么」：开场 `brief` 给现状，收尾五连跑给证据，存量项目用基线棘轮只许降不许升。

## 方向线：节点与边

**功能是节点，方向是边。** 需求线建节点，方向线建边。只建节点，系统是一堆功能；只建边，系统是一条没有内容的空路。

### 为什么产品体验需要它

用户感知到的往往不是功能，而是**接缝**：上一步的数据有没有带过来？失败了能不能退？明天回来状态还在不在？换一个人能不能接上？空状态、权限、超时、重试——这些都不属于任何单个功能。功能测试全绿，用户这条路仍然可能走不通。

### 为什么系统级串联需要它

集成 bug 也住在接缝里：数据模型、状态机、权限、事件、错误传播，都是跨功能的东西，单个功能的测试覆盖不到。方向线的「工作」常常不是新功能，而是让 A 的输出成为 B 的合法输入、让 A 的状态变化通知 B、让 A 失败时 B 能回滚、让 A 和 B 的术语与错误码一致。

### 为什么 AI 协作需要它

- AI 擅长局部实现，不擅长全局产品判断；没有方向线，它会把每个 prompt 优化到最好，但功能之间不连。
- AI 会在功能级说「做完了」；方向线逼它走一遍端到端，看见接缝。
- AI 的上下文有限；方向线是一张压缩的「用户这条路」地图：现在在哪一段、下一段是什么、哪些接缝不能绕。
- 方向线是人的判断最该介入的地方：选哪条路、哪条先走、哪些体验不能妥协。AI 填实现，人定路径。

### 一条方向要有哪些东西

一个方向一行，写在 `00-门面/方向卡.md`；机器判「现状 / 成功状态 / 走通验收」三格在不在（`P18`），其余靠人读。

| 字段 | 写什么 |
|---|---|
| **现状** | 现在有什么、卡在哪、哪些是旧账、哪些是新问题 |
| **为什么是现在** | 为什么这条方向比别的更该先走 |
| **用户 / 角色** | 谁走这条路 |
| **起点** | 从什么状态开始 |
| **成功状态** | 可观察的终点（一句话） |
| **路径** | 3–7 步，每步用哪些功能 |
| **接缝** | 步骤之间的状态 / 权限 / 失败 / 空状态 |
| **不覆盖** | 这次不做什么 |
| **走通验收** | 一份可执行的 walkthrough 或 E2E |

**接缝是方向卡和「功能清单」的分水岭。** 写不出接缝，说明这条方向还只是几个功能的拼盘。

### 怎么验收

方向不能用一条 `verify:` 命令验收，它用**走通验收**：在干净环境里按路径走一遍，每步记录观察结果，包括失败路径、空状态、权限、重试。机器只能判「走通记录存在、每步引用的功能存在、接缝有归属」；走没走通、体验能不能接受，人判。

## 不是什么

- 不是「一次变更怎么讲清楚」——那是 Spec-Driven Development 的地盘，分工见 [ADR-001](../30-决策/adr/ADR-001-与SDD的分工.md)。
- 不是文档规范合集：规则有码、有脚本，不靠自觉。
- 不是项目管理软件：不做工时 / 甘特 / 看板同步，只管「下一步做什么、凭什么」。
- 不做语义判断：条款写得对不对、行为是不是这件事、开放问题该不该关，仍要人读。
- 不替代专业追溯工具：合规审计场景换 StrictDoc / sphinx-needs 承载契约层。
