# 产品定位

> 一句话：让 AI 协作开发「记得住、分得清、排得明」——把过程、决策与下一步写成会被脚本检查的文档。

## 愿景

让 AI 协作开发的上下文不再随窗口关闭而蒸发：每个项目都有一份**记得住、分得清、排得明**的项目记忆，人和 Agent 读的是同一份，做的判断基于证据而不是回忆。

- 对开发者：换会话、换人、隔三个月回来，仍能看懂「当时为什么、做到哪、下一步是什么」。
- 对 Agent：开场先读现状，不用重新对齐技术栈与约束；说「做完了」时指得出证据。
- 对项目：文档不再是开发之外的额外负担，而是开发过程本身的可执行骨架。

## 三条核心价值

### 1. 记得住（治「忘」）

AI 协作最贵的隐性成本不是写代码，是反复对齐：新会话要重讲技术栈和约束，同一个决定再吵一遍，「当时为什么」只剩「我记得」。

这条记录的不只是决策。决策只是「取舍」那一格；一次会话一份档案，留下五样：

| 记什么 | 具体 |
|---|---|
| 意图 | 你当时要什么——原话按类型归档，每句有落点 |
| 约束 | 答应过什么、明确排除了什么 |
| 取舍 | 还摆着哪些选项、为什么没选、什么条件下翻案 |
| 进度 | 做到哪、什么没做完、下一步是谁 |
| 证据 | 凭什么说做完了——功能 → 需求 → 代码入口 → 验收命令 → commit |

**价值**：这条不是「留档」，是**让上下文可交接**。记录的直接读者不是审计，是下一个会话的 Agent——它先读交接段再动手，你不用重讲；「为什么」和「还没做什么」不随窗口关闭消失。只记决策，交接时仍要重讲需求、约束、进度和证据，那等于没交接。

### 2. 分得清（治「混」）

问题按「命运」分，不按「紧急程度」分。待办有两种死法：永远清不完（把优化空间当缺陷修），或者静默丢掉（把开放问题当已完成关掉）——根因是两类混在一张表里。

| 命运 | 是什么 | 怎么处理 |
|---|---|---|
| 能关的 | 缺陷、文档债、口径冲突 | 有**完成判据**，修完进已闭环 |
| 关不掉的 | 优化空间、方向性机会、待决取舍 | 没有「做完」这个判据，只有**回到条件**：这一轮先做到哪、什么信号再回来 |

**价值**：收件箱既能关、又能开——可关闭的问题有闭环，开放问题有触发；不逼人为问题硬造任务（这个仓库自己踩过：为了「每条开放问题都有任务」硬造，噪音大于收益）。

> 一个精度：开放问题「永远不关」说的是**问题类**没有终点——单条可以在某一轮以「先做到这」或「决定不做」收口，但它不靠「做完」关闭，只靠「判断 + 回到条件」。

### 3. 排得明（治「乱」）

需求是一句话，落地是一个大任务——一个会话做不完，也说不清做到哪；于是每天重新决定「今天做什么」，或者同时推五件，每件都差一点。

把「要做什么」拆成三层，每层有自己的「做完」：

| 层 | 回答什么 | 怎么算完 |
|---|---|---|
| 需求 | 必须成立什么 | 一条能跑的验收命令 |
| 工作 | 1–3 场会话交付哪块能力 | 验收判据 |
| 任务 | 这一场做完什么 | 产物 + 证据 |

排期时，工作在「方向」下排队——方向回答「为什么现在做这块」；需求通过「功能」行接到代码入口与证据。**下一步只留一个出口**（六维打分 + 三视角排序），状态只被证据推进——不是 Agent 说「完成了」就算完成。

**价值**：颗粒度对上了，才谈得上「做完」；否则不是拖延，就是永远差一点。

### 三条是一条链

记得住 → 才分得清哪些是旧账、哪些是新问题；分得清 → 才排得明下一步该做哪件；排得明 → 做完的证据再回到记录里。缺一条，另外两条都会退化成「形式」。

## 这是什么

`doc-driven-development` 是一个 Agent Skill（本仓库是它的源码），用文档管住开发中三件最容易散掉的事：

| 想知道 | 唯一载体 |
|---|---|
| 这件事怎么一步步变成现在这样 | 会话档案（一次会话一份，双侧记录）+ 生成的时间线 |
| 为什么这么定、还摆着哪些选项 | ADR（一文件一决策，带双向取代链与回到条件） |
| 下一步做什么、为什么是它 | 开发计划（方向/工作/任务三层 + 六维 + 多视角排序） |

外加一张问题收件箱：过程里发现的一切先落地，不打断当前话题。

三件载体 + 收件箱，正好对应上面的三条价值：过程与决策 → **记得住**；下一步 → **排得明**；问题 → **分得清**。

## 两条线：需求线与方向线

需求一多，最容易卡住的不是「不知道要什么」，而是「知道要什么，却不知道先做哪件」。所以这里把两件事拆成两条线，各有各的载体与判据：

| 线 | 回答什么 | 载体 | 判据 |
|---|---|---|---|
| **需求线** | 必须成立什么、做到了没有 | `20-契约/requirements.md`（REQ）→ `40-运行/FEATURES.md`（F） | EARS + `verify:`；功能指回需求、代码入口与证据（`E22` / `E23` / `E24` / `W8` / `E26`） |
| **方向线** | 先做哪个、为什么是它 | `00-门面/开发计划.md`（D / W / T） | 六维打分 + 三视角排序；`W` 挂 `D`、`T` 挂 `W`（`P12` / `P6`） |

两条线不是父子关系，而是两条独立的轴：

- **工作挂在方向上，不挂在需求上**（`plan.py` 的 `P12` 只校验「方向存在」）。一条需求可以跨几个工作，一个工作也可以服务几条需求 / 功能。
- 它们在**功能行**交汇：功能写「满足了哪条需求」，也写「代码入口与证据」；排期时参照这些功能，决定先做哪块。
- 脚本能判的硬链接只有「功能 → 需求」（`E24`）与「需求有没有功能覆盖」（`W8`）；「工作 / 任务 → 需求」靠人写在「关联」里，不强制——这是两条线各自独立的代价，也是它们能各自成立的原因。

**为什么分开**：只有需求线，你会知道「必须成立什么」，但不知道「先做哪件」；只有方向线，你能排出很漂亮的顺序，却没人说得清它满足了哪条需求。需求少时一条方向就够；需求一多，方向线就是那根把工作串起来、让排期不跟着需求树打结的线。

## 为什么是文档

和 AI 结对开发时，需求只活在聊天记录里：对话一关，技术栈、约束、取舍全归零；而「记录」一旦写成散文，它既不能被校验，也不能被排序，最后既不会被人读，也不会被 Agent 读。所以本技能不做文档规范合集，只做**三件带校验的事**：每条规则有码、每个引用可查、每个下一步有分数。

## 不做什么

不解决「一次变更怎么讲清楚」（那是 Spec-Driven Development 的地盘，分工见 [ADR-001](../30-决策/adr/ADR-001-与SDD的分工.md)）；不做语义判断（条款写得对不对、撤销条件是否成立，仍要人读）；不替代专业追溯工具（合规审计场景换 StrictDoc / sphinx-needs 承载契约层）。
