# 真机验收台账

> **这是什么**：实现不是最终版时的落点——两种实现比不出优劣、明知是临时方案、或结论只能等真机用出来。结论没出来之前，它既不是缺陷也不是待办，所以不进问题收件箱。
> **什么时候开单**：① 两种实现对比不出优劣；② 明知是临时实现、迟早要换；③ 结论依赖真机使用体验（用够久 / 攒够场景 / 等到某个信号）。纯实现选择、行为不变的重构、能当场验证的，不开单。
> **判据三型**，写在「判据」列，格式 `类型:门槛`：`时长:N`（用够 N 天）、`场景:N`（N 个不同场景下用过且没出事）、`信号:一句话`（某事件出现或不出现）。样本型按**不同场景**计，不按次数计——同一场景用十次不算十份数据。
> **状态**：观察中 → 信号已足待拍板 → 已定论。`信号已足` 是人看到进度后改的；`rv list` 只提示「到门槛了」，不替人拍板。
> **结论出口**：「结论 · 出口」列必须写三种之一：`保持：一句话`、`改造：T 或 REQ 编号`、`撤销：回滚 <commit 短号>`。改造与撤销要能落地，否则不许写「已定论」。
> **不开场列**：这张表不进开场简报，也不显示计数。用户问「还有哪些问题」时才展开（`rv list`）。
> **记录**：每场收尾 AI 问一句「这段时间用到了吗」；会话里出现「刚试了…」「用了一下…」这类痕迹时由 AI 直接追加一条，记录人标 AI 或用户。
> **机器只判形式**：编号格式与重复（V1）、判据格式（V2）、状态词（V3）、定论出口是否带编号（V4）、观察记录是否指向存在的编号与合法日期（V5）、回看日格式（V6）。判不了「用够了没有」「这个场景算不算新」。
> **时间盒**：回看日到期必须拍板（保持 / 改造 / 撤销三选一），或写明续期理由 + 新回看日；续期最多 2 次，第 3 次到期不许再续——到了必须拍板，哪怕结论是「保持，理由：用了这么久没出事」。
