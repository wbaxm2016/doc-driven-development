## 3. AI 侧记录

### 3.1 需求理解

把它理解成：给「下次还会用到、但既不是问题也不是决策」的开发经验加一个**项目级唯一落点**，机器只判形式、语义归人。与用户原话的偏差：用户没说要不要新开载体；本场用一次两问确认（载体三选一 / 内容四类可多选），用户选 A + 四类全要——这一步不是替用户拍板，是把「载体」这个真取舍摆出来。

### 3.2 实现思路

1. 先判类 `R` → 回看既有四个去处（§3.6 摩擦 / §7 别踩的坑 / 收件箱 / ADR + SKILL「坑」），确认是**缺口**不是重复。
2. 载体单独一张表：`70-过程/经验台账.md`，九列；`_schema.json` 加 `names.experience` 与 `ids.experience`——结构仍只在一处定义（硬规则 11）。
3. 判据只写一处：SKILL 硬规则 18；收尾段落只写动作指针；模板与 `references/reference.md` 只写形状。
4. 机器侧只加 `E33`（形式）：表头九列 / 编号 / 类别与状态白名单 / 必填列 / 来源编号存在 / 日期。台账自身不进 `known_refs`——否则写错一个 `ISS` 能自己证明自己。
5. 先立断言：`self_test` 第 76 组 9 条（铺骨架 / 首跑 / 合规三态 / 六类坏例 / 修回复原）。
6. `doc_init` 铺进新项目；本仓先种 5 条真实经验，证明它不是空壳。

**否决的做法**：并入 §3.6（跨会话检索不到）；只写规则不建载体（没有落点，等于没做）；新加一条写入命令（多一条写路径，违反「一处一条」）。

## 4. 决策与选项对比

### D1 · 经验落在哪个载体

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 新开项目级台账 | 高（一表可检索） | 中（模板 + schema + E33 + `doc_init`） | 五类载体 | 高（删文件 + 撤一条规则） | 中（靠定期减法清） | 高（多一张能查的表） | 高（E33 判形式） | 变成第二份坑列表 |
| B 并入 §3.6 | 中 | 低 | 一处 | 高 | 低 | 低（散在 166 篇档案） | 低 | 跨会话检索不到 |
| C 只写规则不建载体 | 低 | 低 | 一处 | 高 | 低 | 低 | 无 | 没有落点，等于没做 |

**结论**：选 A
**是否暂定**：否
**拍板**：用户（2026-11-19 选项 A）
**依据**：「A. 新开项目级「经验台账」（推荐）」
**复述**：—（用户在选项里已看到代价「多一个载体要维护」；这是可回退选择，按 REQ-064「可逆实现细节不逐项问」不再补复述门）
**为什么更合理**：对比维持 §3.6 与只写规则：选 A 换来「按场景查得到」与「过期有去处」；放弃的是零新增载体的简洁，代价是每场多写一行、每 4 场扫一次。
**撤销条件**：连续 3 场台账没有新增、或全是重复条目 → 退回 §3.6（RV-007 到期时判）。
**被否方案**：B（回到条件：出现「一条经验跨 3 场重复写」）；C（回到条件：用户明确只要口径不要台账）。
