## 3. AI 侧记录

### 3.1 需求理解

用户要的不是「再写一个工具」，而是**把状态回写从「多文件手工编辑 + 每次编辑前重读」换成一条命令**，且这条命令不能变成第二个权威。三个词各指一件事：

- **输入输出**：能说清「给它什么、它改哪几格、它回什么」，否则没法给它写断言。
- **失败不写半截**：ISS-036 记的 4 次 stale 都是「改了一半、文件被 `plan.py index` 重写」；命令要么全改，要么一个字节都不动。
- **不成为第二条写路径**：状态仍由证据推进、人工编辑仍等价；命令只做「把已裁决的状态写进既有载体」的转写。

与用户原话的偏差：用户说「补一条 REQ」，我把它扩成「四类输入 + 考核四格」（§4 D1 A）——因为 `P15` 要求已完成任务四格齐全，只写状态与 `完成于` 的命令写不出合法的 `已完成`。这一处已显式标出，用户本轮采纳时未提异议。

### 3.2 实现思路

1. **输入**：`<任务编号> --to <状态> [--commit <短号>] [--review "做法=…｜一致=…｜代价=…｜结论=…"] [--dry-run]`；`--to 已完成` 时后两项必填。
2. **读**：一次读入计划文档与 FEATURES，记下两文件的 sha256 与 mtime（stale 守卫的基线）。
3. **内存构造**：按「表头 + 第一列编号」定位行（不认行号），产出两份新文本 + 一份「文件 · 表 · 行 · 原值→新值」清单。
4. **验**：用同一套 `load` / `load_features` / `validate` 对**新文本**跑一遍（`P15` / `P16` 必须绿）；任一条不过 → 放弃，不落盘。
5. **写**：两文件各写临时文件再 `os.replace`；写前重算 sha256，与基线不等 → 放弃；新文本与旧文本相同 → 直接 exit 0（幂等）。
6. **断言先行**：`self_test` 第 48 组先红（六类坏输入 + 幂等 + 零写入），实现后转绿。

**结论**：选 A。B 写不出合法的 `已完成`（`P15` 要求四格 + `完成于` 齐全），命令会停在半成品；C 仍要手工编辑，正是 ISS-036 记的那次 stale 复发路径。

**撤销条件**：若实现时发现四格文本经命令行传入会诱发「照抄模板」，退回 B（四格手写）并另开一条只转 `状态` 的子命令；触发信号是首次出现两条任务考核四格逐字相同。
