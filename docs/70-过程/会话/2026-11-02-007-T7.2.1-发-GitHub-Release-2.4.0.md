## 3. AI 侧记录

### 3.1 需求理解

「发 release」不是点一下按钮：对读者而言，一个 release 要能回答三件事——**这一版包含什么**（正文）、**代码停在哪**（tag）、**拿到的东西是不是这一版**（资产与哈希）。所以验收不是「页面 200」，而是「资产下载回来后 sha256 与 `dist/` 一致」。

本机没有 `gh`（`gh: command not found`），但 `git credential fill` 里有一个能推代码的 token。选择走 REST API：建 release（`target_commitish` 指 HEAD，`make_latest`）→ 上传资产 → 匿名下载回核。token 只活在进程变量里，不落文件、不回显。

### 3.2 实现思路

设计见 `00-门面/设计卡.md` 的 **K3 · W7.2**。顺序：

1. **先立任务与卡**：W7.2（D7）+ T7.2.1（挂 F-012 打包与验包）+ 设计卡 K3——`P19` 要求进行中的工作有卡。
2. **取凭证与仓库信息**：`git credential fill` 拿 token，`git remote get-url` 解析 `owner/repo`，`rev-parse HEAD` 拿目标提交。
3. **建 release**：`POST /repos/{slug}/releases`，`tag_name=v2.4.0`、`target_commitish=<HEAD>`、正文取 `CHANGELOG.md` 的 2.4.0 段（1472 字）、`draft=false`、`make_latest=true`。GitHub 顺带把 tag 建在目标提交上。
4. **传资产**：`POST https://uploads.github.com/.../assets?name=doc-driven-development-2.4.0.skill`，二进制体 147604 字节。
5. **回核**：拿 `browser_download_url` 匿名 `curl` 下来，`sha256sum` 与本地产物比；同时读 API 的 `assets[].digest`（GitHub 自己算的）三方对齐。
6. **同步 tag**：`git fetch --tags`，本地也有 `v2.4.0`。
7. **回写**：计划两行、FEATURES 任务考核、D7 方向卡的现状与走通验收。

## 4. 决策与选项对比

### D1 · 发布通道：装 `gh`、手动网页传，还是直接调 REST API

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 先装 `gh` 再发 | 高 | 中（装包 + 登录态） | 本机环境 | 高 | 中（多一个要维护的登录） | 无差别 | 高 | 装完还得 `gh auth login`，为一次性动作引入长期依赖 |
| B 网页手动建 release + 上传 | 高 | 低 | 无 | 高 | 差（正文靠复制，容易漏段） | 无差别 | 低（要人工核对哈希） | 手传大文件易中断，且没留下可复跑的命令 |
| C 用 git 凭证里的 token 调 REST API（选中） | 高 | 低 | 无 | 高 | 好（脚本可复跑） | 无差别 | 高（API 返回 digest，可再下载回核） | token 处理不当会泄漏——只放进程变量、不回显 |

**结论**：选 C。一次 API 调用能做完的事，不引入新工具；脚本化的好处是资产与正文都可复现，且 GitHub 自己回一个 `digest` 供三方对齐。
**是否暂定**：否。
**拍板**：agent 自选（发布通道，属于实现选择，不进决策回顾）。
**依据**：本机 `gh: command not found`；`git credential fill` 能取到可推代码的 token；ADR-001 的分工里「工具怎么发」不在契约层。
**撤销条件**：第二次发版时若仍要手写一百多行脚本，或需要 draft / 多资产 / 签名，就装 `gh` 或抽成 `scripts/release.py`。
