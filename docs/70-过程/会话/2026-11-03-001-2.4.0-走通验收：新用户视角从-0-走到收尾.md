## 3. AI 侧记录

### 3.1 需求理解

「继续开发」落在本仓的含义不是「接着做排好的活」——`brief` 已经说计划 47/47 全完成，没有排好的活。所以我先把它拆成两件事：**选下一件**（决策）与**做掉它**（执行）。选的那步我给了三个候选并标了推荐（A 走通 / B 修口径债 / C 唤醒机制），用户选 A。

偏差要说清：我原本倾向直接按六维排序开修 ISS-052/053/055（读出来的债），用户选的是先走通。事后看这个顺序更对——走通当场把 052 与 055 从「读出来的债」变成「遇到的坑」，还多出一条谁都没料到的 057（装机记录与磁盘不符）。**读出来的债与撞上的坑，可信度不一样。**

本场对「走通验收」的口径也收窄了一处：D7 原文要求「干净机器」，本轮只能做到「本机干净克隆 + 空目录新项目」，所以结论按「贡献者路径本机可复现」写，不冒充「干净机器已验证」。

### 3.2 实现思路

四条证据链，每条都要求「文档说什么 → 我跑什么 → 实际输出什么」：

1. **贡献者路径（干净克隆）**：`git clone` 本仓到 `D:\career\_wt\clone-ddd`（HEAD=0881f17）→ `python scripts/self_test.py`（203/203）→ `python build.py`（体检 / 自测 / 打包 33 文件 / 验包 32 文件哈希吻合 / 解包自测 203/203，sha256 `087e7287…` 与 release 一致）→ 改一处 docs → `doc_check` 0 error → `git commit` 成功。
2. **装机路径**：`python install.py --list`（5 个宿主全部 `[ok]`，各自报「已装 v2.3.2」）→ `python install.py --only dsh`（34 文件、v2.4.0、source=worktree、commit 0881f17）→ **用绝对路径回读** `~/.dsh/skills/doc-driven-development/.install.json` 核对，而不是相信脚本自己打印的那行。
3. **新项目路径**：空目录 `init` 成 git 仓 → `python "<已装技能>/scripts/doc_init.py" --target .`（14 篇，`doc_check` errors=0）→ `devlog brief`（无档案提示）→ `devlog new` → 待分诊门（`ask` 后 `new` 被拒 exit 1，`--clear` 后通过）→ 收尾五连跑 → 轻档改动复跑 `doc_check`。
4. **对照**：把每一步的「文档承诺」与「实际输出」并排放，差异才登记；一致的不写进 ISS。

## 4. 决策与选项对比

### D1 · 计划已清空时，这一场做哪件

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 走通验收（实跑一次） | 高：直接验 D7 的承诺 | 中（40–60 分钟） | 无代码改动 | 高：临时目录可删 | 好：产出的差异是事实 | 中 | 高：每步有命令与输出 | 可能一场只发现「文档没错」 |
| B 修口径债（052/053/055/056） | 中：修的是读出来的债 | 低 | 文档为主 | 高 | 好 | 中 | 高 | 可能修了没人踩的那部分 |
| C 唤醒机制（050 + 046） | 高：补机制度量 | 高（动 devlog/plan/_schema） | 大 | 中 | 中 | 高 | 中 | 机制先于实例会产生新债 |

**结论**：A。理由不是「A 分数高」，而是**它能把另外两条的输入换成证据**——052/055 当场复现，057 是读文档读不出来的；先修后测等于拿猜的清单开工。
**是否暂定**：否
**拍板**：用户
**依据**：用户在本轮从三个候选中选「A · 走通验收（推荐）」
**撤销条件**：若连续两场走通都只产出「文档没错」的结论，说明它已不是瓶颈，改为按六维排序直接修债。
