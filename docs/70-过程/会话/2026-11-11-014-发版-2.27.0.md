### D1 · 2.27.0 发版的范围

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |

| **A 出 2.27.0 包、装 6 端、推 origin，不打 tag / 不发 GitHub Release** | 高：脚本行为变了，按 minor 升版 | 中：一次打包 + 6 端逐字节核对 | 中：`VERSION` / `CHANGELOG` / `dist/` / 6 端安装目录 | 中：重装 2.26.0 包 + 回退版本号即可 | 低 | 高：端上立刻不再每场误报「整理」 | 高：`--check-dist` + 逐端「缺 0 / 不等 0」+ `origin/main = HEAD` | 低 |
| B A 之外再打 `v2.27.0` tag 与 GitHub Release | 中：本版没有需要长期回滚的契约变化 | 高：凭据 / 网络 / 资产回核 | 大：对外资产与 digest | 低：发布后不许动 tag | 中 | 中 | 中 | 中：网络短断会留半成品 |
| C 只重打 `dist/`、不升版本 | 低：同名 2.26.0 会含两份不同内容 | 低 | 中：`dist/` 同名覆盖 | 高 | 低 | 中 | 低 | 高：用户与产物对不上 |

**结论**：A（2.27.0：ISS-118 修复入包、装 6 端、推 origin）。
**是否暂定**：否。
**拍板**：用户。
**依据**：「把 ISS-118 的修复发版（2.27.0）并装到 6 端，然后把 3 个本地提交推上 origin」。
**复述**：—（用户整句已写明要做什么与验收：2.27.0 入包 / 6 端 / 推送；推翻代价 = 重装 2.26.0 包并回退版本号，重发一版）。
**为什么更合理**：ISS-118 的收益本来就要靠「端上不再误报」兑现，只把修复留在仓库等于收益停在半路；B 把一个普通 minor 变成对外资产，网络一断就留半成品；C 会让「2.26.0」这个已发布版本名指向两份内容，用户与产物对不上。
**撤销条件**：若任一宿主装后自测不过或 `brief` / `flow` 行为异常，重装 `dist/` 里 2.26.0 的包并把 `VERSION` 回退，修好后发 2.27.1；若 `git push` 后 `origin/main ≠ HEAD`，以远端为准重推，不 force。
**被否方案**：B（回到条件：用户要对外发布，或出现需要「回到这个版本」的真机问题）；C（回到条件：只改了 docs / README，包内文件没变时）。
