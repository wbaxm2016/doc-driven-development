## 3. AI 侧记录

### 3.1 需求理解

两件事：**第一，把 2.4.0 真正发出来**——不是改个 `VERSION` 就算发版，要 `build.py` 验包（解包后按安装方视角再跑一遍自测）、`--check-dist` 证明产物与 HEAD 逐字节一致。**第二，按本机实际情况装**：用户说的「没有豆包跟 DSH」是一条约束，不是让我去造目录。

于是「5 端」这个说法在本机只能兑现成 2 端。这里的选择是：**如实记几端可用、缺哪几端、为什么缺**，而不是把 `install-targets.json` 里那两个条目删掉或改成 `enabled: false`——清单是产品级的（支持哪些宿主），本机装没装是环境级的，两件事不该混。`probe()` 的探查原因是现成的证据，直接抄进台账。

与计划验收的一处偏差：计划验收写的「可用端」在本轮定义为「`probe()` 能探查到技能根目录的宿主」，而不是「清单里所有宿主」。

### 3.2 实现思路

设计与顺序见 `00-门面/设计卡.md` 的 **K2 · W8.1**。关键顺序：

1. **先立任务再动手**：计划 §4 加 W8.1、§5 加 T8.1.1（挂 F-012 打包与验包）、设计卡加 K2——`P19` 要求 `待开工` / `进行中` 的工作有卡，先写卡才不红。
2. **改 `VERSION` + CHANGELOG，先提交**：`build.py --check-dist` 要求包内文件无未提交改动；包里字节必须等于某个提交的字节，`.install.json` 记的 commit 才有意义。
3. **打包**：`python build.py` → 体检（元数据 / SKILL 引用 27 个路径 / 7 个脚本语法）→ 源自测 203/203 → 打包 32 文件 → 验包（解包后再跑一遍自测）。
4. **校验产物**：`python build.py --check-dist` → 32 个文件与 HEAD 逐字节一致。
5. **按可用端安装**：`python install.py --from dist --only qwenworkcn,workbuddy`；不带 `--only` 会把缺宿主计成失败，这也是有用的信息（本轮用 `--list` 先探查过一次）。
6. **逐端核哈希**：把包内 32 个文件的 sha256 与两个安装目录逐文件比，`缺 0 / 多 0 / 不等 0`。
7. **回写**：计划两行 + FEATURES 任务考核 + D3 方向卡的现状与走通验收（现状是「现在有什么」，发完版就该更新）。

## 4. 决策与选项对比

### D1 · 缺宿主时怎么记账：改清单、造目录，还是如实记未覆盖

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 把 dsh / 豆包从 `install-targets.json` 删掉或 `enabled: false` | 低 | 低 | 小 | 中 | 差（产品能力被本机环境改写） | 低 | 中 | 换一台机器又要改回来；清单不再回答「支持哪些宿主」 |
| B 手工建 `~/.dsh/skills`、`~/Doubao/skills` 凑满 5 端 | 低 | 低 | 小 | 高 | 差 | 低 | 低 | 证据失真：目录存在不等于宿主会读，等于自己骗自己 |
| C 清单不动，按 `probe()` 装可用端，缺的如实记原因（选中） | 高 | 低 | 无 | 高 | 好 | 中 | 高 | 「装了几端」要读台账而不是数目录 |

**结论**：选 C。清单回答「支持谁」，`probe()` 回答「本机有没有」，台账写两者的差。
**是否暂定**：否。
**拍板**：agent 自选（记账方式，不涉及产品清单与 ADR）。
**依据**：用户本场原话「本机没有豆包跟DSH」；`install.py` 的既有约定「目录缺失时按探查原因报错，不猜目录名」。
**撤销条件**：出现「因为记录写的是 2 端、所以以为只支持 2 个宿主」的误解 ≥ 2 次，或 CI 需要按端数做断言时，改成清单里显式区分 `enabled` 与 `available`。
