## 3. AI 侧记录

### 3.1 需求理解

两条约束是给「提交—任务」之间立锚：提交要能回溯到任务，重档变更必须先有任务锚点才能动手。原话「设计到」按「涉及到」理解、「哦」为衍字，不影响语义。**偏差点**：①「代码变更」的覆盖面原话没给边界，经复述门拍板为「重档都触发」（复用硬规则 12 的轻 / 重档白名单，不新造第二条口径）；②「创建任务并落档」被理解为**先建后改**——这两步发生在动手改之前。②比字面更严，是「按任务提交」推到底的必然结论：没有任务锚点的变更，之后没法按任务提交。

### 3.2 实现思路

1. `AGENTS.md` 在「文档约定」后加「Git 提交与任务」一节：两条 bullet；提交前缀引用 `CONTRIBUTING.md`、分级判据引用 `SKILL.md` 硬规则 12，都只引用不复制。
2. 规则自身适用自身：本场 `AGENTS.md` 改动＝规则＝重档 → 先挂 T2.1.2（W2.1 / F-007；W2.1 已完成，追加任务无需新设计卡）再动手；提交后回写完成于。
3. 过程中发现两处口径不一致（007 的 W34.1 行未回写；S13 认不出散文「无」），按规矩当场登记收件箱 ISS-117 / ISS-118，不打断本场主线。

## 4. 决策与选项对比

### D1 · 新增两条过程约束：提交按任务、重档变更任务先行

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 重档都触发（选定） | 高：复用轻 / 重档白名单一条边界 | 低（一节两条） | 小（AGENTS.md 一处） | 高（revert 即回） | 低（不新增判据体系） | 中（提交信息可见） | 高（grep + git log 可核） | 「为挂任务而凑任务」的形式化 |
| B 仅脚本与可执行内容 | 中：漏掉契约 / 规则 / SKILL 的锚点 | 低 | 小 | 高 | 低 | 中 | 高 | 规则类变更仍无任务锚点 |
| C 仅包内文件 | 中：仓内过程文件不覆盖 | 低 | 小 | 高 | 低 | 低 | 高 | 档案 / 规则变更回溯断链 |
| D 维持现状（不加约束） | 低：提交与任务脱钩 | 零 | 零 | — | 中（靠自觉补锚） | 低 | 低 | 重档变更无锚点发生 |

**结论**：两条约束落进 `AGENTS.md` 新节「Git 提交与任务」；覆盖面＝重档都触发（复用硬规则 12 白名单，不新造第二条口径）。
**是否暂定**：否（撤销条件见下）。
**拍板**：用户
**依据**：「增加git提交约束，要求按任务提交。以及用户提问设计到代码变更时就要哦创建任务并落档。」（本档 §2 #1 逐字；覆盖面经复述门追问定为「重档都触发」）
**复述**：要做什么＝`AGENTS.md` 加「Git 提交与任务」两条（提交信息注明任务编号；重档变更先建任务并落档再动手）；推翻代价＝低（一个文件几行、一条 revert 可回，不动脚本与校验、不触发发版）——用户答「过，按此落」（2026-11-11 复述门）。
**为什么更合理**：对比维持现状（D）：提交与任务脱钩，重档变更可无锚点发生，「按任务提交」无从谈起。对比 B：漏掉契约 / 规则 / SKILL 的任务锚点（实践里它们历来走任务，如 T33.1.x、T34.1.1）。对比 C：把仓内过程文件排除在外。A 复用既有轻 / 重档白名单一条边界，不新增第二套判据，符合「做减法」。
**撤销条件**：连续 2–3 场出现「为挂任务而凑任务」（任务只为提交存在、无实际验收）或补写任务号成为纯形式负担；或硬规则 12 的轻重档白名单本身被推翻（口径失去地基）。
**被否方案**：B 仅脚本与可执行（回到条件：出现规则 / 契约变更因无任务锚点导致回溯断链）；C 仅包内文件（回到条件：仓内过程文件频繁改动且确需逐笔追溯）；D 维持现状（回到条件：两条规则被真机使用证实为纯负担）。
