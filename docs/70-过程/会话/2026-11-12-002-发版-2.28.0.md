## 4. 决策与选项对比

### D1 · 2.28.0 发版的范围

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| **A 出 2.28.0 包、装 6 端，不打 tag / 不发 GitHub Release** | 高：规则 + 模板资产变了，按 minor 升版 | 中：一次打包 + 6 端逐字节核对 | 中：`VERSION` / `CHANGELOG` / `dist/` / 6 端安装目录 | 中：重装 2.27.0 包 + 回退版本号即可 | 低 | 高：端上立刻拿到编辑规则 | 高：`--check-dist` + 逐端「缺 0 / 不等 0」 | 低 |
| B 再打 `v2.28.0` tag 与 GitHub Release | 中：本版没有需要长期回滚的契约变化 | 高：凭据 / 网络 / 资产回核 | 大：对外资产与 digest | 低：发布后不许动 tag | 中 | 中 | 中 | 中：网络短断会留半成品 |
| C 攒到 2–3 笔文档改动再发 | 中：规则早进包早生效，攒着与「尽快」矛盾 | 低 | 小 | 高 | 低 | 低：端上继续用旧版 | 中 | 重复编辑问题继续存在 |
| D 只重打 `dist/`、不升版本 | 低：同名 2.27.0 会含两份不同内容 | 低 | 中：`dist/` 同名覆盖 | 高 | 低 | 中 | 低 | 高：用户与产物对不上 |

**结论**：A（2.28.0：规则升级 + ISS-120 修复入包、装 6 端、不打 tag / Release、不推送）。
**是否暂定**：否。
**拍板**：用户。
**依据**：「因为重复编辑问题反复出现，所以必须尽快安装与发版」（本档 §2 #1 逐字；复述门「强制过」的原因）。
**复述**：强制过——重复编辑问题反复出现，必须尽快安装与发版（用户原因，照抄；要做什么＝发 2.28.0 装 6 端；推翻代价＝重装 2.27.0 包并回退版本号，重发一版）。
**为什么更合理**：规则的价值只在端上兑现——用户明确说重复编辑问题反复出现，A 是唯一让 6 个宿主当天用上 2.28.0 的路径；B 把普通 minor 变成对外资产，网络一断就留半成品；C 与「尽快」相悖；D 会让「2.27.0」这个版本名指向两份内容。
**撤销条件**：若任一宿主装后自测不过或 `brief` / `flow` 行为异常，重装 `dist/` 里 2.27.0 的包并把 `VERSION` 回退，修好后发 2.28.1；若后续要对外发布，另起 tag / Release（须过复述门）。
**被否方案**：B 打 tag / Release（回到条件：用户要对外发布，或出现需要「回到这个版本」的真机问题）；C 攒批（回到条件：规则改动不急、且发版成本成为负担）；D 不升版本（回到条件：只改 docs / README、包内文件没变时）。
