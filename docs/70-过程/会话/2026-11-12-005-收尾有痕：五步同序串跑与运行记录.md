## 3. AI 侧记录

### 3.1 需求理解

用户问的是「执行」——不是规则写没写全，而是该做的动作有没有真做。我把它收敛到收尾这一头：一条命令按收尾口径跑完五步、失败非零、留下可回查的运行记录；并先修掉现成串跑工具与收尾口径相反的缺陷。与用户原话的偏差：其余三项候选（状态一致性机检 / 开场留痕 / 并发检测）本场不做，留在 §4 的被否方案里带回到条件。

### 3.2 实现思路

1. 先修 `observe.py` `cmd_five_run` 的步骤表：与 SKILL 收尾口径同序（`doc_check` 最后），顺序只写在这一处，注释说明理由。
2. 在 `self_test` 第 72 组用**独立期望序列**断言 span 顺序（干净骨架 + 坏档失败两种场景），先红后绿——只断「5/5 都过」证明不了顺序对。
3. `SKILL.md` 收尾块补「一条命令串跑（同序、留记录）」，可观测性段、验收第 42 条、坑列表同步；`AGENTS.md` 收尾条加指针。
4. 本场收尾用 `five-run` 实跑一次，把 `run_id` 写进 §6，作为「收尾有痕」的第一个实例。
5. 第二段 T13.3.2：`devlog check` 读最新一篇 §6，引用的 run id 必须能在 `.dd/observe/runs/` 找到（`S15`，错误）；没写给 `W14` 提醒、不阻断；写「无（分开跑）」表示照旧分开跑，不提醒；只判最新一篇，旧档不追溯。两份档案模板与码表同步。

## 4. 决策与选项对比

### D1 · 本场先做「收尾有痕」还是别的执行缺口

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 收尾有痕（一条同序串跑 + 运行记录） | 高：每场都用，痕迹可查 | 小：1 个脚本 + 1 组断言 + 文档 | 小：收尾口径与自身参考实现 | 高：回退一次提交 | 低：步骤表一处 | 中：收尾更快、有记录 | 高：第 72 组 + 运行记录 | 低 |
| B 状态一致性机检（工作行 / 任务 / 档案互校） | 中：漂移最阴，但发生频率低 | 中：要读多处载体 | 中：校验脚本 | 高 | 中 | 中 | 中 | 中：口径未定易误报 |
| C 少做：先做减法，不加检查 | 中：能降执行成本，但不产生痕迹 | 小 | 小 | 高 | 低 | 低 | 低 | 中：3.10 未到点，删什么没有依据 |

**结论**：选 A（收尾有痕）。
**是否暂定**：否（本场已执行）。
**拍板**：用户。
**依据**：「确认按 收尾有痕走」。
**复述**：可免——上一轮已列明要做什么（一条同序串跑 + 运行记录）与推翻代价（回退本场提交，不改契约 / 接口）；用户指名选择，按实现取舍记。
**为什么更合理**：对比 B，A 每场都用、无痕最常发生，而状态漂移频率低；对比 C，减法降成本但不产生执行痕迹，且 3.10 未到点。A 还正好补上 D13 自身参考实现缺的收尾入口。放弃的是本轮不覆盖状态漂移 / 并发 / 开场留痕。
**撤销条件**：连续 2 场收尾档案没有 `run_id`，或仍出现一次收尾漏跑 / 顺序错 → 说明一条命令不足以改变行为，回到 B / C 重新选。
**被否方案**：B——回到条件：再出现一次跨载体状态漂移（计划行与档案不一致）且没有自动提醒；C——回到条件：规则数量继续增长、且 3.10 扫描发现可删项时。
