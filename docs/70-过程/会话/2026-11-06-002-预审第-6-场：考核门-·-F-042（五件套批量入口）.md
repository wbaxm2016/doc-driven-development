### 3.1 需求理解

「考核门事前预审」按 SKILL 的预审判据理解成：**只回答「这条链的编号在不在、状态对不对、证据指向真东西」**，不回答「考核该不该过」。对象取 F-042（功能行），考核落在任务 T5.9.1，所以扫的是 REQ-031 → F-042 → W5.9 → T5.9.1 → 考核汇总 / 对照行这一条链，而不是「把 2.10.0 通读一遍」。

### 3.2 实现思路

1. **定位**：门 = 考核门（事前），对象 = F-042；考核载体是任务行 T5.9.1。
2. **按链扫**：`requirements` REQ-031（已实现 + 确认）→ `FEATURES` F-042（已验收 + 评审三问 + 考核汇总 + 完成于）→ 计划 §4 W5.9 / §5 T5.9.1（六维 6 个、依赖、证据）→ 任务考核四格 → `功能对照` F-042 行（一致）。
3. **机器复核**把可跑的都跑了：`self_test` 311/311（第 60 组 15 条）、`doc_check` 0 error、`plan check` 0 error、`dist` 包 sha256 前 8 位 `C578A24E` 与 F-042 证据写的 `c578a24e…` 一致、`完成于` 的 `81e159b` 在 git 里。
4. **只报两类**：断链（承诺的东西没有证据）与过期（写出来的数与事实不符）。报不出的不报。
5. **不代判**：§3.8 的裁决列全部留「待裁决」，不写状态、不改台账。

## 4. 决策与选项对比

### D1 · 先补档还是先跑预审

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |

| A 先补档再预审（选中） | 高：事实源先不写假话 | 低 | 小 | 高 | 好 | 中 | 高：`ls-remote` 与 `git show` 可核 | 低（多一轮） |

**结论**：A。先把「推送未完成」这句话改掉，再让预审读一份不说假话的文档。
