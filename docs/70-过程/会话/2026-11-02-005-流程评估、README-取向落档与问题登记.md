### 3.1 需求理解

用户问的不是「README 写得顺不顺」，而是「这套流程在真实项目里成不成立」。所以第一轮没有改字，先做体检：把 11 步逐个对到载体与判据码，再看仓库自己的档案能不能证明它跑得动。

偏差要写明：第一次回答偏成了「文档批评」（重复、密度、编号冲突），用户明确纠正为「流程整体如何」之后，才转到结构层。这个偏差本身有信息量——评估一套流程时，最先看到的往往就是它自身的表述问题。

### 3.2 实现思路

1. 用自举数据当证据，而不是讲方法论：42 场档案 / 25.6 万字、45 任务 44 完成、台账 52 条 39 闭环、考核 44 行四格齐。
2. 找「表格声称有落点、实际没有」的格子：设计卡（全文 54 次提及、0 模板 0 判据）、对照清单（模板不随 `doc_init` 落地）。
3. 把门分成两类：正向门每次收尾都跑；反向判据（撤销条件 / 回到条件 / 走通验收）全无唤醒机制。
4. README 只写读者需要的那一层：载体名、判据有无、拍板点，不搬 `SKILL.md` 的码。

## 4. 决策与选项对比

### D1 · 「闭环优先于覆盖」叫什么、放哪

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 作为「最大特色」，并列功能清单 | 低：特色是别人也能有的功能 | 低 | README 开头 | 容易 | 差：功能会变 | 中 | 低 | 定位被功能清单绑架 |
| B 作为「取向」，讲取舍 + 三个判断 | 高：解释了为什么砍覆盖 | 中 | README 开头 + 承诺 4 收窄 | 容易 | 好 | 高 | 中：三个判断各能指到字段 | 读者以为是「半成品」 |
| C 不写进 README | 低：最有解释力的一条缺席 | 零 | 无 | 容易 | 中 | 低 | — | 每次都要口头解释 |

**结论**：B。「最大特色」这个词不成立——特色可被复制（EARS / ADR / 三层计划别人也有），取舍不可复制（要砍掉覆盖）；且取舍是解释项，不是卖点。同时补一句「那是取舍，不是待补」防误读。
**是否暂定**：否
**拍板**：用户（要求放开头，并接受「取向」而非「最大特色」的措辞）
**依据**：「尤其是「闭环优先于覆盖」是最大的特色吗？如果是需要在 README 开头就重点介绍」
**撤销条件**：出现「开头只讲不做什么、看不出能做什么」的读者反馈时，改成先功能、后取舍的顺序。

### D2 · 原则的唯一定义放哪

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A README 定义 + vision 指路 | 高：一处定义 | 低 | 2 个文件 | 容易 | 好 | 中 | 高：`doc_check` 查链接 | vision 读者要跳转 |
| B 两处都写全 | 低：违反硬规则 1 | 中 | 2 个文件 | 难：改一处忘一处 | 差 | 高 | 低 | 迟早不一致 |
| C vision 定义 + README 指路 | 中：README 开头成了链接 | 低 | 2 个文件 | 容易 | 中 | 低 | 中 | 开头少一句能打动人的话 |

**结论**：A。README 是人的入口，原则的正脸放这里；vision 只留「这几条『不是』出自同一个取舍」+ 链接，并明写「只指路，不复制」。
**是否暂定**：否
**拍板**：用户
**依据**：「后者」
**撤销条件**：出现两处口径不一致，或 vision 的读者必须跳转才能读懂「不是什么」。
