## 4. 决策与选项对比

### D1 · 怎么补这两类计数

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 只补两码 + 一条断言 + 基线说明 | 强：汇总口径与码表同源 | 极低（一行常量） | 小：一个列表 + 一条断言 + 两处说明 | 高：删两码即回退 | 低：`CODES` 仍是一处 | 中：统计与基线恢复正确 | 强：断言先红后绿 | 低：存量基线需重跑一次 |
| B 顺手把 `CODES` 重排成数字序 | 中：可读性更好，但与缺陷无关 | 低 | 中：`--json` 键序全变 | 高 | 低 | 无 | 中 | 中：可能打断按序读输出的脚本 |
| C 只加断言、不改 `CODES` | 弱：断言永远红，等于关掉它 | 零 | 无 | — | 低 | 无 | 无 | 高：假绿或被迫跳过 |
| D 少做：只在收件箱记着 | 弱 | 零 | 无 | — | 低 | 无 | 无 | 低但问题留着 |

**结论**：选 A。
**是否暂定**：否（已落地，断言红 / 绿两态都跑过）。
**拍板**：用户
**依据**：「先做3」
**复述**：采纳式——用户以「先做3」直接选定上一轮列的第 3 项。要做什么：把两类漏算补进统计，并让断言盯住；推翻代价：删 `CODES` 里两个码 + 一条断言，其余（说明文字）可留着。
**为什么更合理**：对比 B（重排是为好看，动到 `--json` 键序，属另一个决定）、C（断言红着不修，等于把检查关掉）、D（问题留在台账里，下一次按统计判断的人继续看不见），A 用一行常量把「统计与码表同源」补回来，且证据两态可复现。
**撤销条件**：若 `--json` 的消费者确实依赖键序、或补列后存量基线大面积误报且无法用重跑基线解决，则改成「`CODES` 排序输出 + 基线按码字典序比对」，或退回只报 text 汇总。
**被否方案**：B（回到条件：下一次动 `--json` 形状或加脚本化消费方时）；C（回到条件：无——这是失败路径）；D（回到条件：用户明确表示统计暂不重要）。
