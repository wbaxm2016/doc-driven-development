## 3. AI 侧记录

### 3.1 需求理解

用户要的不只是文案，而是先证明这个双线真的在实现里；确认后再把 README 写成「特色」，vision 补定义。我的理解：「需求线」= 怎么知道必须成立什么、做到了没有；「方向线」= 需求一多时怎么排先做哪个。

**与用户原话的偏差**：用户说「两条路线」，实现里不是两套模式 / 二选一，而是两条**并行的轴**；README 会写成「并行、不是父子」，不写成「可切换模式」。

### 3.2 实现思路

1. **先读实现**：`requirements.md`（REQ 七列）、`FEATURES.md`（F 十二列）、`开发计划.md`（D/W/T）、`SKILL.md` 主干道、`plan.py`、`doc_check.py`。
2. **核对结论**：需求线 = REQ → F → 入口 / 证据，硬判 `E22` / `E23` / `E24` / `W8` / `E26`；方向线 = D → W → T，硬判 `P12` / `P6` / `P1`–`P13`。两条线独立：W 只挂 D，不挂 REQ。
3. **边界**：`plan.py` 不校验 W / T 的「关联」列；F → REQ 是唯一硬链接。README 明说这是「松耦合」，不假装机器管住了。
4. **写作分工**：README 讲「是什么 / 为什么 / 在哪交汇」（产品语言）；vision 给「载体 + 码 + 边界」（定义权威）；`technical-design` 顺带把过期码段改成「码族 + 码表指针」。
5. **修正一个说法**：不是「两套开发模式」，是「两条并行的轴」；需求少时一条方向就够，需求多了方向线负责串起来。
