## 3. AI 侧记录

### 3.1 需求理解

「不够白话」不是要删术语，而是**术语不该挡在第一屏**：读者先判断值不值得用，再决定学不学它的词。所以目标是重排信息顺序，不是压缩长度。

与用户原话的偏差：用户说「三句内说清」，我按字面做——文件前三句各回答一个问题（痛点 / 是什么 / 怎么试），命令块紧随第三句；没有把三点合成一段。若用户要的是「一段三句」，改起来只是删两个换行。另：用户说「再给一版重写」，我理解为落盘到 `README.md`（否则「改完 `doc_check`」无从验收），但**不提交、不发版**。

### 3.2 实现思路

1. **先用文件本身做诊断**：旧版前 15 行 = 标题 + 一句定位 + 「不是文档规范合集」这张表（`用户侧 8 类 / AI 侧 6 项`、`双向取代链`、`六维 + 多视角`）——读者要先把这张表当词汇表背完，才知道它解决什么。
2. **定分工**：根 README = 产品入口（是什么 / 治什么 / 怎么试 / 怎么装）+ 维护者手册；`docs/README.md` = 仓库内「要改东西先读哪份」的地图。定义权威仍在 `vision.md` / `SKILL.md`；两边只互指，不复制索引。
3. **按读者的决策顺序重排**：值不值得试 → 怎么试 → 怎么维护。旧版把「发版」放在「安装」之前，新版把维护细节整体后移。
4. **事实先核后写**：`self_test.py` 实测 47 秒（写「约 1 分钟」而非「30 秒」）；`doc_init --target .` 在临时目录实测 `errors=0 warnings=0`；`install.py --list` 与 `--only dsh --dry-run` 实测 5 个目标、31 个文件；目录表与 id 按 `install-targets.json` 写全。
5. **只改门面**：README 属包外文件，按 `docs/60-规范` 不发版；`dist/`、`VERSION`、`SKILL.md` 未动；`docs/README.md` 只加一行作用域声明。

## 4. 决策与选项对比

### D1 · 这次改 README 算重档还是轻档

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 重档（选中） | 5 | 2 | 2 | 5 | 4 | 3 | 4 | 1 |
| B 轻档 | 2 | 5 | 1 | 5 | 2 | 3 | 4 | 3 |

**结论**：选 A。用户明确判重档：改的不是措辞，是「读者第一眼看到什么、先回答哪三个问题、两份 README 怎么分工」——属于门面口径；按用户约束走 brief + new + 五连跑。
**是否暂定**：否。
**拍板**：用户。
**依据**：「改 README 属重档（先 devlog brief + new 开档，收尾跑五连跑）」——用户本轮原话。
**撤销条件**：若同类改动经复核只动措辞、不改读者判断路径与两份 README 的分工，可降为轻档；本场涉及首屏与分工，判定不撤。

### D2 · 首屏怎么写

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 三句 + 命令块（选中） | 5 | 5 | 1 | 5 | 5 | 5 | 4 | 1 |
| B 保留「三件带校验的事」表 | 3 | 5 | 1 | 5 | 4 | 2 | 4 | 2 |
| C 三句后再塞术语表 | 2 | 4 | 1 | 5 | 2 | 3 | 3 | 3 |

**结论**：选 A。验收要求三句内说清；结构表放第二屏，读者已知道它是什么之后再看不迟。
**是否暂定**：否。
**拍板**：agent 自选。
**依据**：用户验收「首屏三句内说清……不堆术语」；旧版诊断（前 15 行是词汇表）。
**撤销条件**：若目标读者读完前三句仍说不出「它是什么 / 治什么 / 怎么试」，或「约 1 分钟」与实际差距明显，则重写首屏。

### D3 · 根 README 与 docs/README 怎么分工

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 根=产品入口 + 维护，docs=仓库地图（选中） | 5 | 5 | 1 | 5 | 5 | 3 | 5 | 1 |
| B 两处都放产品介绍 | 3 | 3 | 3 | 3 | 2 | 2 | 3 | 3 |
| C 根 README 只做文档索引 | 1 | 4 | 2 | 4 | 2 | 1 | 3 | 4 |

**结论**：选 A。根 README 回答「值不值得装、怎么装」；docs/README 回答「在这个仓库里改东西先读哪份」。定义仍只有一处（`vision.md` / `SKILL.md`），两边只互指。
**是否暂定**：否。
**拍板**：agent 自选（在用户约束下）。
**依据**：用户「README 只有一份权威，根 README 与 docs/README 分工先讲清再改，别两处同步维护」。
**撤销条件**：若根 README 开始逐篇登记仓库文档，或 `docs/README.md` 出现第二份产品介绍，分工失效，删弱的一份。
