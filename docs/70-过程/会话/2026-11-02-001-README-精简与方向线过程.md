## 3. AI 侧记录

### 3.1 需求理解

README 是产品入口，不是痛点散文，也不是运维手册：读者应先看到「项目目标是什么、值什么、怎么运转」，再看到「结构怎么分层、两条线怎么分」；安装、发版、回滚属于参与开发，交给 `CONTRIBUTING.md`。

需求线与方向线不是两个并行流程，而是同一个开发整体的两个切面：需求线按「必须成立什么」切，方向线按「用户怎么走通」切；10 步流程是双线共用的主干，第 3–5 步分叉（`REQ`/`D`、`F`/`W`、`T`），第 6–10 步共用。任务可以想成一张表的格子：行是功能，列是工作；需求线读行，方向线读列。

第 8 步不是单向的考核门：它是考核回顾 + 回流点——回顾开发流程、发现开放问题、重评实现的可调整 / 可优化 / 可扩展；需要补任务就回到定任务，需要重新设计就回到设计，即使没发现开放问题也可以回去。

设计是工作和任务之间的一步：先写设计卡（接口 / 可替换点 / 扩展点 / 失败边界 / 任务拆分），设计门过了再拆任务。考核回顾发现「实现要可替换」时，回到设计重做，而不是只补任务。

工作流整体成立，但补了六个口子：实施里加冒烟；轻档改动不跑满 11 步；设计卡按改动大小伸缩；回到设计时旧任务标 `搁置` / `撤回`；收尾要更新现状；小改动不必两条线都走。

方向线不是一张静态的 `D → W → T` 树。它是开发者与 Agent 多轮对话的产物：先把现状说清楚，**方向是这一步的结论，不是独立的一步**；再沿方向制定工作，把工作拆成任务，一个任务一个任务推进。之前的 vision 只写了「方向是一条用户能走通的路」，缺了「这条路从哪来」。

### 3.2 实现思路

1. **README 重写**：删掉 AI 开发痛点开头与 5 分钟接入/维护/发版/回滚的长段落；正文改为「项目目标 / 价值 / 使用工作流程 / 结构与分层 / 双线开发 / 快速开始 / 文档地图 / 许可证」。工作流程写成「一次开发怎么走」10 步 + 6 个人工卡点；方向线的概念流程移到「双线开发 · 方向线怎么推进」。
2. **vision / ADR 补过程**：在工作网与方向线两节加「现状（含方向）→ 工作 → 任务 → 推进 → 新的现状」；方向卡加「现状 / 为什么是现在」两个字段。
3. **核对实现**：`brief` 给一屏现状；会话档案记录多轮对话；`plan.py` 校验 `D→W→T`。缺的是「现状」结构化产物、方向卡模板与 `P18`。
4. **安排后续**：F-018（任务双亲与考核下沉）、F-019（方向线的形成过程），对应 W5.6/W5.7 与 T5.6.1/T5.7.1；缺口记 ISS-042/043。

## 4. 决策与选项对比

### D1 · 问题模型与任务模型的三项取舍

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| 候选发 ISS 号 | 中 | 低 | 小 | 高 | 差（噪音） | 低 | 高 | 收件箱被撑爆 |
| 候选留 Q 层（选中） | 高 | 低 | 小 | 高 | 好 | 中 | 高 | 重要候选可能被遗忘 |
| 加第六状态 `持续` | 中 | 中 | 中 | 中 | 中 | 低 | 中 | 与 `确立` 重复 |
| 五状态 + 回到条件（选中） | 高 | 低 | 小 | 高 | 好 | 中 | 高 | 开放问题状态不够显眼 |
| 考核留功能级 | 低 | 低 | 小 | 高 | 中 | 低 | 中 | 功能一大就变总结 |
| 考核下沉到任务（选中） | 高 | 中 | 大 | 中 | 好 | 高 | 高 | 表变宽、迁移量大 |

**结论**：候选留候选层（`Q`，不占 `ISS` 号）；开放问题用五状态 `确立 → 实施中 → 确立` 收口，不加第六状态；考核下沉到任务，功能只留一行汇总。
**是否暂定**：否。
**拍板**：用户。
**依据**：「1. 前者 2. 推荐 3. 确认」（2026-11-02）。
**撤销条件**：候选连续两个季度出现「这条当时想说什么」的返工 ≥ 3 次/季度；或同一开放问题在两次开场里被重复分诊 ≥ 2 次；或连续 5 个任务的考核四格内容重合度 > 80%。

### D2 · README 的叙事与方向线的形成过程

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| 保留痛点叙事，补目标 | 中 | 低 | 小 | 高 | 中 | 中 | 中 | 读者先看到问题，看不到项目是什么 |

| 写成完整运维手册 | 低 | 高 | 大 | 中 | 差 | 低 | 中 | README 失焦 |

**结论**：README 以目标与价值开头，正文只讲工作流程、结构与分层、双线开发；安装/发版/回滚交给 `CONTRIBUTING.md`。方向线写成循环：现状（含方向）→ 工作 → 设计 → 任务 → 推进 → 新的现状。
**是否暂定**：否。
**拍板**：用户。
**依据**：「精简 README……用项目目标与价值描述，实现讲工作流程、结构与分层、双线开发」「开发方向线是开发者通过多轮对话搞清楚现状……一个任务一个任务推进」（2026-11-02）。
**撤销条件**：读者仍把 README 当安装手册（issue/提问集中在安装步骤）；或方向线连续 3 个月没有「现状」记录，只剩静态 `D → W → T` 树。

### D3 · 设计放在哪里

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| 设计放在任务内 | 低 | 低 | 小 | 高 | 中 | 低 | 中 | 功能级可替换性没人负责；任务拆完才发现接口不对 |
| 设计独立成一步（选中） | 高 | 中 | 中 | 高 | 好 | 中 | 高 | 多一份设计卡 |

**结论**：设计独立成一步，卡在工作和任务之间；设计卡含接口 / 可替换点 / 扩展点 / 失败边界 / 任务拆分；考核回顾发现「要可替换」时回到设计，而不是只补任务。
**是否暂定**：否。
**拍板**：用户。
**依据**：「是不是缺了设计，我从考核回顾这里发现了需要保持某个实现需要可替换，应该重新设计这个功能如何实现」（2026-11-02）。
**撤销条件**：连续 5 个设计卡的可替换点都是「无」且后续频繁因替换 / 扩展返工；或设计卡从不影响任务拆分。
