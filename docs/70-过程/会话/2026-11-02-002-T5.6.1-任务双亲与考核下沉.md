## 3. AI 侧记录

### 3.1 需求理解

这一轮不是「再加两条规则」，而是把**任务**变成系统里唯一同时向需求线与方向线交代的节点：向上挂功能、向内挂工作，做完还要自己交代值不值。功能因此从「一个能力 + 一段总结」退成「一行汇总 + 一个入口」，考核的重量移到任务上。

与用户原话的两处偏差，先写在这里：

1. **任务考核四格没有放进计划表**，而是按用户第 3 条放进 FEATURES 的第二张表。代价是 `plan.py` 要跨文件读台账（`P15`）；好处是计划表不再宽到 14 列里再塞四段长文本。这条偏差是用户要求本身，不是我的选择。
2. **`P16` 没有重复判「证据 + 考核汇总 + 完成于」**：那三格分别由 `E24`（证据）与 `E27`（汇总 + 完成于）判，`P16` 只判「汇总有没有来源」——功能至少有一条任务，汇总点名的任务必须真挂在这个功能下。ADR-003 写的是「`P16`：已验收必须有证据 + 考核汇总 + 完成于」，实现上按**判据不重复**切了一刀；模型没变，只是每个码管一件事。

### 3.2 实现思路

**设计卡（3 行，F-020 未落地前的试点；模板还没有，就地写在档案里）**

| 字段 | 内容 |
|---|---|
| 接口 | 三处表头即契约：计划 §5 的 `功能` 列、FEATURES 的 `考核汇总` 列、FEATURES 第二张表 `任务 / 做法 / 一致 / 代价 / 结论 / 完成于`。脚本只按表头取列、不按列序；对外可见的判断只有 `P14`–`P16` 与 `E27` 的报错文本。 |
| 可替换点 | 「任务考核」落在哪张表是唯一可替换点（现在在 FEATURES，也可挪回计划 §5）：只影响 `plan.py` 的取数函数 `load_features()` 与两份模板，`P14–P16` 的判据不依赖落点。判据本身再往下拆是「双亲存在性 / 考核完整性 / 汇总可回溯」三件事，换成别的载体也仍是这三件。 |
| 失败边界 | 台账缺失或表头被改坏时，三个码会**全部沉默**——这是最坏的失败（errors=0 的假通过）。所以：找不到功能台账 → 报一条 `P14` 而不是跳过；表头缺 `功能` 列 → 报 `P14`；任务考核表缺行 → `P15`；汇总里点名的 `T` 不存在或不挂本功能 → `P16`。历史豁免只走「`—（历史）` + 状态已完成」这一条窄门。 |

## 4. 决策与选项对比

### D1 · `P16` 判什么：重复槽位，还是只判来源

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A `P16` 全判（证据 + 汇总 + 完成于 + 任务） | 中 | 低 | 小 | 高 | 差（与 E24/E27 双报） | 低 | 高 | 一处缺格报三次，误以为系统坏了 |
| B `P16` 只判「汇总有来源」（选中） | 高 | 中 | 小 | 高 | 好 | 中 | 高 | 判不了四格写得好不好（本来也判不了） |
| C 不设 `P16`，只靠 `E27` | 低 | 低 | 小 | 高 | 中 | 低 | 中 | 汇总可以点一个不存在的任务而全绿 |

**结论**：选 B。`E24` 判证据、`E27` 判汇总槽位与完成于、`P16` 判「汇总点名的任务真挂在这个功能下」，每个码只管一件事，报错不重复。
**是否暂定**：否。
**拍板**：agent 自选（实现分工，不是模型取舍；模型按 ADR-003 未动）。
**依据**：ADR-003 §2「P16：功能 `已验收` 必须有 `证据` + `考核汇总` + `完成于`；功能没有任务时只能标 `—（历史）`」——三格已各有归属，`P16` 补的是「来源」这一格。
**撤销条件**：出现「`P16` 报的问题其实 `E27` 也报了」的重复报错 ≥ 3 次，或 `P16` 连续 5 个功能从未触发。
