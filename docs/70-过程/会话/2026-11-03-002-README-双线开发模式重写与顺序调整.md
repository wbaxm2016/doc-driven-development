## 3. AI 侧记录

### 3.1 需求理解

用户要的不是「再加一段解释」，而是**让这一节的顺序符合读者的认识顺序**：先看两条线是什么（一张对比表），再看需求线从一句必须成立的话怎么走到回写，再看方向线为什么存在、跟 AI 协作时强在哪、它是不是自然的开发方式、方向定下来之后怎么走。

三处与字面的偏差，显式写出：

1. **「双线开发模式」是这一节的正式名称**，不是引入一个新概念。正文仍用「需求线 / 方向线」，与 vision、SKILL 的用词保持一致。
2. **「它是不是一种很自然的开发方式」我答「是，但不自动」**，而不是并列两种观点：开发本来就有「现状 → 下一步 → 回头看」的循环，方向线只是把它写成可核对的东西；但 AI 不主动做这一步时会滑向 prompt 堆叠，所以「自然」不构成「可以不做」。
3. **「从需求出发的开发过程」我按 `REQ → F → T → 对照 → 考核 → 回写` 写**，而不是把上一节 11 步表抄一遍；重复的部分只保留这条线自己的性格（刹车：只回答做到了没有）。

### 3.2 实现思路

1. **先搬块再改字**：第一刀只移动「双线开发」整块到「工作流程」之后、`## 结构与分层` 之前，`git diff` 确认是纯搬运（30 行删 + 30 行增），避免搬运与改字混在一次 diff 里。
2. **改名 + 重写**：标题改 `## 双线开发模式`；新增 `### 需求线：从一句必须成立的话出发`（四步：`REQ` / `F` / `T` / 做完再说完成）与 `### 方向线：先找到方向，再走通`（四个 `####`：为什么需要 / 跟 AI 协作时它的优势 / 这是一种自然的开发方式 / 方向确定之后）。
3. **事实逐条对齐权威**：需求线四步取自 `SKILL.md` 主干道第 1–2 格与对齐门 / 评审门；方向线四层取自 `vision.md` §工作网与「方向线：节点与边」（接缝、集成 bug、AI 四条弱点、方向卡九字段）；「方向是现状的结论」取自 vision 与 ADR-003 §3。
4. **补回合流**：把原节的合流图、任务双亲、`W` 挂 `D` 不挂 `REQ`、小改动可只走一条线，收成 `### 两条线在哪里合流`，放在方向线之后。
5. **顺手修引用**：README 第 47 行原写「区别见「双线开发」」，标题改名后同步成「双线开发模式」。
6. **自查**：README 不在 `doc_check` 的校验范围，只能人工查——标题层级 1→4 连续、代码块 4 对全部闭合、`doc_check` 确认 docs 侧无回归。

## 4. 决策与选项对比

### D1 · 双线这一节怎么写

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 保留原结构，只补一段需求线 | 中 | 低 | 小 | 高 | 中 | 低 | 中 | 读者仍要自己拼「为什么需要方向线」；需求线只有一句 `REQ → F → T` |
| B 按用户给的顺序重写：对比表 → 需求线过程 → 方向线四问 → 合流（选中） | 高 | 中 | 中 | 高 | 好 | 高 | 中 | 与「工作流程」11 步有部分重叠；篇幅变长 |
| C 拆成「需求线」「方向线」两个平级 `##` 节 | 中 | 中 | 大 | 中 | 中 | 中 | 中 | 读者先读到两条线各自的过程，才在末尾知道它们是一件事；与「双线是同一开发整体的两个切面」相冲突 |

**结论**：选 B。双线是一件事，先给对比表建立「两条线」的认知，再分别讲过程；方向线按「为什么 → AI 优势 → 是否自然 → 方向定了怎么走」推进，正好回答「它凭什么存在」。
**是否暂定**：否。
**拍板**：用户（顺序与四个要点由用户直接给出）。
**依据**：「README内容排序调整……工作流程：一次开发怎么走之后应该放双线开发模式」「改成双线开发模式……开发方向线先说明为什么需要方向线以及跟ai协作时它的优势，它是不是一种很自然的开发方式，在开发方向确定后」。
**撤销条件**：读者反馈 README 太长、双线与「工作流程」重复难读，或改完后仍有人把方向线当优先级工具（问「那先做哪个」）——则压回两段，把过程细节指回 vision 与 SKILL。
