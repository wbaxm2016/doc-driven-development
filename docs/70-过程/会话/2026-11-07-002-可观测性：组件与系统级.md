## 3. AI 侧记录

### 3.1 需求理解

用户要的不是「多打日志」，是两层的**可回看窗口**：

- **单组件层**：开发某个组件（脚本 / 子命令 / 门）时，就把它「怎么工作」变成可观测的——输入是什么、按哪条规则得出结果、读了哪一版数据、失败落在哪。
- **系统层**：把组件串起来（五连跑、建档→记录→校验→回写、发版→装机、门链）时，能看见「上一步的输出怎么成了下一步的输入、哪一步断了、整体能不能交付」。
- **与用户原话的偏差（要显式核）**：用户说的「窗口」我理解成**查询面**（CLI 命令 / 只读汇总 / 档案引用），不是 GUI 或监控平台。若用户要的是一个可视化页面，定义要改——这是本轮请用户核的第一点。

一句话定义（提案）：观测性 = 组件或组件链运行时，主动留下足以**事后回答**的结构化事实——这次跑的是什么、为什么是这个结果、预期是什么样的、系统下一步是什么——让不在场的人（用户 / 下一个会话的 agent / CI）不必重跑、不必读源码、不必问当时的人。

**对齐门修正（2026-11-07，用户复述）**：用户把「读的是哪一版」换成了「预期是什么样的」——这是语义修正，不是措辞调整：观测记录必须把**预期与实际并排**，否则只能看到「发生了什么」，看不到「差在哪」。版本 / hash 仍进记录（算「运行的是什么」与证据的一部分），但不再占四问之一。

**四维框架（用户 2026-11-07 补）**：可观测 / 可解释 / 可诊断 / 可改进。**四问是记录内容，四维是验收框架**——同一条记录要同时支撑四维：可观测（跑了吗、跑的是什么）、可解释（为什么是这个结果）、可诊断（问题在哪、下一步做什么）、可改进（同类问题是否复发、规则 / 流程怎么改）。前三维单次记录就能答；**可改进**要跨 run 聚合，v0 只保证可聚合（稳定 `finding.key` + `tool_version`），聚合视图另议。

**作用域（用户 2026-11-07 纠正）**：以「使用本技能的项目」为主，本技能自身为参考实现（dogfood）。技能能强制的是**设计与文档**（项目模板 / 设计卡四格 / `W` 检查），不能替项目跑运行时；项目侧运行时按模板自行实现。现有 REQ-032/033 是自身口径，先保留为参考实现，待项目侧载体定了再改写或新增。

**项目侧载体（用户 2026-11-07「按」）**：选 A——`doc_init` 铺观测地图（`40-运行/可观测性.md`，基础 5 层即建）+ 设计卡「观测四格」+ `doc_check` 缺格 `W12`（不阻断、存量不追溯）+ `SKILL.md` 一节；项目运行时按模板自行实现。落 REQ-034 / REQ-035、K28、W26.2；自身 K27/v0 留作参考实现。
