## 4. 决策与选项对比

### D1 · 需求生命周期采用 A（状态机 + 最小校验）并本场落档

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 状态机 + 最小校验（选中） | 高：补的是改 / 删两处没写死的迁移 | 低：一处规则 + 两条校验 | 小：SKILL、delta 规则、doc_check | 高：改回一处即可 | 低：无新数据形态 | 中：生命周期可读可见 | 高：两条均有正反例 | 改句即需重确认，措辞级改动也红 |
| B 需求版本化 | 中：与 delta 职责重叠 | 高：契约表改形态、存量回填 | 大：契约 + 模板 + 全部校验 | 低：回填后难退 | 高：两份变更史 | 中 | 中 | 两份事实 |
| C 需求-功能-任务-证据依赖图 | 高：直接答「上层同步」 | 高：新视图 + 新数据边 | 大：新命令与数据关系 | 中 | 高 | 高 | 高 | 过重，先于真实痛点 |
| D 少做（只统一口径） | 低：改 / 删的缝留着 | 零 | 零 | — | 低 | 低 | 低 | 缝留着，下次还会遇到 |

**结论**：按 A 落档并本场执行：REQ 只保留四个状态（待实现 / 已实现 / 阻塞 / 搁置），删除一律走归档删除（去掉「作废」状态）；`doc_check` 的 E22 白名单去「作废」、E20 补「MODIFIED 后仍标已实现时确认列不得与 before 相同」；SKILL「推翻与回滚」扩成「需求生命周期」，`_delta` README 补 MODIFIED 改句规则。
**是否暂定**：否。
**拍板**：用户（承接 002 §4 D1「按建议」；本场指令确认执行）。
**依据**：「1. 改句后旧确认不得沿用 2. 删除直走归档删除」
**复述**：第二轮通过（逐字见 §2 #2）；第一轮漏「两条校验具体是什么」，已换讲法加例子重问。
**为什么更合理**：补规则比加数据形态便宜；B 与 delta 的变更史重复，C 要等改 / 删变频繁才值，D 会让同一个缝再出现一次。
**撤销条件**：真实会话里同一需求被改 / 删 ≥2 次且出现漏改上层 → 升级 C；真正需要单条需求的历史版本视图且 delta 不够用 → 改 B；改 / 删极低频且愿意接受报错兜底 → 退 D。
**被否方案**：B（回到条件：需要历史版本视图且 delta 不够用）；C（回到条件：改 / 删高频且漏改上层 ≥2 次）；D（回到条件：改 / 删极低频、接受报错兜底）。
