## 1. 本次范围

- **要解决什么**：审批策略已从「逐条询问」改成「从不询问」，而 README 与 vision 仍只写「人拍板、Agent 执行」，读者会以为人还逐个动作点「批准」。本轮把这件事写成门面层的**协作事实**：Agent 的读写、执行、校验不必逐条请示；人的判断集中在五道门的语义判断与开放问题收口 / 发版回滚两处不可逆动作上；不逐条问的兜底是 git 与证据，不是审批弹窗。

## 3. AI 侧记录

### 3.1 需求理解

我把它理解成：把「审批策略不再逐条问」落成**协作事实**，不是写一份宿主设置说明。偏差有两处：

1. 我起初把「最新的变化」读成「最近几版实现变化（2.10–2.12）」，先问了一次范围；用户确认是审批策略这一条。
2. 我起初想在 README 里写「怎么把设置改成从不询问」，后来改成写「为什么不需要逐条批」——设置手册会随宿主版本漂移，协作事实不会。

### 3.2 实现思路

1. 同一件事实只有两个落点：README「一次开发怎么走」的分工段**详写**，vision「工作方法」第 2 条**定位一句**；不复制成两段长文。
2. README「它不保证什么」补一条 caveat：不逐条请示的代价是 Agent 可能跑错命令、改错文件，兜底是 git 与证据（可 `revert` / `verify` 可重跑 / 提交只 `add` 自己的路径）。
3. vision「不是什么」加一条边界「不是审批流」，避免读者把它读成一套审批流程。
4. 改完跑 `doc_check`、`devlog check`、`devlog index`、`plan check`、`plan index`。

## 4. 决策与选项对比

### D1 · 本轮改什么

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 只改 README | 4 | 5 | 5 | 5 | 3 | 3 | 5 | 3 |
| B README + vision 都改 | 5 | 4 | 4 | 5 | 4 | 5 | 5 | 3 |
| C 写进 SKILL.md（包内文件） | 4 | 2 | 2 | 3 | 2 | 4 | 4 | 4 |

**结论**：B。两份门面都要读到这件事；SKILL 是给 Agent 的规则，不是读者门面，写进去还要发版装 5 端，代价与收益不成比例。
**是否暂定**：否
**拍板**：用户
**依据**：「更新下README以及vision根据最新的变化」「审批策略 = 不逐条问（推荐）」
**复述**：可免——本轮只改两份门面文案，反悔是一次 `git revert`；用户已点名 README 与 vision 两处。
**撤销条件**：若某宿主上审批策略强制逐条询问、README 里「不必逐条请示」被证伪，或用户要求改回旧口径，就删掉这段。

### D2 · 落在哪、怎么写

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A README 详写 + vision 定位一句 + 「不保证」补 caveat | 5 | 4 | 4 | 5 | 5 | 4 | 5 | 2 |
| B 只写 README 一段 | 3 | 5 | 5 | 5 | 3 | 3 | 4 | 3 |
| C README / vision / SKILL 三处同写 | 3 | 2 | 2 | 3 | 2 | 4 | 4 | 4 |

**结论**：A。事实详写一处（README 分工段），vision 只留定位句与边界；兜底写进「它不保证什么」，否则读者会把「不逐条问」读成「没人管」。
**是否暂定**：否
**拍板**：agent 自选
**依据**：README 的「一处定义」——同一件事只详写一处，vision 与 README 现有的分工就是这么排的。
**复述**：—
**撤销条件**：若后续两处口径分叉（同一句出现两种说法），回到「一处定义」删弱的那份。
