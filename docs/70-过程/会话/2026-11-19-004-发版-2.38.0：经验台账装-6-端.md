### 3.1 需求理解

把它理解成执行类指令，不是新需求：2.38.0 的内容（经验台账）上一场已落地并提交，本场只做「改版本与变更记录 → 打包 → 验包 → 装 6 端 → 记录」。与用户原话的偏差：用户写的是 `build` / `check-dist` / `install` 三条命令，本场用 `release.py --jobs 1` 串起同序三步——`release.py` 只编排、判据仍在 `build.py` / `install.py`，不改任何验收口径。

### 3.2 实现思路

1. 起手核对：`git log --oneline -3`（HEAD `c4a551b`，与 brief 的上一场锚点一致）、`git status` 干净 → 无并发写者，开工。
2. 开档（本档），写 §1：档位、用途、可写范围、目标、不做什么。
3. 改 `VERSION` 为 2.38.0，`CHANGELOG.md` 加 `## 2.38.0`（经验台账：载体 / 模板 / E33 / 第 76 组 / 硬规则 18），一起提交 `a7d3e5a`——顺序必须是「先提交、后打包」（`release.py` 预检会拒未提交的包内改动，`VERSION` 正是包内文件）。
4. `release.py --dry-run` 认一遍版本 / CHANGELOG 段 / 6 端，再 `release.py --jobs 1` 真跑：按 EXP-001 串行跑「源目录自测」与「打包 + 解包后自测」，不并行。
5. 验收：每端「缺 0 / 不等 0」、`dist` 与 HEAD 逐字节、`install.py --list` 逐端 v2.38.0；提交 `dist/`（`93ebc72`）。
6. 记 RV-007 第一条：本场查台账、按 EXP-001 照做，并新增 EXP-006（发版验收看逐端版本）。
7. 收尾：五连跑 5/5 → 本档 §2–§7 一次写成 → 补 `run_id`。

**否决的做法**：按 `release.py` 默认 `--jobs 2` 并行（EXP-001 已记：打包会改写源文件行尾，与被测文件并行会互相踩）；只信退出码不看逐端版本（补 EXP-006 的理由）。
