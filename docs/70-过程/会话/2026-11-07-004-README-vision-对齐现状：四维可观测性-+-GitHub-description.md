## 3. AI 侧记录

### 3.1 需求理解

「按当前项目现状改」不是补版本号（README 本来就不写版本），而是补**能力变化**：2.13.0 之后只有一件事改变了产品面貌——四维可观测性（组件级 + 系统级、四问、观测地图 / 设计卡四格 / `W12`、`observe run` / `five-run` / `show` / `status` / `trend`）。两份门面都停在这次变化之前。

偏差一处：起初把「现状」理解成「最近几版发版记录」，先读了 git log 与 CHANGELOG；后来收窄到「读者读门面时缺什么」——版本记录在 CHANGELOG，门面缺的是能力与边界。另外，GitHub description 只能产出文本：本机没有 `gh` CLI（`gh: 术语 ... 不会被识别`），不能代填到仓库设置。

### 3.2 实现思路

1. 先跑 `devlog brief` + 读 2026-11-07-002 / 003 两篇档案，确定 2.13.0 之后真正新增的能力面，再动笔。
2. 一处定义：README 详写「看得见：组件级与系统级可观测性」一节（两层、四问、四维、三样载体、命令），vision 只在运行层加「旁路：观测层」定位与边界，不复制长表。
3. 顺手核对 README 已有的可验证承诺，而不是只追加新段：五连跑顺序与 `SKILL.md`「日常三动作」一致；门码（`E23` / `E24` / `E27` / `W9` / `W10` / `W12` / `P15` / `P18` / `P19`）在脚本里都存在；`self_test` 实测 94.2 秒、339/339，原文「约 1 分钟」改「约 1–2 分钟」；临时目录跑 `doc_init` → 15 篇、`errors=0`，快速开始成立。

## 4. 决策与选项对比

### D1 · 本轮改到什么程度

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 只在 README 追加可观测性一节 | 4 | 5 | 5 | 5 | 3 | 4 | 4 | 3 |
| B 两份门面补可观测性 + 顺带核对既有承诺（选中） | 5 | 4 | 4 | 5 | 5 | 5 | 5 | 2 |
| C 重写 README 叙事骨架 | 3 | 2 | 2 | 3 | 3 | 3 | 3 | 4 |

**结论**：B。用户点名 README 与 vision 两份；同时「按现状」意味着既有承诺也要核对，不能只追加新段。重写骨架没有证据支持，风险高于收益。
**是否暂定**：否
**拍板**：用户
**依据**：「根据当前项目现状修改README跟vision，还有顺带生成github description。」
**复述**：可免——两份门面文案，反悔是一次 `git revert`；用户已点名两处文档。
**撤销条件**：若用户要求只改一处，或门面需要按新的叙事骨架重排，回到本决策重定。

### D2 · 可观测性在两份门面里怎么落

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |

| A README 详写一节 + vision 运行层定位一节（选中） | 5 | 4 | 4 | 5 | 5 | 5 | 4 | 2 |
| B 只写 README | 3 | 5 | 5 | 5 | 3 | 3 | 4 | 3 |
| C README / vision / SKILL 三处同写 | 3 | 2 | 2 | 3 | 2 | 4 | 4 | 4 |

**结论**：A。读者门面详写一处（README「看得见」），vision 只回答「这层在体系里的位置与边界」；`SKILL.md` 已有可观测性一节，不再复制。
**是否暂定**：否
**拍板**：agent 自选
**依据**：README 的「一处定义」——同一件事只详写一处；vision 现有分工就是定位 + 边界。
**复述**：—
**撤销条件**：若两处口径分叉（同一事实出现两种说法），回到「一处定义」删弱的那份。
