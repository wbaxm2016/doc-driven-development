## 3. AI 侧记录

### 3.1 需求理解

用户问的是两件事：① 后来推翻 / 修改需求、用户要求删代码时，技能有没有「文档更新」的规定动作；② 比代码更高一层的文档（需求 / 功能 / 计划 / 方向）会不会随代码变动同步。这不是要立即加功能，而是在核现有技能在「推翻 / 删除」方向上是否闭环。我按「规定动作 → 机器兜底 → 边界」三层答，并把查到的 1 处口径冲突登记。同场用户随后要求**设计需求的生命周期**（§2 #3）；先摆选项空间（状态机 / 版本化 / 依赖图 / 少做），用户「按建议」选定 A，复述两轮过门；落档交实施会话（新会话提示词见本场回复）。

### 3.2 实现思路

1. **先读规定动作**：`SKILL.md`「推翻与回滚」写明——需求作废走 `_delta` 的 `REMOVED`（编号作废不复用、`_archive/` 留档）；功能撤回把状态改成「撤回」并在「考核」里写理由；回滚用 `完成于` 的 commit；并规定**先改文档再改代码**。
2. **再查机器兜底**：E22（状态词白名单）、E24（已对照 / 已验收功能的代码入口必须存在；删除后引用不存在的需求会报）、E27（撤回仍要考核汇总）。
3. **上层同步**：状态只被证据推进；需求落位（设计卡）三条查的时机；任务考核 / 功能汇总 / 方向卡覆盖靠收尾回写与人读——没有「代码一删、上游自动改」的传播。
4. **顺带发现**：E22 允许「作废」状态词，但 `verify.py` 的 `SKIP_STATES` 不含「作废」——标了作废的需求行仍会被 verify 真跑，与 `doc_check.py` 注释「与 verify.py 的跳过集合对齐」矛盾；已转 ISS-133（可关闭，随 W5.6 删除「作废」状态关闭）。
5. **需求生命周期设计**：先摆四个结构不同的方向——A 状态机 + 最小校验（规则层，补「改句后确认失效」「作废 / REMOVED 二选一」两条检查）、B 需求版本化（数据形态）、C 需求-功能-任务-证据依赖图（结构 / 工具）、D 少做（只统一口径）；推荐 A（先顺既有骨架、补规则比加数据形态便宜），C 留作改/删变了痛感后的升级路径，B 被否（delta 已是变更史）。用户「按建议」选定 A，进入深化：状态与迁移表 + 两条校验 + 落档链（ADR-008 / SKILL 小节 / delta 规则 / REQ-065/066 / F-073 / W5.6 / K55）；复述两轮通过，落档交新会话。

## 4. 决策与选项对比

### D1 · 需求生命周期采用 A（状态机 + 最小校验）

| 选项 | 语义正确性 | 实现成本 | 改动半径 | 可逆性 | 长期维护 | 用户可感知 | 可验证性 | 风险 |
|---|---|---|---|---|---|---|---|---|
| A 状态机 + 最小校验（选中） | 高：补的是改 / 删两处没写死的迁移 | 低：一处规则 + 两条校验 | 小：SKILL、delta 规则、doc_check | 高：改回一处即可 | 低：无新数据形态 | 中：生命周期可读可见 | 高：两条均有正反例 | 改句即需重确认，措辞级改动也红 |
| B 需求版本化 | 中：与 delta 职责重叠 | 高：契约表改形态、存量回填 | 大：契约 + 模板 + 全部校验 | 低：回填后难退 | 高：两份变更史 | 中 | 中 | 两份事实 |
| C 需求-功能-任务-证据依赖图 | 高：直接答「上层同步」 | 高：新视图 + 新数据边 | 大：新命令与数据关系 | 中 | 高 | 高 | 高 | 过重，先于真实痛点 |
| D 少做（只统一口径） | 低：改 / 删的缝留着 | 零 | 零 | — | 低 | 低 | 低 | 缝留着，下次还会遇到 |

**结论**：选 A——REQ 保留四个状态（待实现 / 已实现 / 阻塞 / 搁置），删除一律走归档删除（去掉「作废」状态）；补两条校验：改句后旧确认不得沿用、删除只留归档删除一条路。设计详情见本场回复。
**是否暂定**：否（方向已定；落档细节待实施会话补）。
**拍板**：用户。
**依据**：「按建议」——用户对上一条回复里推荐 A 的确认。
**复述**：**通过（第二轮）**——用户自述：「1. 改句后旧确认不得沿用 2. 删除直走归档删除」（逐字）；两条校验与代价均已复述。
**为什么更合理**：先顺既有骨架，补规则比加数据形态便宜；B 与 delta 的变更史重复，C 的依赖图要等改 / 删变频繁才值，D 会让同一个缝再出现一次。
**撤销条件**：真实会话里同一需求被改 / 删 ≥2 次且出现漏改上层 → 升级 C；真正需要单条需求的历史版本视图且 delta 不够用 → 改 B；改 / 删极低频且愿意接受报错兜底 → 退 D。
**被否方案**：B（回到条件：需要历史版本视图且 delta 不够用）；C（回到条件：改 / 删高频且漏改上层 ≥2 次）；D（回到条件：改 / 删极低频、接受报错兜底）。
