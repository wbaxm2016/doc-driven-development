# ADR-008 · 需求生命周期：四状态 + 改 / 删两条校验

> 一文件一决策。命名 `ADR-<三位编号>-<短标题>.md`；编号只增不复用。
> **双向链**：本决策取代别人，写在 `supersedes`；被别人取代，写在 `superseded_by`。

## 状态

active（2026-11-16 起）。用户 2026-11-16「按建议」选 A（2026-11-16-002 档 §4 D1）；复述第二轮通过「1. 改句后旧确认不得沿用 2. 删除直走归档删除」；落档与验收见 2026-11-16-003 档 §4 D1、REQ-065 / REQ-066、W38.1 / T38.1.1–T38.1.2 / K55。

## 背景

1. **需求有「生」与「推翻」，缺「改」与「删」。** 状态推进（待实现 → 已实现）有 `确认` / 依据 / `verify` 管；功能有「撤回」与「完成于」回滚锚点。但一条**已实现**的需求被改句后，旧确认照抄仍算合法——用户确认的是旧句子，新句子没人确认过。
2. **删除有两条路。** `_delta` 的 `REMOVED` 是一条；「作废」状态词是另一条，且 `E22` 白名单允许它而 `verify.py` 的 `SKIP_STATES` 不含它——标「作废」的需求仍会被 verify 真跑，与 `doc_check` 注释「与 verify.py 的跳过集合对齐」矛盾（ISS-133）。
3. **两处缝都不报错。** 只能靠人读；一改一删就悄悄绕过对齐门与删除留档。

## 决策

1. **需求状态只保留四个**：`待实现` / `已实现` / `阻塞` / `搁置`。**删除不是第五个状态**，不得用「作废」状态词代替。
2. **改句（MODIFIED）后旧确认不得沿用**：`after` 仍标 `已实现` 时，`确认` 必须与 `before` 不同（新日期 / 新落点），沿用即由 `E20` 报出（REQ-065）。机器只判「确认列变了」，**判不了**新确认是否真由用户给出——那是对齐门的人读范围。
3. **删除只走归档删除（REMOVED）**：`before` 恰好匹配一次 → 删行；同一次提交把 delta 移入 `_archive/`、`status: snapshot`；编号作废不复用（REQ-066）。`E22` 白名单去掉「作废」，与 `verify.py` 的跳过集合对齐。
4. **功能撤回与回滚保持原规则**：功能撤回把状态改成 `撤回` 并在「考核」里写理由；回滚用 `完成于` 的 commit，先改文档再改代码。

- `doc_check.py`：`REQ_STATES` 去「作废」；`check_delta` 对 MODIFIED 补「沿用旧确认 → E20」；`self_test` 第 31 组 +6 条断言（433→439）。
- `SKILL.md`「推翻与回滚」扩成「需求生命周期」（改 / 删 / 推翻 / 回滚四段）；`docs/20-契约/_delta/README.md` §5 补改句规则与删除唯一路；`references/check-rules.md` 的 E20 / E22 行同步。
- 存量项目：标「作废」的需求行会转 `E22` 报错，须改走 `REMOVED`；根目录还在改句沿用旧确认的 delta 会红（已归档的不追溯）。

## 撤销条件

- 同一需求被改 / 删 ≥2 次且出现漏改上层 → 升级 C（依赖图）；
- 真正需要单条需求的历史版本视图且 delta 不够用 → 改 B；
- 改 / 删极低频且愿意接受报错兜底 → 退 D。
