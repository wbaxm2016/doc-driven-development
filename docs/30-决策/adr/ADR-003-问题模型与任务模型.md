# ADR-003 · 问题模型与任务模型：四维问题、双亲任务、方向走通

> 一文件一决策。命名 `ADR-<三位编号>-<短标题>.md`；编号只增不复用。
> **双向链**：本决策取代别人，写在 `supersedes`；被别人取代，写在 `superseded_by`。
> 两条链都会被 `doc_check.py` 的 E15 校验：指向的 ADR 必须存在，且取代链必须终止在一个活决策上。

## 状态

active（2026-11-02 起）。决策来自 README / vision 重写时的核对，以及用户 2026-11-02 对三项设计的选择：候选留在候选层、开放问题用五状态收口、考核下沉到任务。

## 背景

四个事实把旧模型卡住了：

1. **问题只有状态，没有命运。** 收件箱的状态是 `open` / `deferred` / `done`，类型是自由文本；`deferred` 必须有「回到条件」（`D2`），但任何 `open` 都能直接 `done`。vision 写「开放问题永不关闭」，代码里没有对应判据——这是本仓库唯一一处「文档承诺了、代码没做」的硬缺口。
2. **任务挂不上功能。** 计划 §5 的任务只有 `所属`（工作），没有 `功能`；「任务是将功能划分一到多个任务」在数据里无法表达。需求线到功能就断了，任务无法向上指回功能。
3. **考核在功能级，颗粒度太粗。** 功能可以很大，一条「考核」四格写的是整块能力的总结；任务才是「可实施、可验证、可考核」的最小单元，却没有考核字段。
4. **方向线容易被写成功能清单。** 现在方向只有「成功状态 + 依据」，没有路径、接缝、走通验收；读者会把「方向」理解成「一组功能」，而不是「用户能走通的一条路」。

## 决策

### 1. 问题按四维管理：层 / 状态 / 性质 / 类型

四个维度正交，一行 ISS 同时具备：

| 维度 | 回答什么 | 取值 | 谁定 |
|---|---|---|---|
| **层** | 承诺到哪一步 | 候选层（`Q`）/ 台账层（`ISS`）/ 约束层（`REQ` / `ADR` / `D-W-T`） | 分诊 |
| **状态** | 处理到哪一步 | 候选 / 确立 / 实施中 / 实现关闭 / 拒绝 | 证据推进 |
| **性质** | 能不能关 | 可关闭 / 开放 | 分诊时定 |
| **类型** | 是什么活 | 缺陷 / 缺口 / 债 / 冲突 / 风险 / 机会 / 待决 | 分诊时定 |

**层是承诺级别，状态是处理进度。** 候选在候选层，不占 `ISS` 号；分诊通过才进台账，状态从「确立」开始。这样既保留五段生命周期，又不会让每个一闪而过的念头都占一个编号。

**性质决定关闭方式**：

- **可关闭**：有完成判据；走 `确立 → 实施中 → 实现关闭`，进「已闭环」，写结论、证据、闭环日、完成于。
- **开放**：没有「做完」，只有「这一轮做到哪 + 什么信号回来」；走 `确立 → 实施中 → 确立`，每轮收口带回新的「本轮边界」和「回到条件」。`实现关闭` 只对可关闭开放。

**每个状态都要有依据**：

| 状态 | 依据写什么 | 机器判 |
|---|---|---|
| 候选 | 来源、一句话、影响初判、作废条件 | 有来源、有作废条件 |
| 确立 | 类型 / 性质 / 影响 / 落点 / 验收判据或回到条件 | 字段齐、枚举合法、落点存在 |
| 实施中 | 关联任务、当前进度（做到哪 / 卡在哪）、开始日 | `T`/`W` 存在、进度非空、未 stale |
| 实现关闭 | 结论、证据（commit / verify / 测试）、闭环日、完成于 | 证据非空、commit 格式、日期合法 |
| 拒绝 | 理由、决策人、拒绝日、重新考虑条件 | 四项齐全 |

**类型按完成判据分，不按严重程度分**：

| 类型 | 是什么 | 完成判据 |
|---|---|---|
| 缺陷 | 现在就是错的 | 复现用例通过 + 回归 |
| 缺口 | 该有但没有 | 需求落地 + `verify` |
| 债 | 能用，但让下一次改动更贵（代码 / 文档 / 测试） | 结构改善 + 回归通过 |
| 冲突 | 两处定义或口径互相打架 | 一处胜出，另一处删除或降级 |
| 风险 | 还没发生，但可能出事 | 缓解措施 + 监控信号 |
| 机会 | 不做也不错，做了更好 | 探索结论（做 / 不做 / 条件） |
| 待决 | 不拍板就无法推进 | 决策记录（拍板 / 依据 / 撤销条件） |

**兼容旧值**：`open` → `确立`，`deferred` → `确立`（保留回到条件），`done` → `实现关闭`。读旧值时给 WARN，不阻断；下一轮编辑时迁移。这样不把一次模型升级变成全仓红。

### 2. 任务双亲：同时挂功能与工作，是三类动作的最小单元

需求线与方向线不是两个并行流程，而是同一个开发整体的两个切面：需求线按「必须成立什么」切，方向线按「用户怎么走通」切；它们在任务上合流。

```
REQ ──► F ──► T
              ▲
D ──► W ──────┘
```

- **每个新任务有且只有一个 `功能`（`F`）和一个 `所属工作`（`W`）**；两者都必须存在。
- 一个功能拆 1..n 个任务；一个工作含 1..n 个任务。
- 一个功能的多个任务可以跨多个工作；一个工作也可以含多个功能的任务——工作常常不是新功能，而是功能之间的接缝。
- 历史任务允许 `功能` 写 `—（历史）`，只对存量；新任务不给这个口子。

**任务是最小单元，判据三条**：

| 判据 | 要求 | 不满足怎么办 |
|---|---|---|
| 可实施 | 一场会话内能完成；改动边界清楚（文件 / 组件）；没有「顺便」 | 拆成两个任务，或升级为工作 |
| 可验证 | 一条命令 / 测试能判真假；失败时指得出哪一步 | 补验收，或降为工作 |
| 可考核 | 四格「做法 / 一致 / 代价 / 结论」写得满；一个人不看全过程也能复述值不值 | 合并、重写，或承认它只是个动作 |

**考核下沉**：

- 任务行：`验收`（一条命令）+ `考核`（四格）+ `完成于`（commit）。
- 功能行：`证据`（任务号 + 命令输出）+ `考核汇总`（一行：各任务考核见 T…；整体一致 / 代价 / 结论）+ `完成于`（最后一个任务的 commit）。
- 历史功能保留原「考核」四格，标 `—（历史）`，不追溯。

**考核回顾有三个出口**：不需要补任务 → 测试 / 回写；需要补任务 → 回到「定任务」；发现实现需要重新设计（比如某个实现要可替换）→ 回到「设计」。开放问题不自动变成任务，只有要求改实现的那部分才变成任务；即使没发现开放问题，只要回顾认为设计还要改，也可以回到设计。

**机器判**：

- `P14`：新任务的 `功能` 必须是存在的 `F-nnn`。
- `P15`：任务 `已完成` 必须有 `验收` + 考核四格 + `完成于`。
- `P16`：功能 `已验收` 必须有 `证据` + `考核汇总` + `完成于`；功能没有任务时只能标 `—（历史）`。
- `E27` 从「功能考核四格」改为「功能考核汇总 + 完成于」。

### 3. 方向线：以走通验收，不以功能清单定义

**功能是节点，方向是边。** 需求线建节点，方向线建边。只建节点，系统是一堆功能；只建边，系统是一条没有内容的空路。

**方向不是一开始就有的**：它来自开发者与 Agent 的多轮对话。先 `brief` 读现状，再把「现在有什么、卡在哪、哪些是旧账、哪些是新问题」说清楚；**方向是这一步的结论**，落在 `D` 行，不是独立的一步。然后沿方向制定工作，把工作拆成任务，一个任务一个任务推进。每做完一个任务，现状更新一次，下一轮从更新后的现状开始。

```
现状（定 D）→ W → T → 推进 → 新的现状
```

一条方向必须有：

| 字段 | 写什么 |
|---|---|
| **现状** | 现在有什么、卡在哪、哪些是旧账、哪些是新问题 |
| **为什么是现在** | 为什么这条方向比别的更该先走 |
| 用户 / 角色 | 谁走这条路 |
| 起点 | 从什么状态开始 |
| 成功状态 | 可观察的终点（一句话） |
| 路径 | 3–7 步，每步用哪些功能 |
| 接缝 | 步骤之间的状态 / 权限 / 失败 / 空状态 |
| 不覆盖 | 这次不做什么 |
| 走通验收 | 一份可执行的 walkthrough 或 E2E |
| 关联 | `REQ` / `F` / `W` |

**接缝是方向卡和「功能清单」的分水岭。** 写不出接缝，说明这条方向还只是几个功能的拼盘。

**验收方式**：方向不能用一条 `verify:` 命令验收，它用走通验收——在干净环境里按路径走一遍，每步记录观察结果，包括失败路径、空状态、权限、重试。机器判形式（`P18` / REQ-018，2.8.1）：走通验收带 `@YYYY-MM-DD` 复核日、`F-nnn` / `W<n.m>` / `K<n>` 引用存在、接缝非空；走没走通、体验能不能接受、接缝归谁，人判。

### 4. 设计：工作与任务之间的可替换性检查

**设计是工作和任务之间的一步，不是实施的一部分。** 工作和功能回答「做什么」，任务回答「这一场改什么」；设计回答「怎么做，哪里以后要换」。

一条设计卡必须有：

| 字段 | 写什么 |
|---|---|
| 接口 | 这个功能 / 工作对外暴露什么、依赖什么；哪些是稳定契约 |
| 可替换点 | 哪些实现细节最可能变（数据源、外部服务、算法、UI、存储、权限）；换实现要改几处 |
| 扩展点 | 未来的开放问题 / 新功能从哪里接进来 |
| 失败边界 | 失败、超时、重试、回滚、空状态怎么处理 |
| 任务拆分 | 这份设计拆成哪些任务；每个任务改哪一块 |
| 取舍 | 备选设计与为什么选它；重要取舍开 ADR |

**设计卡按改动大小伸缩**：小改动写 3 行（接口 / 可替换点 / 失败边界）；没有可替换点的写「无」并说明为什么；大改动才写完整设计卡。

**回到设计时**：旧设计下拆出的任务先标 `搁置` 或 `撤回`，不带着旧设计继续做；重新设计后再拆新任务。

**设计门**：设计卡定稿前、拆任务前，由人评审——接口稳定吗、可替换点隔离了吗、扩展点合理吗、任务拆分覆盖设计吗。设计没定，不拆任务。

**考核回顾的回路**：如果考核发现「这个实现要可替换」或「换个实现要改很多处」，回到设计重新设计，再拆任务；不是只补一个补丁任务。

## 备选方案

| 选项 | 说明 | 为什么没选 | 回到条件（什么事实出现就重新考虑） | 触发信号（可观察的） |
|---|---|---|---|---|
| A | 候选也发 `ISS` 号，五状态全在台账 | 每个一闪而过的念头都占号，收件箱被噪音撑爆；候选的默认命运是「不承诺」，发号就是承诺 | 若重要候选连续被遗忘（超过 3 条候选在分诊时已无法还原上下文） | 待分诊里出现「这条当时想说什么」的返工，每季度 ≥ 3 次 |
| B | 加第六个状态 `持续`，专门表示开放问题「还活着但没在动」 | 与 `确立` + `回到条件` 重复；多一个状态就多一套流转与判据 | 若使用者反复问「这条现在到底算不算在做」，且 `确立` 无法回答 | 同一开放问题在两次开场里被重复分诊 ≥ 2 次 |
| C | 任务单亲挂 `W`，用 `关联` 软指 `F` | 需求线到功能就断，任务无法向上回溯；「任务是将功能划分一到多个任务」无法表达 | 若双亲导致计划表维护成本明显上升（任务的功能归属经常改） | 一场会话里为「这个任务算哪个功能」争论 ≥ 2 次 |
| D | 考核留在功能级，任务只写验收 | 功能一大，考核变成总结；最小单元没有考核，回到「功能级假完成」 | 若任务级四格退化成复制粘贴（同一功能下多个任务写同样的四格） | 连续 5 个任务的考核四格内容重合度 > 80% |
| E | 方向线定义为一组功能 + 一个成功状态 | 没有路径与接缝，方向退化成功能清单；体验与集成问题仍然没人负责 | 若走通验收连续 3 个月没有执行记录（方向卡只有成功状态） | 方向卡更新时只改「成功状态」，从不改「接缝 / 走通」 |
| F | 设计放在任务内（每个任务写实现思路） | 功能级可替换性没人负责；任务拆完才发现接口不对，返工在实施阶段 | 若设计卡连续 5 次没有影响任务拆分 / 实现 | 设计卡字段齐全但任务拆分与设计无关，或可替换点全是「无」却频繁返工 |

## 撤销条件

出现下列任一可核对事实，就推翻本决策：

1. **候选被系统性遗忘**：连续两个季度，待分诊里出现「这条当时想说什么」的返工 ≥ 3 次/季度，说明候选层太轻，需要给候选发号或加提醒。
2. **双亲不可维护**：一场会话里为「这个任务算哪个功能」争论 ≥ 2 次，或超过 20% 的新任务无法归属到单一功能，退回单亲 + 软链接。
3. **任务考核变成仪式**：连续 5 个任务的考核四格内容重合度 > 80%，说明颗粒度不对，考核回功能级或改为抽检。
4. **方向卡只有成功状态**：连续 3 个月没有任何走通记录，说明走通验收没有被执行，方向线退化为路线图，需要简化或换承载。
5. **开放问题被反复重开**：同一开放问题在两次开场里被重复分诊 ≥ 2 次，说明五状态不够表达，考虑加 `持续` 或独立的「观察」表。
6. **设计卡变成仪式**：连续 5 个设计卡的「可替换点」都是「无」，但后续频繁因替换 / 扩展返工；或设计卡从不影响任务拆分——说明设计步太重，退回任务内设计。
