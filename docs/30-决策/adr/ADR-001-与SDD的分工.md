# ADR-001 · 与 SDD 的分工：借鉴增补件，不整体替换

> 一文件一决策。命名 `ADR-<三位编号>-<短标题>.md`；编号只增不复用。
> **双向链**：本决策取代别人，写在 `supersedes`；被别人取代，写在 `superseded_by`。
> 两条链都会被 `doc_check.py` 的 E15 校验：指向的 ADR 必须存在，且取代链必须终止在一个活决策上。

## 状态

active（2026-10-29 由本项目自举首场会话确认）。

## 背景

讨论「本项目与 Spec-Driven Development（Spec Kit / Kiro / OpenSpec / BMAD）有何异同」时，出现一个需要当场定下来的取舍：SDD 在 2026 年是事实标准，要不要整体换过去。

可查证据：

- 本仓库模型：`SKILL.md` 的核心结构（会话档案 + ADR + 三层计划）与 `references/ecosystem.md`「明确不接的」一节，此前已写明"可借鉴格式，不建议替换过程层"，但没写清**借什么、不借什么、什么条件下改主意**。
- SDD 侧现行形态：Spec Kit 为 constitution → specify → plan → tasks → implement → converge，Kiro 为 `requirements.md`/`design.md`/`tasks.md`（验收标准用 EARS），OpenSpec 为 `specs/` + `changes/`（ADDED/MODIFIED/REMOVED 的 delta 在归档时合进主规格），BMAD v6.12 改为"先调查再定流程轻重"。
- 外部实践证据（2026）：小改动被套全流程的反例（一个修复被拆成 4 个 user story / 16 条验收标准）、审查负担只是从代码转移到工件、全量规格导致"上下文腐化"（错误因被反复引用而获得权威）、以及 Kent Beck 的质疑——预先写死 spec 假设实现过程中不会学到任何会改变 spec 的东西。

## 决策

1. **不得**整体替换本实践：SDD 的计量单位是"一次变更"，本项目是"一次会话/项目连续演化"，替换会丢掉会话档案、时间线与加权排序三件没有替代品的东西。
2. **必须**按缺口逐个借鉴，四项各承其责：
   - 契约增量（`_delta`，借鉴 OpenSpec 的 ADDED/MODIFIED/REMOVED + 归档合并）→ 计划 `W1.1`；
   - 实现↔契约回检（`verify:` 字段 + CI，借鉴 Spec Kit 的 Converge）→ 计划 `W1.2`；
   - 改动分级（right-sized，借鉴 BMAD v6.12）→ 计划 `W2.1`；
   - 交接锚定任务编号（借鉴 OpenSpec 的 tasks 勾选续做）→ 计划 `W2.2`。
3. **必须**让借鉴件服从本项目的校验体系：新增行为一律落成带码规则（`E*`/`S*`/`P*`），**不得**只写在文档里不实现——这是 `CHANGELOG.md` 2.1.0 已吃过一次的教训。
4. **不得**把过程记录（authority 4）升级为裁决依据；借鉴来的 spec 也**不得**取代 ADR 的选项开放式记录。

## 备选方案

| 选项 | 说明 | 为什么没选 | 回到条件（什么事实出现就重新考虑） | 触发信号（可观察的） |
|---|---|---|---|---|
| A 借鉴增补件（本决策） | 只补 4 个缺口，格式向生态靠拢，骨架与脚本保留 | — | — | — |
| B 整体换成 Spec Kit / Kiro / OpenSpec | 用对方的 constitution/spec/tasks 与 slash 命令取代现有三层计划 | 计量单位不匹配：对方以"一次变更"为原子，做完即归档，没有跨会话时间线与加权排序；且都是重流程，与"轻到一次会话跑完"冲突 | 项目变成多人并行的多 feature 仓库、不再需要"这个项目怎么一步步变成现在这样"的叙事 | 连续两个版本的 `CHANGELOG.md` 里没有任何"过程层/计划层"改动；或时间线连续 4 周无新增档案 |
| C 全量 / 单体 spec 重写 | 每个能力写一篇长 spec，作为唯一事实源 | 规格膨胀与上下文腐化：错误被反复引用后获得权威，模型在错误前提上越写越自洽；实测有效的是 100–500 行的模块化文件 | 对外必须交付完整规格说明书（客户/审计需要成册文档） | 单篇契约超过 300 行，或改一次契约要动 3 篇以上 |
| D 小改动也走全流程 | 任何改动都建档案、走五连跑 | 审查负担只是从代码转移到工件，并没有减少；小改动上收益为负 | 出现"改了但无人复核"导致的线上事故 | 同一周出现 ≥3 次"一行修复却走完五连跑"，或有人因此开始跳过建档 |
| E 角色扮演式团队流程 | 用分析师/PM/架构师/Scrum Master 多角色推进 | LLM 不需要被"协调"，不会疲劳；BMAD 自己在 v6.3 已把多个角色并入开发 agent | 外部合规要求"角色分离"的签字链 | 审计方要求提供分角色签署的评审记录 |

## 影响

- 改动半径：仅新增 `docs/` 目录与计划条目，不动 `scripts/`、`SKILL.md`、`build.py`；`docs/` 不进入 `.skill` 包（`build.py` 的 `ROOT_FILES` + `INCLUDE_DIRS` 不含它），安装包体积与结构校验不受影响。
- 迁移：无旧数据迁移；已有 `CHANGELOG.md` 保持"版本演进"职责，不复制本档案内容（一个事实一处）。
- 代价：本仓库从此每场会话固定五连跑；新增规则要先在 `self_test.py` 里立断言，否则会出现"文档写了、代码没实现"。
- 已知缺口：四项借鉴全部**待开工**，当前 doc_check 对 `_delta` 与 `verify:` 一无所知（ISS-001/ISS-002）。

## 撤销条件

出现下列任一可独立核对的事实，本决策即应推翻并重开 ADR：

1. `docs/70-过程/时间线.md` 连续 4 周（≥28 天）没有新增会话档案——说明过程层成本高于收益，"连续演化"这个理由是空的。
2. 借鉴件落地后 3 个月内，`doc_check --baseline` 的存量问题数为 0 且 `ISS` 表里没有一条"漏登"类问题——说明这套校验已经饱和，继续加固是过设计。
3. 项目性质改变：需要按 feature 并行、且必须向外部交付成册规格说明书——此时应按备选 B/C 重开决策，而不是继续增补。
