# doc-driven-development

**中文** | [English](./README.en.md)

这是一个给 AI 编程助手用的技能（Agent Skill）。它把开发上下文从聊天窗口搬进项目文档，让文档成为项目的唯一事实源。换会话、换人、隔三个月回来，不用重讲背景；AI 说做完了，指得出证据。

## 这是什么

用 AI 开发时，上下文（AI 对这个项目的了解：需求、进度、决策原因、下一步）通常只活在聊天窗口里，窗口一关就没了。

这个技能按顺序做四件事：

1. 把上下文从聊天窗口搬进项目文档。
2. 分类整理搬进来的内容：用户原话按类型归档，AI 的推理与取舍单独成栏，过程压成交接锚点，结论沉淀为需求、决策与功能条目。
3. 让文档成为唯一事实源：每件事只有一个定义处，规则有编号，脚本能校验，生成区由脚本重建、不手改。
4. 在这个地基上长开发能力：过程记忆、决策记忆、计划排序、问题收件箱、门禁、可观测性。

上下文在窗口里，会随会话消失；在文档里，才能交接。

## 给谁用

用 AI 写代码的人，尤其是开发经验不足的开发者。

分工固定：AI 做实现，读文档、改代码、跑校验；人守少数关键门禁。门禁是人工判断的检查点：需求是不是这句、方向值不值得走、做出来的行为对不对。这几个问题由人回答，其余 AI 直接做，做完给证据。

不需要逐条盯着 AI，也不用每个动作点批准，只在门禁上判断。经验不足的开发者尤其适合这个分工：AI 补写代码的部分，人练判断的部分。

## 解决什么

AI 协作开发有四种成本，这个技能为降低它们而设计：

1. 背景反复重讲：换会话、换人、隔三个月，都要重讲需求与进度。交接锚点加开场 brief，让下一场先读现状再动手。
2. AI 假完成：AI 说做完了，其实只改了代码，没验证。这里要求已完成必须指得出需求、代码入口、验收命令与 commit，状态只被证据推进。验收是判断做出来的对不对，不只是代码能跑。
3. 发现的问题丢失：过程中的发现要么打断主线，要么静默消失。问题收件箱先落地不打断；可关闭的走闭环，开放的带回访条件。
4. 每天纠结先做什么：每天重新决定做什么，或同时推五件事。计划的下一步只有一个出口，顺序由打分算出，不手排。

## 目标与做法

目标是系统级覆盖：从系统里任何一个入口出发，把用户能走的每条路走通。走通指每一步的结果能验证、失败能退、换人能接。逐个铺功能不算数，路才是要验的东西。线路覆盖是手段，不是目标。

做法两句话：

- 敏捷优先：先做最小可用版，马上用起来，在使用中调整。很多取舍要产品做出来、真机用过才判得出来。
- 重 AI：可逆的事 AI 直接做，人只守不可逆的门禁。AI 把先做出来看看的周期压得很短。

每加一个环节，先回答一个问题：它怎么判真假、什么时候能撤。答不上就不加。所以只有五道门，每道门要么有机器判据，要么有明确的人判动作。工时、甘特、看板同步，明确不做。

这套做法的结果一句话：说完了能验、验完了能退、没做完的有地方待着。

## 四条承诺

1. 一处定义：同一件事实出现第二份，就是错误。
2. 可回溯：任何已完成都指得出需求、代码入口、验收命令、commit。
3. 可调优先级：想先看哪块功能，就改打分或视角权重，重跑 `plan.py index` 重排。顺序是算出来的，不是手排的。
4. 不丢问题：任何发现都有落点，不许静默消失。

## 能力一览

| 能力 | 做什么 |
|---|---|
| 文档骨架 | 一条命令铺出 5 / 8 层目录、模式与校验脚本 |
| 过程记忆 | 一次会话一份双侧档案，时间线自动重建 |
| 决策记忆 | 一决策一条 ADR，被否的方案不删，写清什么信号可以翻案 |
| 需求与功能 | 需求写成可验证的句子，配验收命令 |
| 计划与排序 | 方向、工作、任务三层，六维打分，多视角排序 |
| 问题收件箱 | 发现的问题先落地，不打断当前工作 |
| 真机验收 | 不是最终版就保持可替换，开一条 RV 单 |
| 五道门 | 对齐、评审、设计、对照、考核；机器判形式，人判语义 |
| 可观测性 | 组件级留记录，系统级留 trace |
| 自校验与交付 | 收尾五连跑、全量自测、六端安装 |

ADR 是决策记录：一个文件记一个决策，为什么这么定、还有哪些选项、什么条件下可以推翻。

## 快速开始

```bash
git clone https://github.com/wbaxm2016/doc-driven-development.git
cd doc-driven-development && python scripts/self_test.py   # 约 1–2 分钟，不碰你的项目
```

接进自己的项目：

```bash
python install.py --list          # 看本机哪些产品能装、各装到哪
python install.py --only dsh      # 装到 DeepSeek Harness；id 见上一条输出

cd <你的项目根目录>
python "$HOME/.dsh/skills/doc-driven-development/scripts/doc_init.py" --target .
python scripts/doc_check.py       # 期望 errors=0
```

装到哪台宿主由 [install-targets.json](./install-targets.json) 声明；发版与回滚见 [CONTRIBUTING.md](./CONTRIBUTING.md)；日常命令与模板见 [SKILL.md](./SKILL.md)。

## 一次开发怎么走

分工：人提供事实和判断，Agent 负责读写、执行、校验。批准不是判断：点批准只回答了让它跑，没回答它对不对。判断留在门禁上。

| 阶段 | 人做什么 | Agent 做什么 |
|---|---|---|
| 开场 | 说清这次要解决什么 | 读上一场交接、未完成的计划、收件箱 |
| 现状与方向 | 讲现在有什么、卡在哪、这次要什么 | 多轮提问、查代码，写成可核对的事实 |
| 对齐门 | 拍板：需求是不是这句、方向值不值得走 | 写需求或方向 |
| 评审门 | 确认：功能满足哪条需求、能不能做、代价多大 | 写功能或工作条目 |
| 设计门 | 评审：接口、可替换点、失败边界 | 写设计卡 |
| 任务与实施 | 关键取舍拍板 | 拆任务、改代码、跑冒烟，问题进收件箱 |
| 对照门 | 读行为：做的是不是需求那一句 | 填对照清单，差异登记 |
| 考核门 | 判断：值不值、代价偏没偏 | 给证据，列开放问题 |
| 测试与回写 | 确认状态回写 | 跑验收命令与收尾五连跑 |
| 收尾 | 确认下一步与开放问题 | 写会话交接，重建时间线 |

五道门一句话：需求或方向没被用户复述或采纳，不立项；功能答不出满足哪条需求、能不能做、代价多大，不进计划；设计卡没定，不拆任务；对照没做、差异没登记，不推到已对照；考核四格没写满，不说已验收。

机器判形式：结构、引用、编号、状态词、入口存在、验收命令真跑。人判语义：条款写得对不对、行为是不是这件事、开放问题该不该关、方向选得对不对。

收尾五连跑：`devlog check` → `devlog index` → `plan check` → `plan index` → `doc_check`，任一不是 `0 error` 都不算收尾。

回滚：需求作废改文档状态，实现回退用完成于记录的 commit 做 `git revert`。先改文档，再改代码。

只改措辞、错字、格式的轻档改动不建档，只跑触及的校验。

## 不保证什么

- 完整性靠纪律，不靠校验。脚本判得了字段与引用，判不了一条问题该不该记、该不该关。
- 不保证 Agent 不乱动。它不逐条请示，就可能跑错命令、改错文件。兜底是 git：完成锚点能回退，验收命令能重跑。
- 判据只在写了日期才会醒来。回访条件写 `@YYYY-MM-DD`，到期才提醒；没写日期的，脚本不猜。
- 观测不替项目跑运行时。技能给模板与参考实现，项目自己实现记录。
- 假设一个人加一个 Agent、一次一个会话。两个会话并行改同一工作区会互相踩，这里没有并发控制。
