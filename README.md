# doc-driven-development

## 项目目标

让 AI 协作开发的每个判断都有落点、每次完成都有证据、每个下一步都有出处。

它把开发过程写成一套可执行的事实骨架：需求、功能、决策、问题、进度、证据各有唯一载体；人负责判断，Agent 负责执行，文档负责记住。三者读的是同一份事实。

这套东西不是提案：本仓库自己就用它开发——`docs/` 里的会话档案、ADR、功能台账与开发计划，都是这套流程的产物。

## 取向：闭环优先于覆盖

过程方法论大多在扩覆盖——更多文档类型、更多字段、更多仪式。这套反过来：**不追求覆盖，只保证闭得上**。每加一个环节，先得回答「它凭什么判真假、什么时候能退」；答不上就不加。所以它只有五道门，却每道门都有机器判据或明确的人判动作；所以它明说不做工时、甘特、看板同步——那是取舍，不是待补。

撑起这个取舍的是三个反直觉的判断：

- **判得真：对照在测试之前，考核在回写之前**。测试只证明「符合断言」，不证明「断言就是需求那一句」；状态一旦推到已验收，也没人再问「值不值」。顺序倒了，就会拿「为错方向写的测试全绿」当完成证据。
- **退得回：完成即可回滚**。`完成于` 记 commit，所以「已完成」不是一句话，是一个能 `git revert` 的点；没有锚点的完成，只能靠记忆复原。
- **收得住：开放问题不许关**。只有可关闭的问题才谈「闭环」；开放问题换的是「本轮做到哪」和「什么信号回来」——它的终态不是关闭，是判断。

三件合起来才叫闭环：**说完了能验、验完了能退、没做完的有地方待着**。缺一件，这套东西就退化成记录。

## 价值

- **对开发者**：换会话、换人、隔三个月，仍能看懂「当时为什么、做到哪、下一步是什么」。
- **对 Agent**：开场先读现状，不用重新对齐技术栈与约束；说「做完了」时指得出证据。
- **对项目**：文档不再是开发之外的额外负担，而是开发过程本身的可执行骨架。

它降低四类成本：

| 成本 | 不解决的后果 | 这套东西怎么降 |
|---|---|---|
| **重复对齐** | 换会话、换人、隔三个月都要重讲 | 交接锚点 + `brief` + 功能行 + 决策回顾 |
| **假完成** | 只改了代码，测试全绿但方向错了 | 冒烟 → 对照 → 考核 → `verify` → 完成于 |
| **问题丢失** | 发现的问题拐进去丢主线，或静默消失 | 发现即登记；候选 → 台账 → 约束 |
| **排序内耗** | 每天重新决定做什么，或同时推进多个目标 | 粒度三层 + 六维排序 + 三视角排序 + 流程门禁 |

四条可检验的承诺：

1. **一处定义**：同类事实出现第二份，就是错误。
2. **可回溯**：任一「已完成」指得出需求、代码入口、验收命令、commit。
3. **可排序**：任一「下一步」来自唯一出口，且能追到方向或需求。
4. **不丢问题**：任一发现都有落点，不许静默消失。

## 工作流程：一次开发怎么走

从「人提出目标」开始，到「下一轮能接着做」结束。需求线与方向线共用这条主干（区别见「双线开发」），在**任务**上合流。分工固定：**人提供事实与判断，Agent 负责读写、执行与校验**；表内编号只在本文件内有效。

| 动作 | 人做什么 | Agent 做什么 | 落在哪 |
|---|---|---|---|
| 1 开场 | 说清这次想解决什么 | `brief` 读上一场交接、计划未完成、收件箱；复述现状 | 本次范围 |
| 2 现状与目标 | 讲现在有什么、卡在哪、哪些是旧账；说清这次要达到什么 | 多轮提问、查代码 / 文档，写成可核对的事实 | 会话 §1 / §3 |
| 3 定切面（门①） | **拍板**：需求复述或采纳；方向确认值得走 | 需求线写 `REQ`（EARS + `verify:`）；方向线在方向卡写 `D` | `REQ` / `D` |
| 4 定中间层（门②） | **确认**：功能答三问（满足 / 能做 / 代价）；工作验收能否独立成立 | 需求线写 `F`（满足哪条、入口、证据）；方向线写 `W`（1–3 场会话能独立验收） | `F` / `W` |
| 5 设计（门③） | **评审**：接口 / 可替换点 / 扩展点 / 失败边界；任务拆分覆盖设计 | 写设计卡（一个工作一张，三格必填）；重要取舍开 ADR | 设计卡（+ ADR） |
| 6 定任务 | **确认**：颗粒度、优先级、前置 | 按设计拆 `T`（双亲 `W` + `F`）；六维打分排序 | `T` + 排序视图 |
| 7 实施 | 关键取舍上拍板，不必全程盯 | 改代码 / 文档；跑冒烟；问题当场进收件箱 | 代码 + `ISS` |
| 8 对照（门④） | **读行为**：冒烟通过后，做的是不是需求那一句 | 取功能行、填对照清单；差异登记 `ISS` | 对照清单 |
| 9 考核回顾（门⑤） | **判断**：值不值、代价偏没偏；回顾流程；定开放问题去留；评估实现是否可调整 / 可优化 / 可替换 / 可扩展 | 提供证据；列开放问题 | 任务考核四格（做法 / 一致 / 代价 / 结论）+ 功能一行汇总 |
| 10 测试 / 回写 | 确认状态回写 | 跑 `verify` + 收尾五连跑；按证据回写需求 / 功能 / 计划 | `0 error` |
| 11 收尾 / 交接 | 确认下一步、开放问题与现状变化 | 写会话 §7；更新现状；重建时间线 | 下一场的起点 |

**第 9 步有三个出口，不是终点**：不需要补任务 → 第 10 步；需要补任务 → 第 6 步；实现要重新设计（比如某个实现要可替换）→ 第 5 步。即使没发现开放问题，只要回顾认为设计还要改，也回第 5 步；回设计时先把旧设计下拆出的任务标 `搁置` / `撤回`，别带着旧设计继续做。

**收尾五连跑**：`devlog check` → `devlog index` → `plan check` → `plan index` → `doc_check`，任一非 `0 error` 都不算收尾；`verify` 太慢，不在其中，挂 CI。

**推翻与回滚**：需求作废走 `_delta` 的 `REMOVED`（编号不复用），功能撤回把状态改成 `撤回` 并写理由；回到某个功能之前，用「完成于」里的 commit `git revert`。**先改文档再改代码**，否则会出现「代码退回了、需求还写着已实现」。

**按改动大小伸缩**：只改措辞 / 错字 / 格式 / 注释的轻档改动不建档、不跑五连跑，只跑改动触及的校验；设计卡同样伸缩——小改动写 3 行（接口 / 可替换点 / 失败边界），没有可替换点写「无」并说明为什么，大改动才写满。判据见 `SKILL.md`。

### 人工卡点：七处必须由人拍板

前五处是门，后两处是决策：

| 卡点 | 在哪 | 不拍板会怎样 |
|---|---|---|
| 门① 对齐 | 第 3 步，立项前 | 功能没人要，或方向走偏 |
| 门② 评审 | 第 4 步，进计划前 | 计划里塞进做不了的事，或工作切不开 |
| 门③ 设计 | 第 5 步，定稿前 | 实现僵化：换一个实现要改许多处，或根本换不掉 |
| 门④ 对照 | 第 8 步，测试前 | 测试全绿，方向却错了 |
| 门⑤ 考核 | 第 9 步，已验收前 | 「做完了」没有质量结论；该重设计的没重设计，下次改动更贵 |
| 决策① 开放问题收口 | 第 9 步回顾时、第 11 步收尾前 | 问题被静默关掉，或永远悬着 |
| 决策② 发版 / 回滚 | 主干之外 | 不可逆的发布事故 |

机器判形式：结构、引用、编号、状态词、入口存在、设计卡在不在、`verify` 真跑、证据组号；人判语义：条款写得对不对、行为是不是这件事、开放问题该不该关、方向选得对不对、设计经不经得起替换。

## 结构与分层

三层 + 一个地基：

| 层 | 回答什么 | 装什么 |
|---|---|---|
| **地基** | 凭什么信 | 唯一事实源：一处定义、引用可查、脚本可验 |
| **结构层** | 项目里有哪些对象 | 三张网：过程 / 工作 / 问题 |
| **运行层** | 一次开发怎么走完 | 正向主干道 + 反向回溯 + 五道门 |
| **治理层** | 多个方向先做哪个 | 三层、六维、三视角、状态机、棘轮 |

三张网：

| 网 | 回答什么 | 载体 |
|---|---|---|
| **过程网** | 怎么一步步变成现在这样 | 会话档案（一次会话一份）+ 时间线 + ADR 取代链 |
| **工作网** | 现在做什么、为什么是它 | 需求/功能 + 方向/工作/任务 |
| **问题网** | 发现了什么、什么时候回来 | 候选 `Q` + 台账 `ISS` + 约束 `REQ`/`ADR`/计划 |

问题按四维管理：

| 维度 | 取值 |
|---|---|
| 层 | 候选层（`Q`，不占 `ISS`）/ 台账层（`ISS`）/ 约束层 |
| 状态 | 候选 / 确立 / 实施中 / 实现关闭 / 拒绝 |
| 性质 | 可关闭 / 开放 |
| 类型 | 缺陷 / 缺口 / 债 / 冲突 / 风险 / 机会 / 待决 |

**开放问题永远不进「实现关闭」**：一轮做完回「确立」，带着新的「本轮边界」和「回到条件」。可关闭的问题修完进「已闭环」，写结论与证据；拒绝的进「已拒绝」，写理由与重新考虑条件。

## 双线开发

| | 需求线 | 方向线 |
|---|---|---|
| 起点 | 一句必须成立的话 | 多轮对话搞清现状 |
| 怎么细分 | `REQ` → `F` → `T` | 现状（定 `D`）→ `W` → `T` |
| 判据 | EARS + `verify:`；功能指回需求、入口与证据 | 成功状态 + 走通验收；`W` 挂 `D`、`T` 挂 `W` |
| 失败模式 | 功能很多，但连不成用户能走通的路 | 路径很顺，但每一步都不可验证 |

### 方向线怎么推进

```
现状（多轮对话，定下方向）──► 工作 ──► 设计 ──► 任务 ──► 推进
   ▲                                                        │
   └──────────────────── 新的现状 ◄─────────────────────────┘
```

- **现状**：多轮对话把「现在有什么、卡在哪、哪些是旧账、哪些是新问题」说清楚；**方向是这一步的结论，不是单独一步**——它落在 `00-门面/方向卡.md`，计划 §3 只登记编号与依据。
- **工作**：沿方向切成 1–3 场会话能独立验收的一段。
- **设计**：在工作和任务之间，先把接口、可替换点、扩展点、失败边界设计清楚；设计定了再拆任务。
- **任务**：把工作拆成一场会话能完成、能验证、能考核的最小改动。
- **推进**：一个任务一个任务做——实施 → 对照 → 考核回顾 →（需要时回到第 5 步重新设计，或第 6 步补任务）→ 测试 → 回写；每做完一个，现状更新一次，下一轮从更新后的现状开始。

方向线不是一开始就有的：它是多轮对话的产物，不是一张静态的 `D → W → T` 树。

两条线不是两个并行流程，而是同一个开发整体的两个切面——需求线按「必须成立什么」切，方向线按「用户怎么走通」切；`W` 挂 `D`，不挂 `REQ`，一条 `REQ` 可以跨几个 `W`，一个 `W` 也可以服务几条 `REQ`。它们在**任务**上合流：

```
需求线   REQ ──► F ──┐
                     ├──► T ──► 实施 → 对照 → 考核 → 测试 → 回写
方向线   现状（定 D）─► W ┘
```

每个任务有且只有一个 `功能` 和一个 `所属工作`；一个功能的多个任务可以跨多个工作，一个工作也可以含多个功能的任务——工作常常不是新功能，而是功能之间的接缝。

不是每个改动都要两条线都走：小改动可以只走需求线或只走方向线；两条线都走时，任务才在两条线上合流。

**为什么 AI 协作需要方向线**：AI 擅长局部实现，不擅长全局产品判断；没有方向线，它会把每个 prompt 优化到最好，但功能之间不连。方向线是一张压缩的「用户这条路」地图：现在在哪一段、下一段是什么、哪些接缝不能绕。需求线是刹车：AI 会自信地说「做完了」，验收是唯一的解药。

## 边界：它不保证什么

闭环说的是「记下来的都对」，不是「该记的都记了」：

- **完整性靠纪律，不靠校验**。脚本判得了字段、编号、引用、状态词；判不了一条问题该不该记、该不该关。
- **判据今天还不会自己醒来**。撤销条件、回到条件、走通验收都只是文字，没有到期提醒，也没有超期告警。
- **假设一个人 + 一个 Agent、一次一个会话**。两个会话并行改同一工作区会互相踩（校验可能瞬时红、编号可能撞），这里没有并发控制。

判不判得了语义、不覆盖哪些领域，见 [SKILL.md](./SKILL.md) 的「边界」与 [vision.md](./docs/00-门面/vision.md) 的「不是什么」。

## 快速开始

```bash
git clone https://github.com/wbaxm2016/doc-driven-development.git
cd doc-driven-development && python scripts/self_test.py   # 约 1 分钟，不碰你的项目
```

接进自己的项目：

```bash
python install.py --list          # 看本机哪些产品能装、各装到哪
python install.py --only dsh      # 装到 DeepSeek Harness；id 见上一条输出

cd <你的项目根目录>
python "$HOME/.dsh/skills/doc-driven-development/scripts/doc_init.py" --target .
python scripts/doc_check.py       # 期望 errors=0
```

装技能、宿主目录、发版与回滚见 [CONTRIBUTING.md](./CONTRIBUTING.md)；日常命令、模板与收尾校验见 [SKILL.md](./SKILL.md)。
