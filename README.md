# doc-driven-development

## 项目目标

让 AI 协作开发的每个判断都有落点、每次完成都有证据、每个下一步都有出处。

它把开发过程写成一套可执行的事实骨架：需求、功能、决策、问题、进度、证据各有唯一载体；人负责判断，Agent 负责执行，文档负责记住。这套东西不是提案——本仓库自己就用它开发。

## 价值

- **对开发者**：换会话、换人、隔三个月，仍能看懂「当时为什么、做到哪、下一步是什么」。
- **对 Agent**：开场先读现状，不用重新对齐技术栈与约束；说「做完了」时指得出证据。
- **对项目**：文档不再是开发之外的额外负担，而是开发过程本身的可执行骨架。

它主要降四类成本：重复对齐、假完成、问题丢失、排序内耗——机制在下面各节。

四条可检验的承诺：

1. **一处定义**：同类事实出现第二份，就是错误。
2. **可回溯**：任一「已完成」指得出需求、代码入口、验收命令、commit。
3. **可排序**：任一「下一步」来自唯一出口，且能追到方向或需求。
4. **不丢问题**：任一发现都有落点，不许静默消失。

## 取向：闭环优先于覆盖

过程方法论大多在扩覆盖——更多文档类型、更多字段、更多仪式。这套反过来：**不追求覆盖，只保证闭得上**。每加一个环节，先回答「它凭什么判真假、什么时候能退」；答不上就不加。所以它只有五道门，却每道门都有机器判据或明确的人判动作；也明说不做工时、甘特、看板同步——那是取舍，不是待补。

撑起这个取舍的是三个反直觉的判断：

- **判得真**：对照在测试之前，考核在回写之前。测试只证明「符合断言」，不证明「断言就是需求那一句」；顺序倒了，就会拿「为错方向写的测试全绿」当完成证据。
- **退得回**：完成即可回滚。`完成于` 记 commit，「已完成」是一个能 `git revert` 的点；没有锚点的完成只能靠记忆复原。
- **收得住**：开放问题不许关。只有可关闭的问题才谈「闭环」；开放问题换的是「本轮做到哪」和「什么信号回来」——终态不是关闭，是判断。

三件合起来才叫闭环：**说完了能验、验完了能退、没做完的有地方待着**。缺一件，这套东西就退化成记录。

## 双线开发模式

开发同时沿两条线推进：一条问「用户怎么走通」，一条问「必须成立什么」。它们不是两套流程，是同一个开发整体的两个切面，在**任务**上合流。

| | 方向线 | 需求线 |
|---|---|---|
| 起点 | 多轮对话搞清现状 | 一句必须成立的话 |
| 回答 | 用户怎么用、系统怎么串 | 做到了什么算数 |
| 怎么细分 | 现状（定 `D`）→ `W` → `T` | `REQ` → `F` → `T` |
| 判据 | 成功状态 + 走通验收；`W` 挂 `D`、`T` 挂 `W` | EARS + `verify:`；功能指回需求、入口与证据 |
| 失败模式 | 路径很顺，但每一步都不可验证 | 功能很多，但连不成用户能走通的路 |

### 方向线：先找到方向，再走通

#### 为什么需要方向线

**功能是节点，方向是边。** 只建节点，系统是一堆功能；只建边，系统是一条没有内容的空路。

用户感知到的往往不是功能，是**接缝**：上一步的数据带没带过来、失败了能不能退、明天回来状态还在不在、换个人能不能接上。空状态、权限、超时、重试不属于任何单个功能——功能测试全绿，用户这条路仍可能走不通；集成 bug（数据模型、状态机、权限、事件、错误传播）也住在接缝里。方向线的「工作」常常不是新功能，而是让 A 的输出成为 B 的合法输入、让 A 失败时 B 能回滚、让 A 和 B 的术语与错误码一致。

#### 跟 AI 协作时它的优势

- AI 擅长局部实现，不擅长全局产品判断：没有方向线，它会把每个 prompt 优化到最好，但功能之间不连。
- AI 会在功能级说「做完了」；方向线逼它走一遍端到端，看见接缝。
- AI 的上下文有限；方向线是一张压缩的「用户这条路」地图——现在在哪一段、下一段是什么、哪些接缝不能绕。
- 方向线是人的判断最该介入的地方：选哪条路、哪条先走、哪些体验不能妥协。AI 填实现，人定路径。

#### 方向线是自然的开发方式，不是凭空造出来的流程

多数团队其实已经在这么做，只是没写下来：先搞清现状，定下下一步，做完回头看现状有没有变。方向线做的事，是把这个循环写成可核对的东西——现状是一组事实，方向是一句能复述的成功状态，走通验收是一次真走。

方向从现状里长出来：开场先 `brief` 读一屏，再用多轮对话把「现在有什么、卡在哪、哪些是旧账、哪些是新问题」说清楚，从这里找出「用户这条路」。方向是这一步的**结论**，不是单独的一步，写进方向卡，计划 §3 只留编号与依据。但它不会自己发生：不主动做，AI 就会滑向「收集 prompt、逐个实现」；把它当成一张静态的 `D → W → T` 树，它便退化成路线图。

#### 方向确定之后：从工作到任务

方向落在方向卡（[`docs/00-门面/方向卡.md`](./docs/00-门面/方向卡.md)）的一行里：现状、成功状态、路径、接缝、不覆盖、走通验收等九项。机器只判三格（现状 / 成功状态 / 走通验收）；**接缝是方向卡与功能清单的分水岭**——写不出接缝，这条方向还只是几个功能的拼盘。

之后是循环，不是流水线：

```
现状（多轮对话，定下方向）──► 工作 ──► 设计 ──► 任务 ──► 推进
   ▲                                                        │
   └──────────────────── 新的现状 ◄─────────────────────────┘
```

- **工作 `W`**：沿方向切成 1–3 场会话能独立验收的一段。
- **设计**：工作和任务之间写设计卡（一个工作一张）：接口、可替换点、扩展点、失败边界；重要取舍开 ADR。设计没定，不拆任务。
- **任务 `T`**：一场会话能完成、能验证、能考核的最小改动。
- **推进**：实施 → 对照 → 考核回顾 →（需要时回到设计或补任务）→ 测试 → 回写；每做完一个，现状更新一次。

### 需求线：从一句必须成立的话出发

另一条线反过来：需求线要的是一句**可以被证伪的话**——写得出触发条件与行为、指得出一条能跑的命令。写不出 `WHEN`，说明还没想清楚——先去开 ADR，别在契约里糊一句「必须好用」。

1. **`REQ`**：EARS 句式 `WHEN <条件> THE SYSTEM SHALL <行为>`，配一条 `verify:`，在用户**复述或采纳**后才立得住（对齐门，没对齐不立项）。
2. **`F`**：落成一块可交付的能力，答完三问才进计划——满足哪条 `REQ`、能不能实现、代价合不合理（`S/M/L` + 一句话）。这是评审门；答不出代价，计划就变成许愿单。
3. **`T`**：一场会话能完成、能验证、能考核的最小改动。
4. **做完再说完成**：实施 → 冒烟 → **对照**（入口机器判，「做的是不是需求那一句」人读；差异必须落 `ISS`）→ **考核**（任务四格 + `完成于`）→ `verify` → 按证据回写。

这条线的性格是**刹车**：只回答「做到了没有」，不回答「该不该做」。每个功能都通过测试、彼此连不成一条路——那是方向线的缺口。

### 两条线在哪里合流

两条线切法不同：方向线按「用户怎么走通」切，需求线按「必须成立什么」切；`W` 挂 `D` 不挂 `REQ`，一条 `REQ` 可以跨几个 `W`。它们在**任务**上合流：

```
需求线   REQ ──► F ──┐
                     ├──► T ──► 实施 → 对照 → 考核 → 测试 → 回写
方向线   现状（定 D）─► W ┘
```

每个任务有且只有一个 `功能` 和一个 `所属工作`，但一个功能的任务可以跨多个工作——工作常常不是新功能，而是功能之间的接缝。小改动可以只走一条线。

## 工作流程：一次开发怎么走

从「人提出目标」开始，到「下一轮能接着做」结束。需求线与方向线共用这条主干（两条线的分工见上一节），在**任务**上合流。分工固定：**人提供事实与判断，Agent 负责读写、执行与校验**；表内编号只在本文件内有效。

> **这里的 1–11 是「动作」编号（按时间顺序），`SKILL.md` 的「十一格」是「对象」编号**（需求 / 功能 / 工作 / 设计 / 任务 / 实施 / 冒烟 / 对照 / 考核 / 测试 / 回写）。两套编号的语义不对齐，**按名字对应，不要按数字**：本文件的「第 5 步」是设计，`SKILL.md` 的「第 5 格」是任务。

| 动作 | 人做什么 | Agent 做什么 | 落在哪 |
|---|---|---|---|
| 1 开场 | 说清这次想解决什么 | `brief` 读上一场交接、计划未完成、收件箱；复述现状 | 本次范围 |
| 2 现状与目标 | 讲现在有什么、卡在哪、哪些是旧账；说清这次要达到什么 | 多轮提问、查代码 / 文档，写成可核对的事实 | 会话 §1 / §3 |
| 3 定切面（门①） | **拍板**：需求复述或采纳；方向确认值得走 | 需求线写 `REQ`（EARS + `verify:`）；方向线在方向卡写 `D` | `REQ` / `D` |
| 4 定中间层（门②） | **确认**：功能答三问（满足 / 能做 / 代价）；工作验收能否独立成立 | 需求线写 `F`（满足哪条、入口、证据）；方向线写 `W`（1–3 场会话能独立验收） | `F` / `W` |
| 5 设计（门③） | **评审**：接口 / 可替换点 / 扩展点 / 失败边界；任务拆分覆盖设计 | 写设计卡（一个工作一张，三格必填）；重要取舍开 ADR | 设计卡（+ ADR） |
| 6 定任务 | **确认**：颗粒度、优先级、前置 | 按设计拆 `T`（双亲 `W` + `F`）；六维打分排序 | `T` + 排序视图 |
| 7 实施 | 关键取舍上拍板，不必全程盯 | 改代码 / 文档；跑冒烟；问题当场进收件箱 | 代码 + `ISS` |
| 8 对照（门④） | **读行为**：冒烟通过后，做的是不是需求那一句 | 取功能行、填对照清单；差异登记 `ISS` | 对照清单 |
| 9 考核回顾（门⑤） | **判断**：值不值、代价偏没偏；回顾流程；定开放问题去留；评估实现是否可调整 / 可优化 / 可替换 / 可扩展 | 提供证据；列开放问题 | 任务考核四格（做法 / 一致 / 代价 / 结论）+ 功能一行汇总 |
| 10 测试 / 回写 | 确认状态回写 | 跑 `verify` + 收尾五连跑；按证据回写需求 / 功能 / 计划 | `0 error` |
| 11 收尾 / 交接 | 确认下一步、开放问题与现状变化 | 写会话 §7；更新现状；重建时间线 | 下一场的起点 |

**第 9 步有三个出口，不是终点**：不需要补任务 → 第 10 步；需要补任务 → 第 6 步；设计还要改（哪怕没发现开放问题）→ 第 5 步。回设计时先把旧任务标 `搁置` / `撤回`，别带着旧设计继续做。

**收尾五连跑**：`devlog check` → `devlog index` → `plan check` → `plan index` → `doc_check`，任一非 `0 error` 都不算收尾；`verify` 太慢，不在其中，挂 CI。

**推翻与回滚**：需求作废走 `_delta` 的 `REMOVED`（编号不复用），功能撤回改状态并写理由；回到某个功能之前，用「完成于」里的 commit `git revert`。**先改文档再改代码**，否则会出现「代码退回了、需求还写着已实现」。

**按改动大小伸缩**：只改措辞 / 错字 / 格式 / 注释的轻档改动不建档、不跑五连跑，只跑触及的校验；设计卡同样伸缩，小改动写三行，判据见 `SKILL.md`。

### 人工卡点：两处决策必须由人拍板

五道门的人动作已经写在工作流程表的「人做什么」列里，这里不再重复。主干之外还有两处必须由人拍板：

| 卡点 | 在哪 | 不拍板会怎样 |
|---|---|---|
| 决策① 开放问题收口 | 第 9 步回顾时、第 11 步收尾前 | 问题被静默关掉，或永远悬着 |
| 决策② 发版 / 回滚 | 主干之外 | 不可逆的发布事故 |

机器判形式：结构、引用、编号、状态词、入口存在、设计卡在不在、`verify` 真跑、证据组号；人判语义：条款写得对不对、行为是不是这件事、开放问题该不该关、方向选得对不对、设计经不经得起替换。

至此，一次开发怎么走已经讲完。这套流程背后的文档模型——三层 + 一个地基、三张网、问题四维——见 [vision.md](./docs/00-门面/vision.md) 的「三层 + 一个地基」「结构层：三张网」两节；README 只留入口，不重复它的定义。

## 边界：它不保证什么

闭环说的是「记下来的都对」，不是「该记的都记了」：

- **完整性靠纪律，不靠校验**。脚本判得了字段、编号、引用、状态词；判不了一条问题该不该记、该不该关。
- **判据今天还不会自己醒来**。撤销条件、回到条件、走通验收都只是文字，没有到期提醒，也没有超期告警。
- **假设一个人 + 一个 Agent、一次一个会话**。两个会话并行改同一工作区会互相踩（校验可能瞬时红、编号可能撞），这里没有并发控制。

判不判得了语义、不覆盖哪些领域，见 [SKILL.md](./SKILL.md) 的「边界」与 [vision.md](./docs/00-门面/vision.md) 的「不是什么」。

## 快速开始

```bash
git clone https://github.com/wbaxm2016/doc-driven-development.git
cd doc-driven-development && python scripts/self_test.py   # 约 1 分钟，不碰你的项目
```

接进自己的项目：

```bash
python install.py --list          # 看本机哪些产品能装、各装到哪
python install.py --only dsh      # 装到 DeepSeek Harness；id 见上一条输出

cd <你的项目根目录>
python "$HOME/.dsh/skills/doc-driven-development/scripts/doc_init.py" --target .
python scripts/doc_check.py       # 期望 errors=0
```

装到哪台宿主由 [`install-targets.json`](./install-targets.json) 声明（`install.py --list` 按它探查并打印每个宿主的目标目录）；发版与回滚见 [CONTRIBUTING.md](./CONTRIBUTING.md)；日常命令、模板与收尾校验见 [SKILL.md](./SKILL.md)。
