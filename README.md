# doc-driven-development

**中文** | [English](./README.en.md)

**AI 协作开发的第一性问题不是「AI 会不会写代码」，而是「上下文存在哪里」。** 只存在 agent 的窗口里，就是一个会随会话关闭而消失的问题；把它落到文档，才能持久；让文档成为唯一事实源，才能交接；地基稳了，技能才有地方长能力。

## 从 agent 的上下文，到项目的唯一事实源

四步，一步比一步硬：

1. **问题：上下文只活在 agent 里**——会话一关，为什么、做到哪、下一步是什么，全凭记忆重讲；换个人接不上，隔三个月查不到。
2. **文档做持久，也做分类、整理、精简、沉淀**——不是把聊天记录倒进文档：原话按类型归档，推理与取舍分栏，过程压成交接锚点，结论沉成需求、决策与功能行。
3. **文档做唯一事实源**——不是「代码一份、文档一份，冲突时猜哪份新」，而是每件事只有一个定义处：一处定义、引用可查、脚本可验、生成区不手改。
4. **在地基上长能力**——文档不再是开发之外的负担，而是开发过程本身的可执行骨架；下面这些能力都建在它上面。

## 它提供什么能力

| 能力 | 一句话 |
|---|---|
| 文档骨架 | 一条命令铺出 5 / 8 层、`_schema.json` 与校验脚本；目录、枚举、编号规则一处定义。 |
| 过程记忆 | 一次会话一份双侧档案：原话按类型归档，推理与取舍分栏，过程压成交接锚点，结论沉成需求、决策与功能行；时间线自动重建。 |
| 决策记忆 | 一决策一 ADR，带双向取代链与撤销条件；被否方案不删，写清什么信号可以切回。 |
| 需求与功能 | 需求写成可证伪的 EARS 句并配 `verify:` 命令；功能台账记入口、证据、完成于 commit。 |
| 计划与排序 | 方向 / 工作 / 任务三层，六维打分、多视角排序；下一步只有一个出口，顺序算出来。 |
| 问题收件箱 | 过程中发现的问题先落地不打断；可关闭的走闭环，开放的带回访条件。 |
| 五道门 | 对齐、评审、设计、对照、考核；机器判形式，人判语义，不可逆动作由人拍板。 |
| 可观测性 | 组件级留一条记录，系统级留一条 trace；四问定内容，四维定验收。 |
| 自校验与交付 | 收尾五连跑、全量自测、六端安装；能交给脚本查的，不靠自觉。 |

> 一句话：**说完了能验、验完了能退、没做完的有地方待着。**

## 四条承诺

1. **一处定义**：同一件事实出现第二份，就是错误。
2. **可回溯**：任何「已完成」都指得出需求、代码入口、验收命令、commit。
3. **可调优先级**：想先看到哪块功能，就把它调上来——改六维分值、换视角权重，重跑一次 `plan.py index` 就重排。顺序是算出来的，不是手排的。
4. **不丢问题**：任何发现都有落点，不许静默消失。

换来的也就四件事：不用重复对齐，不用怀疑假完成，问题不会丢在半路，不用每天纠结先做哪个。

## 设计取舍：做减法，追求系统级覆盖

大部分方法论在扩覆盖：更多文档类型、更多字段、更多仪式。这套反过来——**不求功能覆盖，只求系统级覆盖**：从系统任意一点切入，把整条通路走通再走下一条，每条用户走得通的路都要闭得上，铺满功能不算数。每加一个环节，先答一句「它凭什么判真假、什么时候能退」，答不上就不加。所以只有五道门，每道门要么有机器判据，要么有明确的人判动作。工时、甘特、看板同步，明说不做。

三个判断撑着这个取舍：

- **先判得真，再谈完成**：对照在测试之前。测试只证明「符合断言」，不证明「断言就是需求那一句」；顺序倒了，就会拿「为错方向写的测试全绿」当完成证据。
- **完成就能退**：「完成于」记 commit，「已完成」是一个能 `git revert` 的点。没有锚点的完成，只能靠记忆复原。
- **开放问题不许关**：能关的只有可关闭的问题。开放问题换的是「本轮做到哪」和「什么信号回来」——终态是判断，不是关闭。

合起来才叫闭环：**说完了能验、验完了能退、没做完的有地方待着**。缺一件，就退化成记录。

## 双线：方向线和需求线

开发同时沿两条线走：一条问「用户怎么走通」，一条问「必须成立什么」。不是两套流程，是同一个开发的两个切面，最后在**任务**上合流。

| | 方向线 | 需求线 |
|---|---|---|
| 起点 | 多轮对话先搞清现状 | 一句必须成立的话 |
| 回答 | 用户怎么用、系统怎么串 | 做到什么算数 |
| 细分 | 现状（定 `D`）→ `W` → `T` | `REQ` → `F` → `T` |
| 判据 | 成功状态 + 走通验收 | EARS + `verify:` |
| 失败模式 | 路径很顺，每步都不可验证 | 功能很多，连不成一条路 |
| 性格 | 油门 | 刹车 |

**方向线**：功能是节点，方向是边。只建节点，系统就是一堆功能；只建边，是一条没有内容的空路。

用户真正感知到的是**接缝**——上一步的数据带没带过来、失败了能不能退、明天回来状态还在不在、换个人能不能接上。空状态、权限、超时、重试不归任何单个功能，集成 bug 也住在接缝里。所以方向线的工作常常不是加功能，而是让 A 的输出成为 B 的合法输入。

方向线可以从任意一个功能切入——看的是整条通路，不是某个模块；走通一条再走下一条。线路覆盖是手段，**系统级覆盖才是目标**：覆盖的对象是线路，不是功能——功能只是节点，路才是要验的东西。

这正好是 AI 最容易漏的地方：它能把单个 prompt 做到最好，却判断不了哪条路值得走、哪个体验不能妥协。**AI 填实现，人定路径。**

方向写进方向卡（[`docs/00-门面/方向卡.md`](./docs/00-门面/方向卡.md)）的一行：现状、成功状态、路径、接缝、不覆盖、走通验收等九项。机器判四格在不在（现状 / 成功状态 / 走通验收 / 接缝）、走通验收的 `@复核日` 与引用存在（`P18` / REQ-018）；**写不出接缝，这条方向还只是几个功能的拼盘**。

之后是循环，不是流水线：

```
现状（多轮对话，定下方向）──► 工作 ──► 设计 ──► 任务 ──► 推进
   ▲                                                     │
   └────────────────── 新的现状 ◄────────────────────────┘
```

- **工作 `W`**：沿方向切出的一小段，1–3 场会话能独立验收。
- **设计**：一个工作一张设计卡——接口、可替换点、扩展点、失败边界。设计没定，不拆任务。
- **任务 `T`**：一场会话能做完、能验证、能考核的最小改动。
- **推进**：实施 → 对照 → 考核 → 测试 → 回写。做完一个，现状更新一次。

**需求线**反过来，要一句能被证伪的话：写得出触发条件（`WHEN <条件> THE SYSTEM SHALL <行为>`），配得出一条能跑的命令，才算需求。

写不出 `WHEN`，说明还没想清楚——先去开 ADR，别在契约里糊一句「必须好用」。`REQ` 要在用户复述或采纳后才立得住；`F` 答完三问（满足哪条需求、能不能做、代价多大）才进计划。

两条线切法不同：`W` 挂 `D` 不挂 `REQ`，一条 `REQ` 可以跨几个 `W`。它们只在**任务**上合流——每个任务有且只有一个功能和一个所属工作，但一个功能的任务可以跨多个工作。打分也只落在任务上：方向和工作不进六维评分，选哪条路、哪条先走，是人定的。

## 一次开发怎么走

分工固定：**人提供事实和判断，Agent 负责读写、执行、校验。**

**审批不是判断。** Agent 的读写、执行、校验不必逐条请示——DSH 里把审批策略设成「从不询问」，它照样跑完一轮。点一次「批准」只回答了「让它跑」，没回答「它对不对」；判断留在门上：方向值不值得走、需求是不是这句、做出来的行为对不对，由人过五道门；开放问题收口与发版 / 回滚这两处不可逆动作，由人拍板。

| 阶段 | 人做什么 | Agent 做什么 | 落在哪 |
|---|---|---|---|
| 开场 | 说清这次想解决什么 | `brief` 读上一场交接、未完成的计划、收件箱 | 本次范围 |
| 现状与方向 | 讲现在有什么、卡在哪、这次要什么 | 多轮提问、查代码，写成能核对的事实 | 会话 §1/§3、方向卡 |
| 切面（对齐门） | **拍板**：需求复述或采纳；方向值得走 | 写 `REQ`（EARS + `verify:`）或 `D` | `REQ` / `D` |
| 中间层（评审门） | **确认**：功能答三问；工作能否独立验收 | 写 `F`（入口、证据）或 `W` | `F` / `W` |
| 设计（设计门） | **评审**：接口、可替换点、失败边界 | 写设计卡；重要取舍开 ADR | 设计卡 |
| 任务与实施 | 关键取舍拍板，不必全程盯 | 拆 `T`、改代码、跑冒烟，问题当场进收件箱 | `T` + 代码 + `ISS` |
| 对照（对照门） | **读行为**：做的是不是需求那一句 | 取功能行、填对照清单、差异登记 `ISS` | 对照清单 |
| 考核（考核门） | **判断**：值不值、代价偏没偏、经不经得起下次改 | 给证据，列开放问题 | 任务考核四格 |
| 测试与回写 | 确认状态回写 | 跑 `verify` + 收尾五连跑，按证据回写 | `0 error` |
| 收尾 | 确认下一步、开放问题、现状变化 | 写会话 §7、更新现状、重建时间线 | 下一场的起点 |

五道门一句话版：需求或方向没被用户复述、采纳，不立项；功能或工作答不出「满足哪条、能不能做、代价多大」，不进计划；设计卡没定，不拆任务；对照没做、差异没登记，不许推到「已对照」；任务考核四格没写满，不许说「已验收」。

机器判形式：结构、引用、编号、状态词、入口存在、`verify` 真跑、设计卡在不在。人判语义：条款写得对不对、行为是不是这件事、开放问题该不该关、方向选得对不对、设计经不经得起替换。

考核不是终点，有三个出口：不需要补任务就往下走；需要补任务回「任务与实施」；设计要改就回「设计」，顺手把旧任务标 `搁置` 或 `撤回`——别带着旧设计硬做。

主干之外还有两处必须由人拍板：

| 卡点 | 在哪 | 不拍板会怎样 |
|---|---|---|
| 开放问题收口 | 回顾时、收尾前 | 问题被静默关掉，或永远悬着 |
| 发版 / 回滚 | 主干之外 | 不可逆的发布事故 |

**收尾五连跑**：`devlog check` → `devlog index` → `plan check` → `plan index` → `doc_check`，任一不是 `0 error` 都不算收尾。`verify` 太慢，挂 CI。

**推翻与回滚**：需求作废走 `_delta` 的 `REMOVED`（编号不复用），功能撤回改状态写理由；回退实现用「完成于」里的 commit `git revert`。**先改文档再改代码**，否则会出现「代码退回了、需求还写着已实现」。

**按改动大小伸缩**：只改措辞、错字、格式、注释的轻档改动不建档、不跑五连跑，只跑触及的校验；设计卡也一样，小改动写三行。

## 看得见：组件级与系统级可观测性

闭环管「记下来的都对」，可观测性管「当时到底发生了什么」。分两层：

- **组件级**：一条命令、一个门、一个脚本跑完，留下一条记录——运行的是什么、按哪条规则得出结果、失败落在哪。
- **系统级**：把它们串起来（五连跑、建档→校验→回写、发版→装机、门链），留下一条 trace——上一步的输出有没有成为下一步的输入、哪一步断了。

每条记录回答四问：**运行的是什么 · 为什么是这个结果 · 预期是什么样的 · 系统下一步是什么**。四问是记录内容，四维是验收框架：**可观测**（跑了吗、跑的是什么）、**可解释**（为什么是这个结果）、**可诊断**（问题在哪、下一步做什么）、**可改进**（同类问题是否复发、规则怎么改）。前三维单次记录就能答，可改进要跨 run 聚合。

技能给项目侧三样锚，不替项目跑运行时：

| 载体 | 是什么 | 机器判据 |
|---|---|---|
| 观测地图 | `doc_init` 铺 `40-运行/可观测性.md`：组件清单、每组件四问、信号与窗口、系统级串联 | 铺出来即可用 |
| 设计卡「观测四格」 | 观测对象 / 要回答的问题 / 信号 / 窗口 | `W12` 提醒（不阻断、存量不追溯） |
| 自身参考实现 | `observe.py run / five-run / show / status / trend` | 第 63 / 64 组断言；写失败只降级、不改主命令退出码 |

`observe trend` 按「码 + 目标文件」跨 run 聚合：同一问题出现几次、从哪次开始、跨版本有没有变化。观测是旁路——记录写失败不阻断主命令，也不回写台账状态。

## 它不保证什么

闭环说的是「记下来的都对」，不是「该记的都记了」。

- **完整性靠纪律，不靠校验**。脚本判得了字段、编号、引用、状态词，判不了一条问题该不该记、该不该关。
- **不保证 Agent 不乱动**。它不逐条请示，就会跑错命令、改错文件。兜底是 git 与证据——完成锚点能 `git revert`、`verify` 能重跑、提交前只 `add` 自己的路径；审批弹窗只拦动作，拦不住思路错。
- **判据只在写了日期才会醒来**。撤销条件、回到条件、走通验收里写 `@YYYY-MM-DD`，到期后 `brief` 会单列一行；没写日期的，脚本不猜——猜错就成了噪音。
- **观测不替项目跑运行时**。技能给模板、四格与 `W12` 提醒，项目按模板自己实现运行时；记录缺失只报证据缺口，不阻断主命令。
- **假设一个人 + 一个 Agent、一次一个会话**。两个会话并行改同一工作区会互相踩：校验可能瞬时红、编号可能撞，这里没有并发控制。

## 快速开始

```bash
git clone https://github.com/wbaxm2016/doc-driven-development.git
cd doc-driven-development && python scripts/self_test.py   # 约 1–2 分钟，不碰你的项目
```

接进自己的项目：

```bash
python install.py --list          # 看本机哪些产品能装、各装到哪
python install.py --only dsh      # 装到 DeepSeek Harness；id 见上一条输出

cd <你的项目根目录>
python "$HOME/.dsh/skills/doc-driven-development/scripts/doc_init.py" --target .
python scripts/doc_check.py       # 期望 errors=0
```

装到哪台宿主由 [`install-targets.json`](./install-targets.json) 声明（`install.py --list` 读它并打印每个宿主的目标目录）；发版与回滚见 [CONTRIBUTING.md](./CONTRIBUTING.md)；日常命令、模板与收尾校验见 [SKILL.md](./SKILL.md)。
