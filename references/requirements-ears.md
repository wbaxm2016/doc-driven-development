# 契约层怎么写：EARS 句式

## 为什么需要约束句式

`20-契约/` 的作用是"哪条**必须**成立"。但"必须"两个字救不了含糊：

> 必须支持导出。

这句话永远无法被判定真假——所以它永远不会失败，也就永远没有约束力。

EARS（Easy Approach to Requirements Syntax）原本是空客/NASA 用在安全关键系统上的需求句式，AWS Kiro 把它作为 AI 生成需求的默认格式。它只做一件事：**逼你把触发条件写出来**。写不出触发条件，通常意味着你还没想清楚这个需求什么时候该成立。

## 四种句式

| 类型 | 句式 | 何时用 |
|---|---|---|
| 常规行为 | `WHEN <触发条件> THE SYSTEM SHALL <可观察的行为>` | 有明确触发点 |
| 异常处理 | `IF <异常> THEN THE SYSTEM SHALL <兜底行为>` | 出错、越界、超时 |
| 持续约束 | `WHILE <状态成立> THE SYSTEM SHALL <行为>` | 一段时间内必须持续成立 |
| 无条件约束 | `THE SYSTEM SHALL <行为>` | 确实没有触发条件（少用） |

中文写法同样成立，不必硬套英文关键词：

- `当用户提交的表单含非法字段时，系统必须在该字段旁显示错误提示。`
- `若同一 IP 在 60 秒内请求超过 100 次，系统必须返回 429 并带上 Retry-After。`
- `在会话进行期间，系统必须保证收件箱编号只增不复用。`
- `系统必须对所有外链请求设置 10 秒超时。`

## 一条合格需求的五件套

| 字段 | 要求 |
|---|---|
| 编号 | `REQ-nnn`，只增不复用 |
| 句式 | 上面四种之一；**触发条件可观察** |
| 验收 | 一条命令 / 一次实测 / 一个可核对的数字 |
| `verify:` | **能直接跑**的命令或测试文件路径；CI 会执行它，不接受"人工看一眼" |
| 状态 | `待实现` / `已实现（未验收）` / `已完成`，只被证据推进 |

反例 → 正例：

> ❌ **REQ-007** 导出要快。
>
> ✅ **REQ-007** 当单次导出记录数 ≤ 10 万时，系统必须在 5 秒内返回可下载文件（P95，本机 4 核基准）。

第二句多了三处约束（规模、时限、基准环境），每处都能被独立核对——这才是"可判真假"。

## 机器能查到哪一步（诚实边界）

| 检查 | 码 | 强度 |
|---|---|---|
| 契约层正文出现「必须」，且出现「不得/不许」 | E13 | 强（形式） |
| 带 `REQ-nnn` 的条款行至少有规范措辞（`WHEN/IF/WHILE/GIVEN/SHALL/当/若/一旦/必须/应/不得/不许`，即 `doc_check.py` 的 `EARS_CUES`） | W7 | **弱信号**：只能拦"整行是名词短语"这种明显情形 |
| 条款行是否有 `verify:` 列 | —（**待实现**：W1.2 / T1.2.2） | 计划中的 E 码：缺失即报错；指到的测试是否真能跑由 T1.2.3 的 CI 判 |
| 触发条件是否真的可观察、验收是否真的能判 | — | **机器判不了，必须人读** |

所以 E13 全绿只说明"你没把契约写成说明文"，不说明"你的需求写对了"。W7 漏报是常态，别拿它当保障。

## 写不出来的时候

如果一条需求死活套不进任何句式，通常是下面三种情况之一：

1. **还没想清楚触发条件** → 它是待决项，进收件箱（`ISS-nnn`，类型「待决」），不写进契约。
2. **它其实是方案不是需求**（"必须用 Redis 缓存"）→ 它属于 ADR，把"用户能观察到什么"写进契约，机制交给决策。
3. **它是多个需求的合集** → 拆开。一条需求只留一个可判真假的断言。

`_schema.json` 里可以关掉这条检查：

```json
{ "ears": { "enabled": false } }
```

关掉只是不再报 W7，模板与本文档的写法约定仍然有效。
