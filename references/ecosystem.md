# 生态衔接：哪些轮子直接用，哪些必须自己造

## 先拆目标

这套实践要同时满足四件事，它们的成熟度差别很大：

| # | 能力 | 成熟度 |
|---|---|---|
| A | **文档是唯一事实源**（分层、单一权威、引用关系） | 无现成方案，必须靠约定 + 校验 |
| B | **过程可追溯**（会话档案、时间线、决策留档） | 部分有，但都是"变更级"而非"项目级" |
| C | **用文档管流程**（下一步做什么、为什么是它） | 部分有，且都不做加权排序 |
| D | **形式校验自动化**（front-matter、链接、编号、术语） | **完全成熟，不该自己造** |

结论先说：**没有一套现成工具覆盖 A+B+C。** 所以自研骨架是对的；但 D 类应当整体外包，B/C 的**格式**应当向生态靠拢。

## 逐项对照

### A 类：文档唯一事实源

| 工具 | 覆盖度 | 为什么不够 |
|---|---|---|
| MkDocs / Docusaurus / Antora | 只做渲染与导航 | 不管"哪份是唯一权威"，也不校验 layering |
| Backstage TechDocs | 做目录发现 | 面向服务目录，不面向"事实唯一性" |
| **本实践的分层 + `_schema.json`** | 覆盖 | 但语义重复只有 W2 这一条弱信号 |

这类能力本质是**治理约定**，工具只能查形式。所以判断标准不是"有没有轮子"，而是"约定有没有被机器守住"——这就是 E1–E17 存在的理由。

### B 类：过程可追溯

| 工具 | 覆盖什么 | 缺什么 |
|---|---|---|
| **OpenSpec** | 每次变更一份 proposal / design / tasks，归档时把 delta 折进主规格 | 没有"一次会话一份双侧档案"，也没有时间线 |
| **BMAD-METHOD** | 从简报、PRD、架构到 sprint 记录、复盘的完整留档 | 重量级、token 消耗高；按角色组织，不按"会话"组织 |
| **GitHub Spec Kit** | constitution / spec / plan / tasks 四阶段 | 只覆盖"一次功能"的生命周期 |
| **Log4Brains / adr-tools** | ADR 的浏览与索引生成 | 只做决策，不管过程与计划 |
| **Cline Memory Bank** | 跨会话上下文文件 | 只是"让 agent 记得"，不保证编号唯一、不校验结构 |

**它们的共同盲区**：都以"一次变更 / 一个功能"为单位。而你的目标是"项目连续演化"——需要的是**会话级档案 + 跨会话时间线 + 决策的开放选项**，这三样没人现成给你。

### C 类：用文档管流程

Spec Kit / Kiro / OpenSpec 都产出 `tasks.md`，但都是**依赖顺序**（1→2→3），不做**加权**。而真实项目里"先做哪个"往往不是依赖问题，是"用户可感知 vs 系统完备 vs 风险"的取舍。

三层（D/W/T）+ 六维 + 多视角加权，是把"重要性中偏高"这类无法比较的形容词，换成一个能排序的数。这部分没有轮子，因为**它是取舍模型，不是工具问题**。

### D 类：形式校验 —— 这些已经接进来了

| 能力 | 用什么 | 怎么分工 |
|---|---|---|
| 需求句式 | **EARS**（Kiro 原生格式） | 模板固化四次句式；E13 查「必须/不得」，W7 弱查规范措辞。见 `requirements-ears.md` |
| 外链与锚点 | **lychee**（Rust，异步、带缓存、`--include-fragments`） | 本脚本只管**仓库内相对路径**；外链交 lychee，且只在 **cron 跑**，不阻塞每次提交。见 `assets/ci/github-workflow-docs.yml` |
| 结构配置 | **`docs/_schema.json`** | 层、枚举、七段/六段、编号规则、文件名、状态词全部一处定义；加层/改目录名/加状态词都不改代码 |
| ADR 双向链 | **`supersedes` / `superseded_by`**（MADR 与 adr-tools 的约定） | 模板给字段位；E15 校验"指向存在且链能终止在活决策上" |
| 存量债治理 | **棘轮基线**（ratchet） | `--baseline` 让老项目也能当天接入：存量只许降，新债当场修 |
| 门禁落地 | **pre-commit + GitHub Actions** | `doc_init.py --ci` 直接生成；`--json` 输出便于接其他看板 |
| 习惯落地 | **`AGENTS.md`** 片段 | 把"开场建档、收尾四连跑"从"需要被想起的技能"变成"默认加载的约束"。见 `assets/agents-snippet.md` |

## 明确不接的，及理由

| 不接 | 理由 |
|---|---|
| 整套换成 sphinx-needs / Doorstop / StrictDoc | 它们强在**需求→设计→测试的追溯矩阵**，但会把文档绑到 Sphinx / `.sdoc` / 每需求一个 YAML 的形态，你现有的 8 层中文目录结构与叙述性文档没法直接套；迁移成本远大于收益。**如果你的项目将来要过合规审计（ISO 26262 / DO-178C / IEC 62304），那应该反过来——用 StrictDoc 或 sphinx-needs 承载契约层，本实践只保留过程层与计划层。** 这是唯一值得整体更换的场景。 |
| 整套换成 BMAD / Spec Kit | 它们解决的是"一次变更怎么讲清楚"，不解决"项目连续演化怎么留痕"。而且都是重流程，与你"轻到一次会话能跑完"的设计目标冲突。**可借鉴的是格式**（Spec Kit 的 constitution ≈ 契约层；OpenSpec 的 delta spec 思路可用于"本次会话改了什么"）。 |
| Vale / markdownlint | 面向**对外文档的可读性**（风格、拼写、标题层级）。内部开发文档风格本来就杂，接进来只会产生大量噪音。文档要对外发布时再单独接。 |
| ReqIF / DOORS 互通 | 只在有外部供应商交换需求时才需要。真到那天，用 StrictDoc 做 ReqIF 导出更省事。 |

## 如果你要换，换哪一层

```
门面 / 契约 / 决策 / 运行        ← 对外口径层。将来要合规，这一层换 StrictDoc / sphinx-needs
过程 / 时间线                    ← 连续演化层。没有替代品，本实践的会话档案不可替换
计划（三层+六维+视角）           ← 取舍模型。没有替代品
校验                             ← 形式层。已全部外包给成熟工具
```

这个分界也是 `layer-model.md` 里"单向依赖"的另一种说法：**约束层可以被专业工具接管，过程层不行**——因为过程层的价值恰恰在于它不构成约束、却什么都记得。

## 一句话

自研的是**取舍模型**和**过程留痕**这两件没有轮子的事；凡是能用现成工具查的形式问题（链接、句式、枚举、取代链、存量债），一律不自造。
