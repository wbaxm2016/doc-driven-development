# 过程记录：一次会话一份双侧档案

## 三条硬规则

1. **过程不构成约束**：档案 `authority: 4` + `status: snapshot`。要让它成为约束，必须回写契约或新开 ADR。
2. **只记要点，不逐字转录**：原话摘句 ≤ 2 行；档案是索引，不是录音。
3. **发现即登记，不打断**：问题进收件箱后继续当前话题；用户不需要在对话里回应。

## 七段结构（顺序不可变，脚本会校验）

1. 本次范围（要解决什么 / **明确不做什么** / 承接上期）
2. 用户侧记录（分类表）
3. AI 侧记录（六项）
4. 决策与选项对比（八维表）
5. 开放项
6. 本次产出
7. 交接（下次从这里开始；**首行必须是「下一步：<计划任务编号>」**）

## 用户侧 8 类（一条消息可拆多类）

| 码 | 含义 | 落点要求 |
|---|---|---|
| `Q` | 提问 / 质疑 | 答在哪一段 |
| `R` | 需求 | 哪个 REQ / 哪份契约（**未入表要写明**） |
| `F` | 功能 | 哪个组件 / 哪条工作 |
| `E` | 实现探讨 | 结论或待决项 |
| `D` | 决策 | ADR 或档案 §4 |
| `C` | 确认 / 否决 | 被确认或被否的那一条 |
| `X` | 明确排除 | 排除理由（防以后重复提） |
| `O` | 其它（偏好、语气、边界） | 写进规范或偏好记录 |

每行都要有落点。"未定的决策"必须**同时**进 §5 开放项，否则会烂在档案里。

## AI 侧六项（缺一项，档案就不可对照）

1. **需求理解**：我把它理解成什么；与用户原话的偏差显式写出。
2. **实现思路**：为什么这样做；否决了哪些做法。
3. **组件归属**：落在哪个组件/文件/函数，对应哪个 REQ 或 ADR。
4. **系统位置**：依赖谁、被谁依赖、不参与哪条链路。
5. **gap 四列**：`期望 / 现在 / 证据 / 缺口`。**没有证据只能写"未核实"**，不许写"应该没问题"。
6. **本轮提出的问题**：`ISS` 编号 + 一句话。

## 决策对比：八维，允许"两者相当"

语义正确性 · 实现成本 · 改动半径 · 可逆性 · 长期维护 · 用户可感知 · 可验证性 · 风险

**保持开放性**（这是本实践最容易退化的地方）：

- 未采纳选项**不删**；写清"当时为什么没选"；
- 每条未采纳项给**回条件**（什么事实出现就该重新考虑）+ **触发信号**（可观察的）；
- 结论区写"选 X"和"**是否暂定**"；暂定必须带回条件。

## 决策回顾（收尾时做一次）

**只回顾用户拍板的决策**。agent 自己的实现选择不进回顾（去 §3.2 或收件箱）——否则每场几十个实现讨论都会被抬成「决策」，回顾就退化成仪式。

**每条四问**，写进 §4 决策块（不新建文件、不新建台账）：

| 项 | 答什么 | 不满足的判法 |
|---|---|---|
| 背景 | 为什么会有这条：触发它的具体事 + 之前的现状（行数 / 条数 / 报错，现查） | 只写「讨论后决定」⇒ 断链 |
| 影响 | 改变了什么：作废了哪条旧决策 / 哪些文件与断言要跟着动 / 留下哪条未决 | 只写「已落地」⇒ 断链 |
| 依据 | 谁的话或哪条规则：**用户原话照抄** / ADR / 任务号 | 空着或写成转述 ⇒ 断链 |
| 撤销条件 | 什么可观察的事实出现就该推翻它 | 空着或「以后再看」⇒ 断链 |

**候选要现查，一条都不凭记忆**：

1. 本会话对话与 §2 记录——找出用户拍板的那句原话；
2. `docs/30-决策/adr/` 的 mtime 与 `git log --since=<本场起点>`——新增或改过状态的 ADR；
3. 收件箱与待分诊里状态变过的 `ISS` / `Q`；
4. `git status --short` · `git log --oneline`——脏树与未落档的提交。

**断链与待定**：答不出的标「断链」，同时 `python scripts/devlog.py ask "…" --if "…"` 进待分诊（不占 `ISS` 号）；标着「待定 / 复述未过」的决策原样保留，不许在回顾里升格成「已定」；评审门 / 确认门没过完的需求与功能，也不借回顾推进状态。

**频率**：一场会话一次，不是每轮；新题进收件箱，不在回顾里开新的设计题。

**机器判据**：`devlog.py check` 的 `S12` 只判**最新一篇**的「依据 / 撤销条件」行在不在（占位算缺，「拍板：agent 自选」的块豁免）；写得对不对仍要人读。

## 问题收件箱

| 字段 | 要求 |
|---|---|
| `ID` | `ISS-nnn`，只增不复用 |
| `类型` | 缺陷 / 口径冲突 / 文档债 / 风险 / 待决 / 机会 |
| `影响` | 不处理会怎样，**具体到可感知的后果** |
| `状态` | `open` / `decided` / `deferred` / `done` |
| `落点` | 处理它的 ADR / 文件 / 计划任务 |
| `回到条件` | `deferred` 必填 |

**收件箱不是待办清单**：只保证"不会被忘掉"，排序由计划文档负责。
`done` 的条目移到「已闭环」表并**从主表删除**（否则编号重复会让校验报错）。

## 收尾动作（关会话语义）

1. 每场开发会话开头：先 `python scripts/devlog.py brief` 读一眼——上一场交接锚点、计划里还没完成的任务、收件箱 `open`/`deferred` 计数、待分诊条数；再 `python scripts/devlog.py new --title "主题"` 建档。**门禁**：上一场还有 `open` 待分诊项、或延期超过 5 条时，`new` 直接拒绝（exit 1），先把它们分诊掉。**轻档**改动（只改措辞、错字、格式、注释，不碰契约/ADR/计划/码表/脚本行为）不建档，只跑改动触及的校验——判据见 `SKILL.md` 硬规则 12，分级不豁免任何检查。
2. 过程中：用户侧分类边聊边记；AI 发现问题立刻进收件箱；**要用户定的问题**（「要不要 X」「A 还是 B」）用 `python scripts/devlog.py ask "问题" --if "什么变了它就作废"` 进待分诊——不占 `ISS` 号，所以门槛低，但一样会留到下一次开场。
3. 收尾：先做**决策回顾**（见上节；答不出的标「断链」并用 `ask` 进待分诊）→ 把待分诊分完（`python scripts/devlog.py pending` 应为空：转 `ISS` / 转 §5 / `drop` 带理由 / `defer` 带回条件）→ 填 §3/§5/§6/§7 → `devlog.py check` → `devlog.py index` → 回写计划文档状态。
4. 交接段必须能独立读：**首行是「下一步：<任务编号>」**（编号必须存在于计划 §5；计划全部完成时写「下一步：无」）、现在在哪、别踩的坑、读哪几篇。`devlog.py check` 的 `S8` / `S9` 会校验锚点与计划表是否对得上。
