# 计划模型：三层 + 六维 + 三视角

## 为什么需要它

只有过程档案时，你能回答"之前发生了什么"，但回答不了"接下来做什么、为什么是它"。
散落的"重要性：中偏高"这类形容词**无法比较任意两项**，等于没有排序。

## 三层（唯一分层判据）

判据：**会话收尾时能不能一句话说清"这个做完了"**。

| 层 | 编号 | 粒度 | 完成判据 | 生命 |
|---|---|---|---|---|
| 方向 | `D-n` | 1–3 个月，**3–5 个** | 一个能被复述的成功状态（不是任务列表） | 季度 |
| 工作 | `W-n.m` | 1–3 场会话 | 一条命令 / 一次实测 / 一份文档落地 | 周 |
| 任务 | `T-n.m.k` | 一场会话内勾掉 | 产物存在 + 验收可贴 + 考核四格写满 + 完成于有锚 | 天 |

- 说不清"做完了" → 它是**工作**，不是任务。
- 说得清但说不清"为什么值得做" → 它是**方向**，不是工作。
- **默认不设第四层**：空层是最典型的文档债。某方向工作 >15 才拆子方向，且先写 ADR。
- 编号前缀是**结构**，会被 P6 校验：`T1.2.3` 的「所属」必须是 `W1.2`。

## 任务有双亲：功能 + 工作

需求线与方向线不是两条并行流程，而是同一个开发整体的两个切面：需求线按「必须成立什么」切，方向线按「用户怎么走通」切；它们在**任务**上合流。

```
REQ ──► F ──► T
              ▲
D ──► W ──────┘
```

- 每个新任务**有且只有一个** `功能`（`F-nnn`）和一个 `所属工作`（`W-n.m`），两者都必须存在（`P14`）。
- 一个功能拆 1..n 个任务，一个工作含 1..n 个任务；两者可以互相跨——工作常常不是新功能，而是功能之间的接缝。
- `—（历史）` 只给先于双亲模型的存量任务，且只能标在**已完成**的任务上；新任务不给这个口子。

**判据三条**（任务是最小单元的完整定义）：

| 判据 | 要求 | 不满足怎么办 |
|---|---|---|
| 可实施 | 一场会话内能完成；改动边界清楚；没有「顺便」 | 拆成两个任务，或升级为工作 |
| 可验证 | 一条命令 / 测试能判真假 | 补验收，或降为工作 |
| 可考核 | 四格「做法 / 一致 / 代价 / 结论」写得满 | 合并、重写，或承认它只是个动作 |

## 考核在任务上，功能只留汇总

- **任务行**：`验收`（一条命令，在计划 §5）+ `做法 / 一致 / 代价 / 结论 / 完成于`（在 FEATURES 的「任务考核」表，`P15`）。
- **跨仓任务**：`完成于` 写 `<repo>@<hash>`（如 `DSH@7d47958`）——锚点回答「回滚到哪一步之前」，不是本仓 `git revert` 就会失败；`P15` / `E27` 只判非空与非「待提交」，判不出锚点在哪个仓，得靠这个形态写清楚。
- **功能行**：`考核汇总` 一行——`各任务考核见 T…｜整体一致：全/部分/偏差｜代价：S/M/L｜结论：保留/改造/撤回`；外加 `完成于`（最后一个任务的 commit，`E27`）。
- **汇总必须有来源**：功能至少有一条任务挂它；汇总点名的 `T` 必须存在且真挂在这个功能下（`P16`）。功能没有任务时只能标 `—（历史）`。
- 为什么下沉：功能可以很大，一条「考核」写的是整块能力的总结；只有任务说得清「这一场做到了哪、代价估错没有」。

## 方向从哪来（现状 → 工作 → 任务）

方向不是拍脑袋的路线图，也不是一开始就有的。它是开发者与 Agent 多轮对话的产物：

1. **现状（含定方向）**：`devlog.py brief` 给一屏，再多轮对话把「现在有什么、卡在哪、哪些是旧账、哪些是新问题」说清楚。现状是一组可核对的事实，不是一句总结；**方向是这一步的结论，不是独立的一步**——一条用户能走通的路，写进 `00-门面/方向卡.md`（见下一节）。方向卡没写出来，不要往计划里加 `D`。
2. **工作**：沿方向切成 1–3 场会话能独立验收的一段。
3. **设计**：在工作和任务之间，写设计卡（`00-门面/设计卡.md`，一个工作一张）——接口、可替换点、扩展点、失败边界、任务拆分；重要取舍开 ADR。设计定了再拆任务（`P19`）。
4. **任务**：把工作拆成一场会话能完成、能验证、能考核的最小改动。
5. **推进**：一个任务一个任务做；每做完一个，现状更新一次，下一轮从更新后的现状开始。

这不是单向流水线，是循环：**现状（含方向）→ 工作 → 设计 → 任务 → 推进 → 新的现状**。计划表只装已经定下来的 `D/W/T`；「现状」与方向卡是它们的前置，不是第四层。

## 方向卡：方向的唯一载体

方向不是一句「成功状态 + 依据」。它要能回答：从什么现状推出来、为什么现在做、谁走这条路、分几步、步与步之间的接缝谁负责、什么算走通。这些写在一张卡里（`00-门面/方向卡.md`，一个方向一行），计划 §3 只登记 `编号 / 方向 / 卡 / 依据`。

| 字段 | 写什么 | 机器判 |
|---|---|---|
| **现状** | 现在有什么、卡在哪、哪些是旧账、哪些是新问题 | `P18`：不能空 |
| **为什么是现在** | 为什么这条方向比别的更该先走 | 人读 |
| 用户 · 起点 | 谁走这条路、从什么状态开始 | 人读 |
| **成功状态** | 可观察的终点（一句话） | `P18`：不能空 |
| 路径（3–7 步） | 每步用哪些功能 / 工作；步骤可独立验收 | 人读（步数不机器判） |
| 接缝 | 步与步之间的状态 / 权限 / 失败 / 空状态：上一步的输出或失败怎么影响下一步。**模块内部的异常处理归设计卡的「失败边界」，不写在这里** | 人读（ADR-003 的已知缺口） |
| 不覆盖 | 这次明确不做什么 | 人读 |
| **走通验收** | 一份可执行的 walkthrough 或 E2E：干净环境按路径走一遍，每步记观察 | `P18`：不能空 |
| 关联 | `REQ` / `F` / `W` / `ISS` | 人读 |

**接缝是方向卡与「功能清单」的分水岭**：写不出接缝，说明这条方向还只是几个功能的拼盘。

**走通验收不能压成一条 `verify:` 命令**：机器只判「走通记录存在、每步引用的功能存在」（现在连这个都还没做），走没走通、体验能不能接受，人判。这也是为什么 `P18` 只判三格——判多了会变成"填表仪式"。

## 设计卡：工作与任务之间的可替换性检查

设计不是实施的一部分，也不能拆成每个任务里各写一段实现思路——那样功能级的可替换性没人负责，任务拆完才发现接口不对，返工落在实施阶段（ADR-003 备选 F）。所以设计是**工作之后、任务之前**的一步：一个工作一张卡，写在 `00-门面/设计卡.md`，标题是 `## K<n> · W<n.m> · 标题`（工作号是 `P19` 认的锚）。

| 字段 | 写什么 | 机器判 |
|---|---|---|
| **接口** | 对外暴露什么、依赖什么；哪些是稳定契约 | `P19`：不能空 |
| **可替换点** | 哪些实现细节最可能变（数据源 / 外部服务 / 算法 / UI / 存储 / 权限）；换实现要改几处 | `P19`：不能空（确实没有的写「无」+ 为什么，只写「无」按空算） |
| 扩展点 | 以后的开放问题 / 新功能从哪里接进来 | 人读 |
| **失败边界** | 失败、超时、重试、回滚、空状态怎么处理 | `P19`：不能空 |
| 任务拆分 | 这份设计拆成哪些任务；每个任务改哪一块 | 人读 |
| 取舍 | 备选设计与为什么选它；重要取舍开 ADR | 人读 |

**按改动大小伸缩**：小改动写三行（接口 / 可替换点 / 失败边界）；没有可替换点的写「无」并说明为什么；大改动才写满六格。判满六格会把设计门变成填表仪式——和方向卡只判三格是同一个理由。

**设计门**（卡定稿前、拆任务前，人评审）：接口稳定吗、可替换点隔离了吗、扩展点合理吗、失败边界写清了吗、任务拆分覆盖设计吗。**卡没定，不拆任务**——`P19` 判「待开工 / 进行中的工作有没有卡」（已做完的工作不追溯，与 `P18` 的存量策略一致），并查卡里的工作号在不在 §4（孤儿卡）、一个工作有没有两张卡。

**回到设计**：考核发现「这个实现要可替换」或「换个实现要改很多处」时，旧设计下拆出的任务先标 `搁置` 或 `撤回`，重新设计后再拆新任务——不是只补一个补丁任务（ADR-003 §4）。

**与技术设计的分工**：`10-架构/technical-design.md` 写系统为什么这样搭（稳定的架构描述）；设计卡写「这一块以后要换，换哪里、换一处要改几处」，随工作产生、随工作归档。两处都在定义「怎么搭」时，删弱的那份（硬规则 1）。

## 状态词表（唯一来源：`_schema.json` 的 `plan.states`）

| 状态 | 含义 | 参与排序 |
|---|---|---|
| `待开工` | 还没动手 | ✅ |
| `进行中` | 本次会话正在做 | ✅ |
| `已实现（未验收）` | 代码在，但门禁/判据没过 | ✅（**不等于完成**） |
| `已完成` | 门禁或判据已过，有证据 | ❌ 不排 |
| `阻塞` | 在等外部条件 | ✅（但通常被前置卡住） |
| `搁置` | 主动不做，等回到条件 | ✅ |

**写不在表里的词，`plan.py check` 会直接报 P3。** 这是刻意的：旧版只认硬编码的「已完成」，写「完成」的任务会被静默当成未完成继续参与排序——比报错难查得多。

要加状态词，改 `_schema.json` 的 `plan.states` 与 `done_states` 两处（同一文件），不要改代码。

## 六维（统一方向：分越高越该先做；成本取反）

| 代号 | 维度 | 5 分含义 |
|---|---|---|
| `U` | 用户可感知 | 用户当场能看见或用上 |
| `C` | 闭环贡献 | 直接补齐某个门禁/闭环缺口 |
| `S` | 系统完备 | 补的是能力空洞，不是打磨 |
| `R` | 正确性风险 | 会产出错的数或静默失效 |
| `V` | 可验证 | 做完立刻能判真假 |
| `E` | 实施成本（取反） | 半场会话以内 |

## 三视角（= 三行权重；加视角只是加一行）

| 视角 | U | C | S | R | V | E |
|---|---|---|---|---|---|---|
| 尽快看到效果 | 5 | 4 | 2 | 3 | 2 | 2 |
| 系统更完备 | 2 | 4 | 5 | 3 | 3 | 2 |
| 核心功能优化 | 2 | 2 | 3 | 5 | 4 | 2 |

计分：`score = Σ(权重×分值) / Σ权重`，保留两位；**只有任务层有分值**——方向和工作的顺序是人的判断，不打分，别拿分数去比两层之间的东西。

## 三条硬约束（优先于分数）

1. **门禁 > 优先级**：门禁未全绿，后续阶段只许做设计，不许实施。
2. **一票置顶**：`R=5` 且改动已存数据/已生效契约 → 不看分数直接置顶。
3. **前置未解不排期**：排序视图里标 `⛔`，不进 Top。

> 这三条存在的理由：不让"分数"变成绕过门禁的借口。
> 注意：1 和 2 是**人**的约束，脚本不判——脚本只保证 3（`⛔`）与分数算得对。

## 操作

```bash
python scripts/plan.py check            # P1–P19：编号 / 分值 / 状态词 / 所属与前置 / 方向卡 / 设计卡 / 双亲 / 考核
python scripts/plan.py check --json     # 给 CI 用
python scripts/plan.py index            # 重算各视角排序视图，写回文档生成区
python scripts/plan.py index --check    # 只比对，CI 用
python scripts/plan.py next             # 唯一出口：第一个视角的第一名 + 方向 → 工作 → 任务 路径
python scripts/plan.py next --json      # 机读：每个视角的第一名
python scripts/plan.py tree             # 只读全貌：方向 → 工作 → 任务（--html 出单文件页面）
```

`next` 回答「下一步做什么、为什么是它」：默认取**第一个视角**的第一名（视角表第一行），并把所属方向 / 工作 / 功能与弱项一起打出来；其它视角的第一名若不同会并列列出——**排序不是唯一答案，先看哪个由人定**。全部完成或被前置阻塞时输出「无可排任务」，不瞎挑。

`--help` 只打用法，不写生成区（写盘只发生在 `index`）。

脚本按**表头**识别维度列（单个大写字母列即维度），因此：加维度＝加列+加权重，加视角＝加一行，**都不改脚本**。

`P14`–`P16` 要读功能台账：`plan.py` 按 `_schema.json` 的 `names.features`（缺省 `FEATURES.md`）在操作层目录里找。**台账缺失不是「没有功能」**——它会报 `P14` 并停下，否则三个码会一起沉默，变成 `errors=0` 的假通过。

> 「前置未解不排期」要能被机器兜住，前提是**前置编号必须存在**：写错一位数字（`T1.1.1` 打成 `T11.1`）会让那条任务永久停在 ⛔，
> 而排序视图看上去完全正常。所以 P11（前置不存在）与 P12（工作指向不存在的方向）是硬校验，不是提醒。

## 状态词纪律

`已实现（未验收）` ≠ `已完成`。前者只是代码在，后者要门禁/判据过。
`已完成` 是有代价的状态：验收、任务考核四格、完成于三件齐了才算（`P15`）——先写「已完成」再补考核，`plan.py check` 会当场拦下。
状态只允许被**证据**推进：实测输出、ADR、测试通过。禁止"感觉做完了"。

## 演进原则

1. 加维度只加列，不改机制（例：出现"错过窗口就失效"的任务时加 `时敏性`）。
2. 加视角只加权重行。
3. 拆第四层需 ADR + 触发条件（工作数 >15）。
4. 本文件 >200 行才按方向拆片。
5. **一旦出现两份都在定义"下一步"，删掉弱的那份**，不做两边同步维护。
