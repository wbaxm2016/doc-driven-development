# 校验规则：机器能判的，绝不靠人记

四份脚本各管一段，码不重叠：

| 脚本 | 管什么 | 码段 |
|---|---|---|
| `doc_check.py` | 全库形式一致性（含 `_delta` 契约增量） | `E*` 阻断 / `W*` 提醒 |
| `devlog.py check` | 会话档案与问题收件箱 | `D*` 收件箱 / `S*` 档案 |
| `plan.py check` | 计划编号、分值、状态词；方向卡；设计卡；任务双亲与考核（读功能台账） | `P*` |
| `verify.py` | 按契约 `verify:` 真跑可执行入口 | 无码：退出码即结论（0 全过 / 1 有失败 / 2 环境问题）；`--strict` 把「被状态跳过」也算失败（默认只 WARN 跳过数） |

**下面每个码都在代码里存在，代码里没有的码不许写进本表。**（旧版曾出现「文档列了 W4/W5 但代码没实现」——那比没有规则更坏：它让人误以为已经守住了。）

## doc_check.py

> `_schema.json` 与 `_layers.json` 都缺时**直接 exit 2**：层表无从判断，按内置 8 层猜会让 5 层项目多出 3 条假 E9（ISS-013）。补齐办法见报错行（`doc_init.py --target .` 幂等）。

### 错误（阻断，exit 1）

| 码 | 规则 | 常见原因 |
|---|---|---|
| E1 | 缺 front-matter | 新建文件忘加 `---` 块 |
| E2 | 缺必填字段 | `title/layer/domain/status/authority/updated/summary` 少一个 |
| E3 | 枚举越界或位置错 | `layer` 不在 `_schema.json`、`status`/`authority`/`domain` 越界、文件所在目录与 `layer` 不符 |
| E4 | `title` ≠ 正文 H1 | 从模板复制后忘改其一（最常犯） |
| E5 | `summary` 空或 > 80 字 | 把正文当摘要写 |
| E6 | `updated` 非法或未来日期 | 手填错年份 |
| E7 | 相对链接断链 | 文件移动后路径没改；**代码围栏内的链接不检查** |
| E8 | `superseded` 缺 `superseded_by` | 只改了状态没标取代者 |
| E9 | 某层为空 | 建了层没内容：加一篇，或从 `_schema.json` 删层 |
| E10 | ADR 文件名/H1/六段不符 | 文件名不是 `ADR-<三位>-…`；H1 不以 `ADR-` 开头；缺段或顺序错（`## 附录` 豁免） |
| E11 | ADR 索引与 `adr/` 目录不双向一致 | 新增 ADR 未登记索引；或索引指向已删除的 ADR |
| E12 | ADR 编号重复 | 复制粘贴没改号 |
| E13 | 契约层缺「必须」或「不得/不许」 | 把契约写成了说明文，失去约束力 |
| E14 | 文件名含空格或带版本号 | 用 `-v2`、`_final` 表示版本（版本走 front-matter 或 Git） |
| E15 | 取代链断裂 | `superseded_by`/`supersedes` 指向不存在的 ADR；或取代链停在一个自己也 superseded 的 ADR 上 |
| E16 | 出现未登记的术语旧称 | `50-术语/别名表.md` 登记了禁用别名，别处仍在用 |
| E17 | 超出棘轮基线 | 存量问题数比基线多（只在 `--baseline` 下生效） |
| E18 | 需求行缺 `verify:` | 编号单元格是整条 `REQ-nnn` 的表格行，缺 `verify:` 列、单元格为空或只写 `— / 待补 / TBD`；**delta 围栏里的增量行同判**（T1.2.2 / T1.1.2） |
| E19 | 存在未合并的契约增量 | `_delta/` 根目录有 `status: proposed` 的 DELTA；或根目录 delta 不是 `proposed`；或 `_archive/` 里的 delta 不是 `snapshot`（合并后必须归档） |
| E20 | delta 锚点与目标冲突 | `before` 在目标中出现 0 次或 >1 次；ADDED 的编号已存在、插入位置找不到；缺 before/after 代码块；增量行列数与主表不符；目标文件含合并冲突标记 |
| E21 | 归档 delta 与目标不一致 | 已归档 delta 的 `after` 在目标中出现 ≠ 1 次（合并丢失或目标被后续改动）；REMOVED 的行仍能在目标里找到 |
| E22 | 需求行状态词不在白名单 | 只允许 `待实现 / 已实现 / 阻塞 / 搁置 / 作废`；与 `verify.py` 的跳过集合对齐——写成别的词，`verify` 既不会跑也不会报 |
| E23 | 「已实现」的需求指不出出处或缺用户确认 | 状态为 `已实现` 时：「依据」要有可核对的锚（`ADR-nnn` / `ISS-nnn` / 任务号 / 文件路径）；`确认` 要有 `复述✓`/`采纳✓` + 日期 + 档案落点（先于确认门的存量行写 `—（历史）`） |
| E24 | 功能台账行不合规 | 状态词不在 `待评审/已评审/实施中/已对照/已验收/搁置/撤回`；`满足的需求` 引用了不存在的 `REQ-nnn`；`已对照/已验收` 的代码入口不存在；`已验收` 缺 `verify:` 或证据；`已评审` 及以后缺「评审」结论；`—（历史）` 只允许停在 `已验收`，且不能给挂需求的新功能背书 |
| E25 | 未使用（并入 `W8`） | 这条判据最初是「需求没有功能覆盖」的阻断错误；实跑发现它会挡住「需求先行、功能后补」的正常节奏，于是降级为提醒 `W8`。编号不复用 |
| E26 | 证据引用了不存在的自测组 | 功能行「证据」里写「第 N 组」时，N 必须真的存在于 `scripts/self_test.py`（该项目有该文件时才判） |
| E27 | 已验收的功能缺考核汇总或回滚锚点 | 「考核汇总」是一行：`各任务考核见 T…` + 整体一致 / 代价 / 结论（四格在任务级）；`已验收` 还要有「完成于」（commit 短号）；`撤回` 必须写汇总理由。存量行（`—（历史）`）豁免 |
| E28 | 表格某行的格数与表头不符 | cell 里出现未转义的竖线（例如把 `| ID | 状态 |` 直接写进一格）会把整行切错位：这一行的每一格都往后挪，`E18` / `E24` 读到的是别人的内容。用 `\|` 转义，或改写成语词（「A / B / C 三列」）；分隔行（`|---|`）也按表头格数比 |
| E29 | 会话档案「3.7 想法候选」不合规 | 类别不在 `目标 / 愿景 / 功能 / 需求`；**原话在出处里查不到（逐字）**——改一个字、换标点都算；出处文件不存在；建议落点里的 `D-n` / `REQ-nnn` / `F-nnn` 在整个项目里不存在；同一句原话在 ≥2 篇档案里重复建议。核对原话时跳过「3.7」这一节本身，否则表格自己就能证明自己。**活文档出处必须带版本日期**（`路径.md（YYYY-MM-DD）`）：带日期只核文件存在与日期合法，不核逐字——引文记的是那一版（REQ-025 / ISS-082）；不带日期的 `.md` 出处直接拒收 |
| E30 | 会话档案「3.8 预审记录」不合规 | 缺五列（指向 / 逐字引文 / 疑点 / 建议动作 / 裁决）；表头出现「状态 / 确认 / 评审 / 考核」列——预审不是台账；指向里的 `.md` 文件不存在；**引文在指向文件里查不到（逐字）**——只对「待裁决」的行判，已采纳 / 已驳回的是当时快照，修复改了原文也放行；建议动作不在 `补证据 / 改条款 / 维持`；裁决不在 `待裁决 / 采纳 / 驳回`；「对齐门 / 发版 / 回滚 / 开放问题收口」条目没写「不适用」却给了建议，或反过来。核对「本档」引文时跳过「3.8」这一节本身 |
| E31 | 增量取代链断了 | 归档 delta 的 front-matter 写了 `superseded_by: DELTA-nnn`，但项目里没有这个编号的 delta（proposed 或 archived 都算）。取代链只保证「被取代的一方」——它的 `after` 允许已被后续 delta 删掉/改掉 |

### 提醒（不阻断，收尾前应清零）

| 码 | 规则 |
|---|---|
| W1 | `status: active`，但正文首段自述「草案 / 待评审 / 规划中 / 未实现」 |
| W2 | 两份文档 `summary` 完全相同（"两处在说同一件事"的唯一机器信号） |
| W3 | 段内是占位 `原文未记录`（待补） |
| W4 | `superseded_by` 是 `待补/未标注` 之类的占位，不是 ADR 编号 |
| W5 | 引用块里的「补记」缺 `补记于 YYYY-MM-DD` 日期戳 |
| W6 | 用了绝对路径链接（换目录就断） |
| W7 | **编号单元格是整条 `REQ-nnn`** 的条款行没有任何规范措辞（`WHEN/IF/WHILE/GIVEN/SHALL/当/若/一旦/必须/应/不得/不许`）——大概率是个名词短语，不是可判真假的需求；变更记录里顺带提到需求编号不算条款行（ISS-018） |
| W8 | 需求还没有功能覆盖：契约层定义的每条 `REQ-nnn`，功能台账里至少有一行引用它；只引用示例（`README.md` 与 `_delta/` 里的编号不算定义）。需求可以先写、功能后补 |
| W9 | 已验收 → 对照行缺失：FEATURES 里 `已验收` 且不在存量豁免清单（F-001–F-020）的功能，在 `40-运行/功能对照.md` 没有行。只证明「有行」，不证明「对照过」——补行或写明为什么不需要 |
| W10 | 设计卡选项空间形状不合规：待开工 / 进行中工作的设计卡缺「选项空间」表、少于 3 个方案、没有「不做 / 少做」、被否方案没有回到条件。只判形状，不判「广度够不够」——3 个同轴方案能过，仍靠人读；存量已做完工作的卡不追溯 |

## devlog.py 待分诊（开工门禁）

门禁不是码，**退出码即结论**：

| 命令 | 判什么 | 退出码 |
|---|---|---|
| `devlog.py ask "…" --if "前提"` | 记一条要用户定的问题（`Q<n>`，不占 `ISS` 号） | 0 / 2 |
| `devlog.py pending` | 列出 `open` / `deferred` 与各自前提 | 0 |
| `devlog.py pending --clear Q1 --as s5\|drop\|defer [--note "…"]` | 其它出口：`s5` 转开放项、`drop` 必须写理由、`defer` 要求该条已有前提 | 0 / 2 |
| `devlog.py pending --clear Q1 --as iss --relation new --type … --impact … --to … [--nature 可关闭\|开放]` | **转正**：自动分配下一个 `ISS-nnn` 并追加收件箱主表一行；三格人判字段必填，`--nature` 缺省按类型推断（机会 / 待决 = 开放） | 0 / 2 |
| `devlog.py pending --clear Q1 --as iss --relation merge\|extends\|updates\|duplicate:ISS-nnn` | 不新增行，只把待分诊行标成「→合并入 / 扩展 / 更新 / 重复于 ISS-nnn」；内容并入靠人（脚本不动别人的行） | 0 / 2 |
| `devlog.py inbox [--similar "一段文字"]` | 新增前查重：按字符二元组重合度列出可能相关的开放条目（**候选**，不是判定） | 0 |
| `devlog.py features [--state 实施中]` | 功能对照的取数：列出功能台账里的行（只读；合规判定在 `doc_check` 的 `E24`） | 0 |
| `devlog.py new` | 还有 `open` 项、或 `deferred` > 5 → 拒绝建档 | 0（通过）/ 1（被门禁拦下）/ 2（参数或环境） |

> **转正前必须先查一次**（ISS-031）：`--as iss` 不给 `--relation` 时，脚本先摆出字面候选再 exit 2。候选只是候选——**包含、扩展、还是独立，要人判**；判完用哪一种 relation，就是把判断落成一次选择。

> 文件在仓库根 `.dd/pending/`：不进 `docs/`（躲开 `doc_check` 的形状检查）、不进 git（临时问题不该进历史），但关掉会话仍留在盘上。它只判**「写了没清」**，判不了**「有没有写」**——没记下来的问题不会因为这套机制自己出现。

| P18 | 方向卡里缺计划中的 `D`，或「现状 / 成功状态 / 走通验收 / 接缝」为空；走通验收缺 `@YYYY-MM-DD` 复核日；路径 / 接缝 / 走通验收里引用了不存在的 `F-nnn` / `W<n.m>` / `K<n>`；卡里有 `D` 而计划没有（孤儿方向）；方向卡文件缺失 |
| P19 | 待开工 / 进行中的工作没有设计卡；卡里「接口 / 可替换点 / 失败边界」为空（只写「无」按空算）；卡里有 `W` 而计划 §4 没有（孤儿卡）；一个工作挂了两张卡；设计卡文件缺失 |
| P20 | 方向卡「链路」表里的行不合形式：编号不是 `L<n>`；涉及功能点少于 2 个或引用了台账里不存在的 `F-nnn`；起点 / 终点 / 涉及功能点 / 关键接缝 / 走通验收有空；走通验收缺 `@YYYY-MM-DD` 复核日；记了「最近走通」却缺结论或证据；关键接缝 / 走通验收 / 证据里引用了不存在的 `W<n.m>` / `K<n>`。**缺链路表不报错**（加分层）；走没走通、接缝归谁不判（REQ-039–041、ADR-006） |

`plan.py` 的错误同样带码打印（`ERROR [P11] ...`），可以直接 grep，与 `doc_check.py` / `devlog.py` 一致。

## plan.py new-feature

它不是校验码，是**写入口**：一条命令写 `REQ` / `F` / `W` / `T` / `K` 五件套。机器判的边界就三条——

| 行为 | 判据 |
|---|---|
| 编号 | 默认从各表**首列**取 `max+1`；正文里的 `F-999` / `REQ-999` 反例不算。显式编号要过形态与撞号检查 |
| 落点 | 按表头名定位：需求行插需求表尾、功能行插在 `F-001` 之后（ISS-047）、`W` 插 §4 尾、`T` 插 §5 尾、`K` 插设计卡尾 |
| 写不写 | 先验「改完之后」的 `plan.py validate`，只拒这次改动造成的**新**错误；任一输入错误 → exit 1 且五份文件零写入；未知参数 → exit 2；`--dry-run` 零写入 |

`new-feature` 判不了内容质量（需求句是否可观察、设计是否成立），仍归对齐门 / 设计门的人读。

> P11/P12 存在的原因：引用不存在的编号时，那个任务会被永久标 ⛔（或让读者以为方向还在），
> 而分数与排序看起来一切正常——这是最难自己发现、也最贵的一类静默失效。
>
> P13 存在的原因（ISS-035）：表格被一个空行或一处断行切开后，后半段的第一行会被当成表头，
> 于是「errors=0」只覆盖了前半段——实测 30 个任务只看到 26 个。规则只认编号/日期形态的表头，
> 不会把「ID / 编号 / 视角 / 日期」这类真正的表头误判。

---

## 为什么这几条必须是机器判

- **E4**：`title` 与 H1 不一致，会导致索引显示一个名字、读者看到另一个名字。
- **E7**：断链是文档体系最常见的腐烂方式，且肉眼几乎发现不了（引对了文件、引错小节照样"看起来没问题"）。
- **E11/E12/E15**：一旦索引与目录不一致、"哪个决策还有效"就失去唯一入口；取代链断了，成因追溯就断了。
- **E13**：没有「必须/不得」的契约层会退化成解释文——它会一直"通过评审"，直到某次实现跑偏才被发现。
- **E18**：`verify:` 写成「人工看一眼」或占位符，契约就又变回不可执行——CI 不会跑它，人也不会。delta 的增量行放进代码围栏只是为了「不被当成已合并条款」，**不是豁免区**；围栏里缺 `verify:` 同样报 E18，否则围栏会变成新的假通过通道。
- **E19**：存在未合并的 delta，就是「契约已改、主文件未改」的窗口期。不把它报出来，窗口期会慢慢变成永久分叉：读者按主文件实现，作者以为已经定了。
- **E20**：锚点不是摘要，是机械匹配的原文。出现 0 次说明目标已经变了、出现多次说明会「顺手改错行」，两种都不能自动合并；冲突标记同理——它进了库，就没有哪一边算「已定」。
- **E21**：归档只证明「当时合并过」，不证明「现在还在」。`after` 在目标里消失说明后来被改掉了，正确动作是开新 delta 留痕，而不是改历史或悄悄重写归档。
- **E22/E23**：「文档是唯一事实源」最容易破在"实现"这一步——代码做完了、需求行改个词就算完成，但没人说得清依据是什么。E22 把状态词钉死（与 `verify.py` 的跳过集合对齐），E23 要求「已实现」必须指得出 ADR / 任务 / 文件。**它判不了「先设计后实现」的先后顺序**，只判「声称实现了，出处说得出来」——这是这条目标里唯一能机器化的那一半。
- **E24**：功能的"设计"与"已实现"是同一张表的两个状态，不是两份清单（两份必然漂移）。机器能判的只有：需求引用存在、入口路径存在、已验收有 `verify` 与证据、**评审结论在推进前就写过**；**判不了"三问答得对不对"**，也判不了"行为是否覆盖验收口径"——那是对照与评审时人读的部分，别把它当自动核对。
- **E27**：考核是**给用户看的实现回顾**，也是回写前的最后自检。考核下沉到任务后，功能行只留一行汇总：它回答「这些任务整体值不值」，必须点得出是哪几个任务（`各任务考核见 T…`）；「完成于」是回滚锚点——没有它，"回到这个功能之前"只能靠记忆。结论为「改造」，或开放问题要求实现更可调整 / 可优化 / 可扩展时，回到「定任务」补任务，而不是硬推到已验收。机器只判汇总的槽位与锚点在不在，判不了写得中不中肯。
- **P18**：方向最容易退化成两种东西——一句口号，或一张功能清单。四格必填是「从哪来（现状）、到哪去（成功状态）、怎么算到（走通验收）、步与步之间怎么接（接缝）」的最小证据；REQ-018（2.8.1）再判走通验收的 `@复核日` 与 `F-nnn` / `W<n.m>` / `K<n>` 引用存在——**机器只判存在**，步数与接缝质量仍人读（ADR-003 的已知缺口已从「三条全无」收窄为「语义人读」）。卡缺失时只报一条、不逐行刷屏：一个没迁移的项目要能一眼看出「少的是卡」，而不是被七条同义报错淹掉。
- **P19**：设计最容易变成两样东西——实施里顺手写的几句思路，或一张从不影响任务拆分的表格。只在**工作还没做完**时要求卡（`待开工` / `进行中`），存量不追溯；只判三格（接口 / 可替换点 / 失败边界），扩展点与任务拆分靠人读——判满六格会把设计门变成填表仪式，和 `P18` 只判三格是同一个理由。孤儿卡与「一个工作两张卡」必须报：前者说明工作被删了、设计还挂着，后者说明设计有两份真相，而两份真相里通常有一份是旧设计的残留。
- **P14/P15/P16**：这三条把「任务是最小可实施、可验证、可考核的单元」变成可判的形状，而不是一句口号。`P14` 判**双亲**——需求线到功能断了就再也接不上，任务必须向上指得出功能；`P15` 判**考核下沉**——功能级四格一大会变总结，只有任务说得清代价估错没有；`P16` 判**汇总有来源**——汇总可以写得很漂亮，但点名的任务可能不存在，或者根本不挂在这个功能下（拿别人家的任务给自己背书）。三条都读功能台账：**台账缺失时不能当成「没有功能」跳过**，那会让三个码一起沉默，变成 `errors=0` 的假通过。
- **W8/E26**：对账的两端——**需求不能没人做**（W8：每条需求至少一行功能；提醒而非阻断，因为需求可以先于功能存在），**证据不能是编的**（E26：「第 N 组」得真有第 N 组）。W8 首跑就抓到"`_delta/README.md` 里的示例编号被当成需求"这种假账，所以定义只认契约层的非 README 文件。
- **P6**：编号本身就是结构信息（`T1.1.1` 属于 `W1.1` 属于 `D1`），乱掉的编号让"这个任务服务于哪个方向"无法机器推导。
- **S8/S9**：交接段是下一场会话的唯一入口。散文里的「下一步」读起来像结论，却可以不指向任何真实任务；把锚点固定在首行并与计划表互校，才让"从断点接上"变成可判事实。只判编号存在性、不判状态：历史档案指向的任务后来完成了，档案仍是对的（它记录的是当时）。
- **S10**：「每行都要有落点」以前只是散文——漏写一行，四件照样全绿，而"没回答的问题"最先消失的恰恰就是落点。脚本只判**有没有给**，判不了给得对不对；`—` / `待补` / `无` 这类占位一律当没给，否则它会变成新的假通过通道。
- **S11**：时间线是「按时间回溯」的入口，却不会自己更新；`new` 之后不重建完全静默，CI 也绿。只判「行数 ≠ 档案数」——抓得住最常见的漏，抓不住标题/日期改动（那些仍靠 `index --check`）。
- **S12**：决策回顾的四问里，机器只能判「依据 / 撤销条件」两行在不在（「背景 / 影响」已在 §1/§3 与选项表里，不重复要求）。只判最新一篇：存量档案没有这两行，追溯会让历史集体变红；「拍板 agent 自选」的块豁免——实现选择不是决策，强制四问会把回顾变成仪式。
- **W2**：这是「一个事实一处」的**唯一机器信号**——两份 summary 一样，通常意味职责没收敛。

## 修完全绿之后，剩下什么仍需人读

别把全绿读成零债务：

- 条款**写得对不对**（E13 只判「必须」二字在不在，判不了后面那句话是否可判真假；W7 只是弱信号）。
- 交叉引用的**语义正确性**（只判路径存在，不判「引对了没有」）。
- 两份文档是否在**语义上**说同一件事（只靠 W2 的 summary 相同这一条弱信号）。
- ADR 的撤销条件**是否已经成立**——需要定期人工复核，脚本不会主动提醒。
- 决策依据**是否真的支持**该决策。
- 外部链接是否失效——交给 `lychee`（见 `references/ecosystem.md`），不塞进收尾流程。
