# 功能台账

> **一张表两种读法**：筛 `待评审 / 已评审 / 实施中` 是设计视图；筛 `已对照 / 已验收` 是已实现清单。
>
> 状态链：`待评审 → 已评审 → 实施中 → 已对照 → 已验收`（`搁置` 旁挂）。
> **评审门**：把状态推到 `已评审` 之前必须答完三问——**满足需求吗**（挂哪条 `REQ-nnn`）、**能实现吗**（依赖与卡点）、**代价合理吗**（`S/M/L` + 一句话）——结论写进「评审」列（例：`满足✓ 可做✓ 代价M｜依据 ADR-001｜2026-10-31`）。
> **已评审及以后**：`满足的需求` 写 `REQ-nnn`（可多条，用 `、` 分隔）；`—（历史）` 只留给先于契约存在的老功能，且只能停在 `已验收`。
> **已对照 / 已验收**：`代码入口` 必须真实存在；**已验收**还必须有 `verify:` 与 `证据`（哪条命令/哪组自测 + 日期）。
> **考核在任务级**：`已完成` 的任务在下面「任务考核」表里各占一行；功能只留一行 `考核汇总`：`各任务考核见 T…｜整体一致：全/部分/偏差｜代价：S/M/L（同估或偏差原因）｜结论：保留/改造/撤回`。汇总点名的任务必须真挂在这个功能下（`P16`）。
> **历史功能**（`满足的需求` 写 `—（历史）`）：`考核汇总` 与 `完成于` 也写 `—（历史）`，不追溯。

## 2. 任务考核

> 每个 `已完成` 的任务一行：**做法 / 一致 / 代价 / 结论 + 完成于**。任务是最小可实施 / 可验证 / 可考核的单元，四格写不满就说明它该合并、该重写，或者只是个动作。
> `完成于` 写该任务落地时的 commit 短号（同一批提交可共用）；功能行的 `完成于` 取最后一个任务的那个。
